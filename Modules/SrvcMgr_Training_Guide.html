RTA-SUM Service Manager

Comprehensive training guide for the SrvcMgr module — managing SOME/IP service lifecycle, learning sessions, diagnostics, and fault handling on AUTOSAR-based automotive ECUs.

1 Introduction

What is SrvcMgr?

SrvcMgr (Service Manager) is a software component in the RTA-SUM (Standard Utility Module) product developed by ETAS GmbH for AUTOSAR-based automotive ECUs. It is specifically designed for the GM SUM platform and operates as a bridge between diagnostic tools, the Service Discovery (Sd) module, and other SUM modules to manage the lifecycle of SOME/IP services on an Ethernet-connected ECU.

What does it manage?

AreaWhatWhy
Service Lifecycle Activating and deactivating SOME/IP client/server services The ECU needs to dynamically control which services are running based on commands from the Service Power Manager (SPM)
Learning Sessions Triggering and monitoring the service discovery learning process (RID 0x0654) The ECU needs to discover and record which other ECUs provide which services on the Ethernet network
Diagnostic Support Reading learning table data (RID 0x0612), learning status (DIDs E0CC/E0CD/E0CE) Diagnostic tools need visibility into the service discovery state for troubleshooting
Fault Handling Setting/clearing DTC U19A6 variants (57, 54, 87) Faults must be reported when services fail to be learned or acknowledged

Who should read this?

  • New developers joining the SrvcMgr team
  • System architects needing to understand SrvcMgr's role in the SUM ecosystem
  • Testers writing or maintaining unit tests
  • Anyone integrating SrvcMgr with other ECU modules

2 Why SrvcMgr Exists

The Problem

Modern vehicles use SOME/IP (Scalable service-Oriented MiddlewarE over IP) for ECU-to-ECU communication over Ethernet. When an ECU boots up, it doesn't inherently know which services are available on the network or which ECUs provide them. This information must be discovered and persisted so the ECU can communicate efficiently.

The AUTOSAR Service Discovery (Sd) module handles the low-level discovery protocol, but it needs an orchestrator above it to:

  1. Decide when to start/stop services (coordination with power management)
  2. Decide when to trigger learning (diagnostics-driven, with safety preconditions)
  3. Report faults when expected services or subscriptions are missing
  4. Expose information to diagnostic tools about what has been learned

The Solution

SrvcMgr fills this gap. It sits as an application-level SWC (Software Component) on top of the RTE and coordinates between the diagnostic layer (Dcm), the SOME/IP Service Discovery (Sd), power management (SPM), startup coordination (SUSD), and fault monitoring (SSFM).

3 High-Level Architecture

Runnables (Entry Points)

SrvcMgr exposes its functionality through OS runnables mapped via the AUTOSAR RTE. These are the "entry points" that the OS scheduler or other modules call:

3.1 Runnable_SrvcMgr_Init (Startup, called once)

What: Initializes the SrvcMgr module.

Why: Services need their calibration state set up before any operations can begin. Some services may need to be permanently disabled ("calibrated off") based on vehicle configuration.

How:

  1. Sets the initialization flag to TRUE (preventing re-initialization)
  2. Calls Sd_InitializeServicesCalibrationState() to set all services to CalibrationON
  3. Invokes surveyServiceDisableCalibrations() to let external SWCs disable specific services
  4. If SdEnableExtendedLearningTableFormat is FALSE, zeroes out InstanceId and MajorVersion for all configured services

3.2 Runnable_SrvcMgr_ExecutionManager (Periodic)

What: A finite state machine (FSM) that coordinates SrvcMgr's operational lifecycle with the SUSD (Startup/Shutdown) module.

Why: The ECU goes through startup and shutdown phases. SrvcMgr must only perform its work when the ECU is in the proper power state, and it must gracefully handle shutdown — especially if an SPM request or learning session is still in progress.

How: See Section 4.1 for full FSM details.

3.3 Runnable_SrvcMgr_ActivateServices (On-demand, called by SPM)

What: Processes a batch of service activation/deactivation commands from the Service Power Manager.

Why: SPM determines which services should be active based on power modes, partial networking, etc. It delegates the actual SD API calls to SrvcMgr.

How: See Section 4.3 for full details.

4 Module Components Deep Dive

4.1 Execution Manager

File: Sum_SrvcMgr_Execution_Manager.c

The Execution Manager is the heartbeat of SrvcMgr. It runs periodically and implements a 4-state FSM.

States

StateValueMeaning
SUM_SrvcMgr_Init_and_Shutdown_Mode0x01Module is either not yet started or has been shut down. Default/initial state.
SUM_SrvcMgr_Run_Mode0x00Module is fully operational. Services can be managed.
SUM_SrvcMgr_Prepare_to_Shutdown0x02Shutdown requested, but an SPM request or learning session is still active.
SUM_SrvcMgr_Invalid_Mode0xFFRTE read of PermitExecution failed. Safety fallback.

FSM Transitions

How the PermitExecution Check Works

SUSD provides a bitmask called PermitExecution. SrvcMgr checks specific bits:

// Bit 0 (wakeup bit): Is the ECU awake?
if ((srvcmgr_execution_status | SUM_SRVCMGR_PERMITEXECUTION_MASK) == 0xFF)
    // ECU is awake -> transition to Run_Mode

// Bit 6 (reset bit): Has a reset been requested?
if ((srvcmgr_execution_status | SUM_SRVCMGR_RESETBIT_MASK) != 0xFF)
    // Reset requested -> begin shutdown
ConstantValuePurpose
SUM_SRVCMGR_PERMITEXECUTION_MASK0xFEBit 0 mask (wakeup)
SUM_SRVCMGR_RESETBIT_MASK0xBFBit 6 mask (reset)
SUM_SRVCMGR_EXEC_MASKING_PASSED0xFFAll bits set = pass

Shutdown Permission (Rolling Counter)

When SrvcMgr is in Run_Mode, it sends a rolling counter (0, 1, 2, 3, 0, 1, ...) as its ShutdownPermission to SUSD. This tells SUSD "I'm alive and not ready to shut down yet." When SrvcMgr is ready to shut down, it sets ShutdownPermission to 0xFF (SUM_SRVCMGR_ENABLE_SHUTDOWN).

Delayed Shutdown

The Sum_SrvcMgr_HandlerGetActivateServiceReq() function checks two flags before allowing shutdown:

  1. Sum_SrvcMgr_ActivateServiceReq — Is SPM currently processing a service activation request?
  2. Sum_SrvcMgr_LearningSessionReq — Is a learning session (RID 0x0654) in progress?

If either is TRUE, SrvcMgr transitions to Prepare_to_Shutdown instead of Init_and_Shutdown_Mode, keeping the rolling counter alive to prevent SUSD from forcibly shutting down.

One-Time DTC Actions

Important Behavior

When first entering Run_Mode, the Execution Manager performs DTC U19A6 actions exactly once, but only when battery voltage is available. This ensures that DTC evaluation doesn't happen with unreliable voltage readings. The Sum_SrvcMgr_DtcActionsDoneOnce static flag prevents re-execution.

4.2 Learning Session Manager

File: Sum_SrvcMgr_LearningSession_Manager.c

This is the most complex component. It handles all diagnostic data identifiers (DIDs) and routine identifiers (RIDs) related to the SOME/IP service learning process.

4.2.1 RID 0x0654 — Trigger Learning Session

What: A diagnostic routine that initiates a fresh service discovery learning process.

Why: When a vehicle is assembled or after maintenance, a technician needs to tell the ECU to re-discover all services on the Ethernet network. This RID is the trigger.

Preconditions (Enable Conditions):

All four conditions must be met

What: A diagnostic routine that reads the content of the learning table.

Why: Technicians and engineers need to see what the ECU has learned about the network topology — which services were found, from which IP addresses, on which ports.

4.2.3 DID 0xE0CC — Learning Table Status

What: Returns the current learning table state as a single byte.

Why: Quick check for diagnostic tools to see if learning has completed.

Possible values:

  • CLEARED — No learning data (table was cleared)
  • UPDATING — Learning in progress
  • ALL_SERVICES_LEARNED — All expected services found
  • LEARNING_COMPLETED — Learning session finished (may or may not have found all services)
  • LEARNING_INCOMPLETE — Learning finished but some services are missing

4.2.4 DID 0xE0CD — Client Incomplete Learning Table

What: Returns the list of client service IDs that were expected but not found during learning.

Why: When learning is incomplete, technicians need to know which client services are missing to diagnose network issues.

How:

  1. CheckRead: Verifies that the learning table is in LEARNING_INCOMPLETE or LEARNING_COMPLETED state
  2. ReadDataLength: Calculates response size = (number_of_missing_services × 2) + 2 bytes
  3. ReadData: Retrieves missing service IDs from Sd_RetrieveIncompleteLearningReasons() and merges with SSFM-reported missing services (deduplicated)

4.3 Service Manager

File: Sum_SrvcMgr_Service_Manager.c

What: Handles the actual activation/deactivation of SOME/IP services by calling SD APIs.

Why: SPM decides which services should be active/inactive, but it doesn't know the SD API details. SrvcMgr translates SPM's requests into the correct SD calls.

Activation Flow

Command Status Results

StatusMeaning
E_OK_LOCAL_ENABLEDServer service successfully set to AVAILABLE
E_OK_REMOTE_ENABLEDClient service successfully set to REQUESTED
E_DISABLEDService is calibrated off (CalibrationOFF)
E_GENERAL_ERRORService ID not found or SD API call failed
Service Groups (AUTOSAR SWS_Sd_00746)

Some services belong to Service Groups. Per AUTOSAR specification, services in a group must only be controlled via Sd_ServiceGroupStart()/Sd_ServiceGroupStop(), not via individual calls. SrvcMgr checks for group membership before choosing which API to call.

Why: Some vehicle configurations don't need certain services. Rather than leaving them active (wasting resources and causing false DTCs), they can be "calibrated off."

5 Feature Overview

5.1 DTC (Diagnostic Trouble Code) Management

SrvcMgr manages three DTCs, all under the U19A6 family. These are evaluated at specific trigger points and forwarded to the SSFM module.

DTC U19A6_57 — Invalid/Incompatible SW Component

What it detects: Expected acknowledgments not received from physical ECUs after subscribing to a service.

Trigger points:

  1. Execution Manager first run (one-time, when battery voltage available)
  2. After RID 0x0654 completion (success or failure)
  3. After Service 0x14 (Clear Diagnostic Information) via Runnable_SSFM_ClearDiagReq

Test Criteria:

ResultCondition
FAILLEARNING_INCOMPLETE AND num_Of_Missing_EventGroups > 0
PASSLEARNING_COMPLETED OR (LEARNING_INCOMPLETE AND num_Of_Missing_EventGroups == 0)

RTE Port: Rte_Write_PP_SrvcMgr_SSFM_U19A6_57_Status_invalid(TRUE/FALSE)

DTC U19A6_87 — Service Discovery Missing Message

What it detects: Missing message from service discovery — the learning table is incomplete.

How it works: Rather than directly setting/clearing a DTC, SrvcMgr forwards the learning table status and event context to SSFM via a composite structure:

DTC U19A6_54 — Service Discovery Missing Setup/Learn

What it detects: The learning table is in CLEARED state, meaning no learning has ever been performed.

ResultCondition
FAILSd_GetLearningTableState() == CLEARED
PASSSd_GetLearningTableState() != CLEARED
Note

DTC U19A6_46 is NOT managed by SrvcMgr — it is configured directly in DEM.

5.2 Extended Learning Table Format

The SdEnableExtendedLearningTableFormat calibration parameter controls how SrvcMgr interacts with the Sd module:

ValueBehavior
TRUEUses the actual InstanceId and MajorVersion from the service configuration
FALSEZeroes out InstanceId and MajorVersion for all services (legacy/backward-compatible mode)

5.3 SSFM Missing Service Tracking

SrvcMgr maintains a buffer (Sum_SrvcMgr_Ssfm_MissingServiceIds[]) to track service IDs reported as missing by SSFM. These are merged with SD-reported missing services when DID 0xE0CD is read, with deduplication to avoid reporting the same service ID twice.

.xpt and .ext files use ISO-8859-1 encoding. When editing:

iconv -f ISO-8859-1 -t UTF-8 template.xpt > template_utf8.xpt

# Edit the UTF-8 version, then convert back
iconv -f UTF-8 -t ISO-8859-1 template_utf8.xpt > template.xpt

11 AUTOSAR ECUC Parameter Definition (ParamDef)

SrvcMgr (Service Manager) manages the Service Discovery Learning Table — it handles learning sessions, tracks propulsion system active status, and monitors vehicle speed. It coordinates with DCM DIDs (E0CC, E0CD, E0CE) and RIDs (0654, 0612) for diagnostic interactions.
▶ M SrvcMgr 0..1 — Service Manager module
▶ C Sum_SrvcMgr_General 1..1 4 params — execution mask, periodicities, init

Sum_SrvcMgr_ExecutionManagerPeriodicityFLOAT1..11–65535100Execution Manager Runnable period (ms).
Sum_SrvcMgr_GenerateInitRunnableBOOL1..1—falseGenerate periodic runnable for RE_SrvcMgr_Init.

How SrvcMgr ParamDef works with the module
DID references (E0CC/E0CD/E0CE) for Learning Table diagnostics, RID references (0654/0612) for session control. COM signals (PropSysActv, VehSpdAvgDrvn) provide runtime inputs. Service-Based refs support SOME/IP architectures.
