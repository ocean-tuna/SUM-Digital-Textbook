1. Module Overview

Note: RTA-SUM SUSD Training Documentation — For the authoritative specification, refer to SDV-8002 and the design document in 10_Documents/20_Design/.

What is SUSD?

SUM_SUSD (Start Up Shut Down) is a software module in the Application Layer of the AUTOSAR architecture. It is part of the ETAS RTA-SUM (Standardized Utility Modules) product developed for the GM SUM platform.

SUSD is the central coordinator for an ECU's lifecycle — from the moment it wakes up to the moment it goes to sleep, resets, or powers off.

What does SUSD do?

FunctionOne-Sentence Purpose
Application State ManagerManages the ECU's operational state (Init → Run → Sleep/Off/Reset/Boot)
Application Start/ShutdownCoordinates wakeup source handling, permit execution, and shutdown voting
Battery Voltage MonitorMonitors voltage, classifies it (normal/under/over), and controls NvM write permission
Power Moding SlaveDetermines Vehicle Power Mode from primary and backup power mode signals
Run/Crank PlausibilityValidates the Run/Crank hardware signal and provides diagnostic monitoring
Diagnostic DID ServicesProvides UDS diagnostic data (E0D7 Activity Records, F088, F089, F09E, etc.)

2. Why SUSD Exists — The Problem It Solves

In a modern automotive ECU, dozens of software components need to:

  • Know when to start executing (which wakeup happened? is the voltage OK? is the power mode right?)
  • Know when to stop and vote on whether the ECU can shut down safely
  • Have a common understanding of the vehicle's power state
  • Protect NvM from corruption during low-voltage conditions
  • Report diagnostic information to external tools (wakeup history, activity records, power status)
SUSD centralizes all of this. It acts as the single point of truth for:
• "Should this SW-C be running?" → PermitExecution
• "Can the ECU shut down?" → ShutdownPermission voting
• "What is the vehicle power mode?" → VPM determination
• "Is the battery safe for NvM writes?" → Battery Voltage Monitor

4. Feature Deep Dives

4.1 Application State Manager

The Application State Manager is the heart of SUSD. It manages the ECU's operational state machine and decides when to request state transitions from BswM.

ECU Operating States

StateValueMeaning
SUM_INIT0Initial state — SUSD is initializing
SUM_RUN1Normal operation — BSW is in RUN state
SUM_SLEEP2Low-power state requested
SUM_RESET3ECU reset requested (diagnostic)
SUM_BOOT4Reprogramming request received
SUM_SHUTDOWN5Shutdown process in progress
Two Initialization Methods

Controlled by SusdGenerateInitRunnable:

  • FALSE (default): SUSD_Init() is called from a BswM action list during startup — simpler, one-shot
  • TRUE: A generated init runnable calls SUSD_Init() periodically until init completes — useful when init depends on external conditions
Scenario Walkthrough — Full Ignition Cycle State Transitions
Scenario
A complete ignition cycle from cold power-on through normal operation to sleep, showing every state transition the Application State Manager handles.
Implementation Example — Sum_Susd_StateManager (from SUM_SUSD.c) 
/* Main Application State Manager FSM - called from SUSD periodic runnable */
static FUNC(void, SUM_SUSD_CODE) Sum_Susd_StateManager(void)
{
    switch (Sum_Susd_ApplicationState)
    {
        case SUM_INIT:
            /* Check all initialization prerequisites */
            if (Sum_Susd_InitComplete() == (boolean)TRUE)
            {
                Sum_Susd_ApplicationState = SUM_RUN;
                BswM_RequestMode(SUSD_BSWM_MODE_REQ, SUM_RUN);
                Sum_Susd_DistributePermitExecution();
            }
            break;

        case SUM_RUN:
            /* Normal operation - monitor for shutdown/reset/boot requests */
            if (Sum_Susd_ResetRequested == (boolean)TRUE)
            {
                Sum_Susd_ApplicationState = SUM_RESET;
                BswM_RequestMode(SUSD_BSWM_MODE_REQ, SUM_RESET);
            }
            else if (Sum_Susd_BootRequested == (boolean)TRUE)
            {
                Sum_Susd_ApplicationState = SUM_BOOT;
                BswM_RequestMode(SUSD_BSWM_MODE_REQ, SUM_BOOT);
            }
            else if (Sum_Susd_AllModulesShutdownReady() == (boolean)TRUE)
            {
                Sum_Susd_ApplicationState = SUM_SHUTDOWN;
                BswM_RequestMode(SUSD_BSWM_MODE_REQ, SUM_SHUTDOWN);
            }
            break;

        case SUM_SHUTDOWN:
            /* Request EcuM to enter the configured shutdown target */
            EcuM_SelectShutdownTarget(Sum_Susd_ShutdownTarget, 0U);
            EcuM_GoHalt();
            Sum_Susd_ApplicationState = SUM_SLEEP;
            break;

        default:
            /* SUM_RESET, SUM_BOOT, SUM_SLEEP - handled by EcuM/BswM */
            break;
    }
}

4.2 Wakeup Source Management

SUSD maintains a live list of active ECU wakeup sources and routes them to the appropriate SW-Cs and SUM modules.

Wakeup Routing Table

Wakeup TypeSUM Modules Notified
Any wakeup activeSUM_ERRH, SUM_TCS, SUM_SOH, SUM_SrvcMgr, SUM_DIAG, SUM_SPM + all SW-Cs
CAN-related wakeupSUM_SSC, SUM_PNC
LIN-related wakeupSUM_LNM
CAN or LIN wakeupSUM_SSM

Wakeup Detection Records (DID 0xF09E)

SUSD stores up to 10 records in NvM (90 bytes total). Each record contains:

  • Record ID (1-based)
  • ECU Wakeup Detection Record ID (4 bytes, wakeup source bitmap)
  • Timestamp of occurrence (5 bytes, from TCS_SWC_Clock)
Scenario Walkthrough — Coordinated Startup with PermitExecution Sequencing
Scenario
ECU wakes up due to a CAN wakeup event. SUSD must identify the wakeup source, notify the correct subset of modules, and coordinate the startup sequence with proper PermitExecution ordering.
Implementation Example — Sum_Susd_WakeupSourceHandler (from SUM_SUSD.c) 
/* Process wakeup sources and route notifications to configured modules */
static FUNC(void, SUM_SUSD_CODE) Sum_Susd_WakeupSourceHandler(void)
{
    uint32 wakeupBitmap;
    uint8 idx;

    /* Read current wakeup sources from EcuM */
    wakeupBitmap = EcuM_GetValidatedWakeupEvents();
    Sum_Susd_ActiveWakeupSources = wakeupBitmap;

    if (wakeupBitmap != 0U)
    {
        Sum_Susd_WakeupActive = (boolean)TRUE;

        /* Notify all modules for any wakeup (ERRH, TCS, SOH, etc.) */
        for (idx = 0U; idx < Sum_Susd_CfgPtr->NumAnyWakeupPorts; idx++)
        {
            Rte_Write_WakeupNotification(
                Sum_Susd_CfgPtr->AnyWakeupPorts[idx], wakeupBitmap);
        }

        /* CAN-specific wakeup routing (SSC, PNC) */
        if ((wakeupBitmap & SUSD_WAKEUP_CAN_MASK) != 0U)
        {
            for (idx = 0U; idx < Sum_Susd_CfgPtr->NumCanWakeupPorts; idx++)
            {
                Rte_Write_WakeupNotification(
                    Sum_Susd_CfgPtr->CanWakeupPorts[idx], wakeupBitmap);
            }
        }

        /* LIN-specific wakeup routing (LNM) */
        if ((wakeupBitmap & SUSD_WAKEUP_LIN_MASK) != 0U)
        {
            for (idx = 0U; idx < Sum_Susd_CfgPtr->NumLinWakeupPorts; idx++)
            {
                Rte_Write_WakeupNotification(
                    Sum_Susd_CfgPtr->LinWakeupPorts[idx], wakeupBitmap);
            }
        }

        /* Store wakeup detection record (DID F09E) */
        Sum_Susd_StoreWakeupRecord(wakeupBitmap);
    }
    else
    {
        Sum_Susd_WakeupActive = (boolean)FALSE;
    }
}

Shutdown Timers & SPM Sequencing

Refresh Timer

Each module must periodically refresh its ShutdownPermission signal within SUSD_t_Shutdown_Refresh seconds. If the timer expires, SUSD forces that module to EnableShutdown.

Force Shutdown Timer

Once all PermitExecution interfaces are deactivated, SUSD starts a global timer of SUSD_t_Force_Shutdown_Wait seconds. On expiry, SUSD requests BswM to transition to the shutdown target.

SPM Shutdown Sequencing

  1. When all modules except possibly SUM_SSC vote EnableShutdown, SUSD sets the Shutdown Target bit to OFF for SUM_SPM
  2. SUM_SPM performs its shutdown preconditions and responds with 0xFE (SPM_Shutdown_Ready)
  3. Only then does SUSD proceed with the final EcuM shutdown request

Dual-Timer Shutdown Permission System

SUSD uses two timers to manage the shutdown permission handshake:

TimerPurposeDefaultBehavior on Expiry
SUSD_ShutdownPermissionTimeoutMaximum time SUSD waits for all users to grant shutdown permission5000 msSUSD forces shutdown even if some users have not responded
SUSD_ShutdownGracePeriodAdditional time after permission granted for users to complete final NvM writes200 msSUSD proceeds to final shutdown phase
Timer Interaction: The grace period timer starts only after all registered users have granted shutdown permission (or the permission timeout expires). During the grace period, users can still perform NvM writes but cannot revoke their shutdown permission. This two-phase approach ensures data integrity while preventing indefinite shutdown delays.
Ordering Rules: Enable order: SUM_PNC → SUM_LNM → SUM_ERRH → SUM_SOH → remaining SUMs.
Disable order (reverse): SUM_SOH → SUM_ERRH → SUM_LNM → SUM_PNC.

Implementation Example — Sum_Susd_PermitExecution (from SUM_SUSD.c) 
/* Build and distribute PermitExecution status to all configured modules */
static FUNC(void, SUM_SUSD_CODE) Sum_Susd_DistributePermitExecution(void)
{
    SUSD_SWC_ExecutionStatusType execStatus = 0x00U;

    /* Bit 0: Wakeup Active */
    if (Sum_Susd_WakeupActive == (boolean)TRUE)
    {
        execStatus |= (SUSD_SWC_ExecutionStatusType)SUSD_PERMIT_BIT_WAKEUP;
    }
    /* Bit 2: HW Peripheral Init Complete */
    if (Sum_Susd_HwPeriphReady == (boolean)TRUE)
    {
        execStatus |= (SUSD_SWC_ExecutionStatusType)SUSD_PERMIT_BIT_HW_PERIPH;
    }
    /* Bit 3: VPM Operational */
    if (Sum_Susd_VpmOperational == (boolean)TRUE)
    {
        execStatus |= (SUSD_SWC_ExecutionStatusType)SUSD_PERMIT_BIT_VPM;
    }
    /* Bit 5: Battery Voltage OK */
    if (Sum_Susd_BatteryVoltageOk == (boolean)TRUE)
    {
        execStatus |= (SUSD_SWC_ExecutionStatusType)SUSD_PERMIT_BIT_BATTERY;
    }
    /* Bit 6: ECU Reset Request (inverted logic) */
    if (Sum_Susd_ResetRequested == (boolean)FALSE)
    {
        execStatus |= (SUSD_SWC_ExecutionStatusType)SUSD_PERMIT_BIT_NO_RESET;
    }

    /* Distribute in configured enable order */
    for (uint8 idx = 0U; idx < Sum_Susd_CfgPtr->NumPermitExecPorts; idx++)
    {
        Rte_Write_PermitExecution(Sum_Susd_CfgPtr->PermitExecOrder[idx], execStatus);
    }
}
Implementation Example — Sum_Susd_ShutdownPermission (from SUM_SUSD.c) 
/* Collect and evaluate ShutdownPermission votes from all modules */
static FUNC(boolean, SUM_SUSD_CODE) Sum_Susd_EvaluateShutdownPermission(void)
{
    boolean allReady = (boolean)TRUE;
    SUSD_UserRequestType vote;
    uint8 idx;

    for (idx = 0U; idx < Sum_Susd_CfgPtr->NumShutdownPorts; idx++)
    {
        Rte_Read_ShutdownPermission(idx, &vote);

        if (vote == SUSD_ENABLE_SHUTDOWN) /* 0xFF */
        {
            /* Module is ready for shutdown */
        }
        else if (vote == SUSD_SPM_SHUTDOWN_READY) /* 0xFE */
        {
            /* SPM-specific ready signal */
        }
        else if (vote <= SUSD_DISABLE_SHUTDOWN_MAX) /* 0x00-0x03 */
        {
            /* Check refresh timer for this module */
            if (Sum_Susd_RefreshTimerExpired(idx) == (boolean)TRUE)
            {
                /* Module not refreshing — force to EnableShutdown */
                Sum_Susd_ForceShutdownVote(idx);
            }
            else
            {
                allReady = (boolean)FALSE;
            }
        }
        else
        {
            /* Reserved values — treat as not ready */
            allReady = (boolean)FALSE;
        }
    }

    return allReady;
}

4.4 Vehicle Power Mode (Power Moding Slave)

SUSD determines the Vehicle Power Mode (VPM) — a unified representation of the vehicle's power state.

Power Mode Values

ValueModeMeaning
0x00OFFVehicle is off
0x01ACCESSORYAccessory mode (radio, etc.)
0x02RUNNormal run mode
0x03STARTEngine start request
0x04PROPULSIONVehicle in propulsion

Fallback Strategy

Safety & Security Variants
ConfigurationDescription
QM without cybersecurityBasic determination using availability/validity signals
QM with cybersecurityAdds cybersecurity risk signals (FxFA) to the decision
ASIL A without cybersecurityAdds safety fault signals (FsFA, FsI)
ASIL A with cybersecurityFull safety + security determination

Controlled by SUSD_VPM_ASIL_A_Supported and SUSD_VPM_Cybersecurity_Supported.

VPM Determination Logic

SUSD determines the Vehicle Power Mode (VPM) based on multiple input signals. The determination follows this priority-based truth table:

Ignition SignalPower Mode RequestBattery StatusResulting VPM
OFFOFFNormalVPM_OFF
OFFACCNormalVPM_ACCESSORY
ONRUNNormalVPM_RUN
ONCRANKNormalVPM_CRANK
AnyAnyLow VoltageVPM_LOW_VOLTAGE (overrides)
AnyAnyCriticalVPM_EMERGENCY_SHUTDOWN (overrides)
Priority Rule: Battery status has the highest priority. Low voltage or critical battery conditions override the ignition and power mode signals. This ensures the ECU can initiate emergency shutdown regardless of the requested power mode.
Scenario Walkthrough — VPM Determination with Primary/Backup Signal Arbitration
Scenario
The ECU is running normally when the primary power mode signal from SPM becomes invalid due to a cybersecurity fault. SUSD must fall through the priority chain to determine VPM, checking validity, availability, and security risk at each level.
Implementation Example — Sum_Susd_DetermineVPM (from SUM_SUSD.c) 
/* Determine Vehicle Power Mode using three-tier fallback strategy */
static FUNC(void, SUM_SUSD_CODE) Sum_Susd_DetermineVPM(void)
{
    uint8 spmAvailability;
    uint8 spmValue;
    uint8 sbpmAvailability;
    uint8 sbpmValue;
    boolean spmValid = (boolean)FALSE;

    /* STEP 1: Try Primary Power Mode (SPM) */
    Rte_Read_SPM_Availability(&spmAvailability);
    Rte_Read_SPM_Value(&spmValue);

    spmValid = (spmAvailability == SUSD_SIGNAL_AVAILABLE);

#if (SUSD_VPM_CYBERSECURITY_SUPPORTED == STD_ON)
    if (spmValid == (boolean)TRUE)
    {
        uint8 fxfaRisk;
        Rte_Read_SPM_CybersecRisk(&fxfaRisk);
        if (fxfaRisk == SUSD_CYBERSEC_RISK_ACTIVE)
        {
            spmValid = (boolean)FALSE;
        }
    }
#endif

    if (spmValid == (boolean)TRUE)
    {
        Sum_Susd_VehiclePowerMode = spmValue;
        Sum_Susd_VpmSource = SUSD_VPM_SOURCE_PRIMARY;
        return;
    }

    /* STEP 2: Try Backup Power Mode (SBPM) */
    Rte_Read_SBPM_Availability(&sbpmAvailability);
    Rte_Read_SBPM_Value(&sbpmValue);

    if (sbpmAvailability == SUSD_SIGNAL_AVAILABLE)
    {
        Sum_Susd_VehiclePowerMode = sbpmValue;
        Sum_Susd_VpmSource = SUSD_VPM_SOURCE_BACKUP;
        return;
    }

    /* STEP 3: Fail-Soft — use Run/Crank hardware input */
    if (Sum_Susd_RunCrankInputValid == (boolean)TRUE)
    {
        Sum_Susd_VehiclePowerMode = (Sum_Susd_RunCrankHigh == (boolean)TRUE)
            ? SUSD_VPM_RUN : SUSD_VPM_OFF;
        Sum_Susd_VpmSource = SUSD_VPM_SOURCE_FAILSOFT;
    }
}

4.5 Battery Voltage Monitor

SUSD monitors the vehicle battery voltage and provides standardized voltage range notifications to SW-Cs.

Voltage Classification with Hysteresis

StateCondition
NormalBetween Min + UnderVoltage_hysteresis and Max - OverVoltage_hysteresis
UndervoltageBelow Min
OvervoltageAbove Max

NvM Write Protection

Write allowed (0): Voltage ≥ SUSD_C_DisableNVMWrite_Voltage AND BattVltgSnsrStsEnum == 2 (Available)
Write disabled (1): Either condition not met — all SW-Cs must inhibit direct NvM writes.

Default vs Custom Voltage Ranges

  • Default (always present): 9V–16V, port: PP_SUSD_DefaultBatteryVoltage_MintoMax_9Vto16V
  • Custom ranges: Configurable via SUSD_C_BatteryVoltageRange containers
  • SW-C assignment: Each SW-C references a voltage range; if none specified, uses 9V–16V default
Scenario Walkthrough — Undervoltage Detection and NvM Write Protection
Scenario
During engine cranking, battery voltage drops sharply. SUSD must detect the undervoltage condition, protect NvM from corrupted writes, and properly classify voltage ranges for each SW-C with different thresholds.
Implementation Example — Sum_Susd_BatteryVoltageMonitor (from SUM_SUSD.c) 
/* Evaluate battery voltage and update classification with hysteresis */
static FUNC(void, SUM_SUSD_CODE) Sum_Susd_BatteryVoltageMonitor(void)
{
    float32 currentVoltage;
    uint8 sensorStatus;
    uint8 rangeIdx;

    Rte_Read_BatteryVoltage(&currentVoltage);
    Rte_Read_BattVltgSnsrStsEnum(&sensorStatus);

    /* NvM Write Protection evaluation */
    if ((currentVoltage >= Sum_Susd_CfgPtr->DisableNvmWriteVoltage) &&
        (sensorStatus == SUSD_BATT_SENSOR_AVAILABLE))
    {
        Sum_Susd_NvmWriteAllowed = SUSD_NVM_WRITE_ALLOWED; /* 0 */
    }
    else
    {
        Sum_Susd_NvmWriteAllowed = SUSD_NVM_WRITE_DISABLED; /* 1 */
    }
    Rte_Write_NvmWriteProtection(Sum_Susd_NvmWriteAllowed);

    /* Evaluate each configured voltage range with hysteresis */
    for (rangeIdx = 0U; rangeIdx < Sum_Susd_CfgPtr->NumVoltageRanges; rangeIdx++)
    {
        const Sum_Susd_VoltageRangeCfgType* rangeCfg =
            &Sum_Susd_CfgPtr->VoltageRanges[rangeIdx];

        if (currentVoltage < rangeCfg->MinVoltage)
        {
            Sum_Susd_VoltageState[rangeIdx] = SUSD_VOLTAGE_UNDER;
        }
        else if (currentVoltage > rangeCfg->MaxVoltage)
        {
            Sum_Susd_VoltageState[rangeIdx] = SUSD_VOLTAGE_OVER;
        }
        else if ((currentVoltage >= (rangeCfg->MinVoltage + rangeCfg->UnderHysteresis)) &&
                 (currentVoltage <= (rangeCfg->MaxVoltage - rangeCfg->OverHysteresis)))
        {
            Sum_Susd_VoltageState[rangeIdx] = SUSD_VOLTAGE_NORMAL;
        }
        /* else: remain in current state (hysteresis band) */

        Rte_Write_BatteryVoltageRange(rangeIdx, Sum_Susd_VoltageState[rangeIdx]);
    }
}

4.6 Run/Crank Plausibility

SUSD monitors the physical Run/Crank hardware signal as the last-resort backup for Vehicle Power Mode determination.

Input Types

TypeConfig ValueDescription
Discrete0x01Digital input — High/Low
Analog0x00Voltage compared against thresholds
Stuck High / Stuck Low Diagnostics

Stuck High Diagnostic — detects when input is stuck HIGH when it should be LOW:

  • Enable: Battery ≥ 9.5V, Run/Crank Command is LOW, SUSD_C_RunCrankInputStuckHi_Enable = TRUE
  • Failure: Local input is HIGH
  • Maturation: Fail count reaches FailCount threshold within SampleCount samples → FAILED

Stuck Low Diagnostic — mirrors the above but detects stuck LOW.

If either reports FAILED, Run/Crank Input is marked Invalid and cannot be used for VPM fail-soft.

Scenario Walkthrough — Detecting Stuck Run/Crank Signal and Diagnostic Reporting
Scenario
The Run/Crank hardware input becomes stuck HIGH due to a wiring short circuit. SUSD must detect this condition through its plausibility check, report the diagnostic fault, and invalidate the signal so it cannot corrupt VPM fail-soft determination.
Implementation Example — Sum_Susd_RunCrankPlausibility (from SUM_SUSD.c) 
/* Check Run/Crank hardware signal plausibility and update diagnostics */
static FUNC(void, SUM_SUSD_CODE) Sum_Susd_RunCrankPlausibility(void)
{
    boolean localInputHigh;
    boolean runCrankCommandHigh;
    float32 batteryVoltage;

    Rte_Read_RunCrankLocalInput(&localInputHigh);
    Rte_Read_RunCrankCommand(&runCrankCommandHigh);
    Rte_Read_BatteryVoltage(&batteryVoltage);

    /* Stuck High Diagnostic */
    if ((Sum_Susd_CfgPtr->RunCrankStuckHiEnable == (boolean)TRUE) &&
        (batteryVoltage >= SUSD_BATT_DIAG_THRESHOLD) &&
        (runCrankCommandHigh == (boolean)FALSE))
    {
        /* Enable conditions met: evaluate failure */
        if (localInputHigh == (boolean)TRUE)
        {
            Sum_Susd_StuckHiFailCount++;
        }
        Sum_Susd_StuckHiSampleCount++;

        if (Sum_Susd_StuckHiSampleCount >= Sum_Susd_CfgPtr->StuckHiSampleThresh)
        {
            if (Sum_Susd_StuckHiFailCount >= Sum_Susd_CfgPtr->StuckHiFailThresh)
            {
                Sum_Susd_RunCrankInputValid = (boolean)FALSE;
                Dem_SetEventStatus(SUSD_DEM_RUNCRANK_STUCK_HI, DEM_EVENT_STATUS_FAILED);
            }
            else
            {
                Dem_SetEventStatus(SUSD_DEM_RUNCRANK_STUCK_HI, DEM_EVENT_STATUS_PASSED);
            }
            Sum_Susd_StuckHiFailCount = 0U;
            Sum_Susd_StuckHiSampleCount = 0U;
        }
    }

    /* Stuck Low Diagnostic - symmetric logic with inverted conditions */
    if ((Sum_Susd_CfgPtr->RunCrankStuckLoEnable == (boolean)TRUE) &&
        (batteryVoltage >= SUSD_BATT_DIAG_THRESHOLD) &&
        (runCrankCommandHigh == (boolean)TRUE))
    {
        if (localInputHigh == (boolean)FALSE)
        {
            Sum_Susd_StuckLoFailCount++;
        }
        Sum_Susd_StuckLoSampleCount++;

        if (Sum_Susd_StuckLoSampleCount >= Sum_Susd_CfgPtr->StuckLoSampleThresh)
        {
            if (Sum_Susd_StuckLoFailCount >= Sum_Susd_CfgPtr->StuckLoFailThresh)
            {
                Sum_Susd_RunCrankInputValid = (boolean)FALSE;
                Dem_SetEventStatus(SUSD_DEM_RUNCRANK_STUCK_LO, DEM_EVENT_STATUS_FAILED);
            }
            else
            {
                Dem_SetEventStatus(SUSD_DEM_RUNCRANK_STUCK_LO, DEM_EVENT_STATUS_PASSED);
            }
            Sum_Susd_StuckLoFailCount = 0U;
            Sum_Susd_StuckLoSampleCount = 0U;
        }
    }
}

4.9 Activity Records (DID E0D7)

Activity Records track how the ECU spends its time across different wakeup reasons. This is the most complex feature in SUSD.

State Machine

Activity Record State Machine: Each activity record tracks its state independently:
  • INACTIVE — Activity not started or completed. No resource consumption.
  • REQUESTED — Activity start has been requested but not yet acknowledged by the owning module.
  • ACTIVE — Activity is running. SUSD will not proceed to shutdown while any activity is in ACTIVE state.
  • COMPLETING — Activity end has been requested. Module is performing cleanup (NvM writes, message completion).
SUSD monitors all activity records and only initiates shutdown when all records are either INACTIVE or have exceeded their individual timeout.

How SUSD ParamDef
How SUSD ParamDef works with the module
SUSD is the first SUM module to execute. It reads the wakeup source from EcuM, matches it against SUSDWakeUpRelation to determine which modules should start, then distributes PermitExecution bitmasks through SUSD_C_SUMsInfo (one instance per SUM module: SPM, LNM, SSFM, PNC, DIAG, TCS, etc.).

SUSDGeneral handles Vehicle Power Mode (VPM) determination from Primary/Backup Power Mode COM signals, with configurable security level and initial power mode values. Multiple periodicities control how often SUSD polls battery voltage, wakeup sources, RunCrank status, and VPM changes.

SUSDConfigSet configures RunCrank input diagnostics (stuck high/low with fault maturation counters), battery voltage ranges with hysteresis, and Activity Records (DID E0D7) for tracking wakeup history in NvM.
Key relationship: SUSD ↔ PermitExecutionMask
Every SUM module has a PermitExecutionMask parameter (INTEGER, 0..255, default 254). SUSD sets a PermitExecution value based on the wakeup source, and each module checks: if (PermitExecution & PermitExecutionMask) != 0 then execute. This allows fine-grained control over which modules run for each wakeup scenario.

Common Patterns Across Modules

PermitExecutionMask
Found in: TCS, DIAG, PNC, SrvcMgr, SPM, LNM, SOH, SSFM. Always INTEGER 0..255 with default 254. Used by SUSD to control module startup based on wakeup source.
GenerateInitRunnable + InitFuncPeriodicity
Found in: TCS, DIAG, SrvcMgr, and others. A BOOLEAN flag that enables generation of a one-shot init runnable, paired with a FLOAT periodicity (ms). When FALSE, init is called by BswM action list instead.
ServiceBased References
Found in: TCS, DIAG, SrvcMgr. Paired FOREIGN-REFs for DataTypeMappingSet + IMPLEMENTATION-DATA-TYPE-ELEMENT. These enable SOME/IP service-based communication as an alternative to signal-based COM. Presence activates service-based mode.
CHOICE-REFERENCE-DEF
Found in: TCS, DIAG, SrvcMgr, PNC, SSFM. Used when a reference can point to multiple target types (e.g., ComSignal OR ComGroupSignal, SdClientService OR SdServerService). The integrator selects which target type applies for their project.
Reliability Monitor / Detector Pattern (SOH)
SOH uses a highly consistent detector pattern repeated ~20 times: each detector has a Thresh_Init (INT, fault counter), TW_Thresh_Init (INT, time window in seconds), an NvM block reference for persistent storage, and a DcmDspData DID reference for diagnostic readout. Detectors are grouped under 5 Reliability Monitor categories (Reset, MemoryStatus, Communication, WatchdogManager, Platform).
Error Filter Pattern (SSFM)
SSFM uses reusable GeneralEventsFilter containers with FilterType (NONE/BLOCK/X_OF_Y), threshold X, and window Y parameters. Error handlers across all error categories reference these shared filters, allowing consistent error debouncing configuration.
NvM Block References
Found in: SOH (extensively), SSFM, SUSD, TCS. References to NvMBlockDescriptor containers for persistent data storage across power cycles. Used for DID data, counters, and configuration values that must survive reset.
