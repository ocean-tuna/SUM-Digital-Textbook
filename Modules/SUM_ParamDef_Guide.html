RTA-SUM Parameter Definition Guide

Understanding ECUC Parameter Definitions across all SUM modules

What is a ParamDef?

ECUC Parameter Definition (EcucParamDef) is the AUTOSAR mechanism for defining configurable parameters of a software module. Each SUM module ships an .arxml file (the ParamDef) that declares which parameters exist, their types, valid ranges, defaults, and multiplicities. The RTA toolchain (ISOLAR, RTA-CFG) reads these definitions and presents them as configuration forms to the integrator.

Key Concepts

ConceptDescription
ContainerA logical grouping of parameters. Containers can be nested (sub-containers). Each container has a multiplicity that says how many instances are allowed (e.g., 1..1 = exactly one, 1..* = one or more).
ParameterA single configuration value inside a container. Types include INTEGER, BOOLEAN, FLOAT, ENUMERATION, STRING, and FUNCTION-NAME.
ReferenceA pointer to another AUTOSAR container (e.g., referencing a DCM DID, NvM block, or Com signal). Types: ECUC-REFERENCE-DEF, ECUC-CHOICE-REFERENCE-DEF (multiple targets), ECUC-FOREIGN-REFERENCE-DEF (cross-module).
MultiplicityLOWER-MULTIPLICITY / UPPER-MULTIPLICITY define how many instances are required/allowed. 0..1 = optional, 1..1 = mandatory, 1..* = at least one.
Config VariantWhen the parameter is resolved: VARIANT-PRE-COMPILE (at compile time) or VARIANT-POST-BUILD (loadable at runtime).
INTEGER Numeric value
BOOLEAN True/False
FLOAT Decimal value
ENUM Fixed choices
STRING Text value
REFERENCE Pointer to another element

How TCS ParamDef works with the module
The timing parameters control how often TCS polls the master clock and processes time management. The PermitExecutionMask defines which SUSD wakeup bits must be set before this module starts.

How SPM ParamDef
How SPM ParamDef works with the module
SPM is the most configuration-heavy SUM module (45 params, 30 refs, 16 containers).

SpmConfigSet contains the three core subsystems:
1. Power Profiles (SpmPowPrf) - define services/features needing power, their activation priorities (NOTAPP through EMERGENCY), and COM IPdu group references for enabling/disabling network Tx/Rx per profile. Profiles can have software dependencies (SpmProfileSwDep).
2. Power Graph (SpmPgttEntries) - the network topology: target devices (with IPv4 addresses, DTC reporting), waking device config (EDGE vs INTERMEDIATE node), HW variants (SpmVariantCfg with per-VLAN heartbeat IPs), and wake-up sequences.
3. LowVoltagePowerInfo - optional LV Energy Optimizer integration.

SpmGeneral provides timing (SM/PM periodicities), queue sizes for Rx message buffering, calibration timers (HeartBeat shutdown delay, SM stay-awake time), and sub-containers for diagnostics (DID E0DD/E0DE/E0DF), CAN wake-up frame references, and VLAN communication interfaces (heartbeat, wakeup frames, SW manager info - each with Tx/Rx FOREIGN-REFs to IMPLEMENTATION-DATA-TYPE and SENDER-RECEIVER-INTERFACE).

How LNM ParamDef
How LNM ParamDef works with the module
LNM (LIN Network Manager) manages LIN bus networks with a layered configuration:

1. Inputs → Conditions → Rules: Schedule signals (from SWC, COM, or VPM) serve as inputs. Conditions compare inputs against values using operators (==, !=, <, >). Rules combine conditions with AND/OR logic.

2. Networks → Schedule States → Transitions: Each LIN network has its own schedule state machine. Transitions between states are triggered by Rules. States reference LinSM schedules.

3. Responders: Each network has LIN responder devices with MSCL (Master Schedule Control List) bit assignments, DTC configurations for loss-of-communication, and Internal Electronic Failure monitoring.

The wakeup delays (Commander/Responder) control timing when transitioning from sleep. The MSCL strategy (Calibration vs Evaluation) determines how responder presence is managed.

How SOH ParamDef
How SOH ParamDef works with the module
SOH's paramdef is built around a Reliability Monitor architecture with 5 monitor categories:
  • Reset Monitor: Tracks immediate, delayed, and diagnostic resets. Each detector counts occurrences within a time window (TW) and reports via DID F08F.
  • Memory Status Monitor: Tracks NvM errors (Status/Action/Privilege classes) and OS errors (6 OS error categories). Reports via DID F090.
  • Communication Monitor: Tracks diagnostic session activity, security access failures, MAC failures, replay attacks, and SecP errors. Reports via DID F092.
  • Watchdog Monitor: Tracks WdgM local supervision failures and DEM supervision errors, including ERRH-reported supervision status. Reports via DID F093.
  • Platform Monitor: Tracks shutdown delay patterns. Reports via DID F091.
The 21 SupportEnabled flags in SOHGeneral allow project-specific detector selection. Each detector's Thresh_Init and TW_Thresh_Init are calibratable, and NvM blocks ensure data persists across power cycles. This modular architecture lets integrators enable only the health monitoring relevant to their ECU.

How SSFM ParamDef
How SSFM ParamDef works with the module
SSFM's ParamDef mirrors its complex dual sub-module architecture:
  • SSM side: Sum_Ssfm_SerialData instances define every CAN/Ethernet signal the module monitors. Each links to an RteSerialData callback, a Channel, optional SecOC/PN/SD references, and FcI/FoI/FpI/FsI debouncers. GroupInfo organizes these by ECU, LIN responder, or target device with per-group DEM event mappings and debounce timers.
  • ERRH side: ErrorsHandlers categorizes errors by source (BSW, LNM, SUSD, SSC, SrvcMgr, Safety/Security) with individual DTC process flags. ErrorFilter provides reusable filtering methods (X_OF_Y windowing or BLOCK) that any error handler can reference.
  • DID/NvM: Errh_DID configures diagnostic DIDs (E0B8–E0BB, F094) and their NvM block storage for persistent error data across power cycles.
The two separate PermitExecutionMasks (SSM vs ERRH) allow SUSD to independently control startup of each sub-module based on wakeup source.

How SUSD ParamDef
How SUSD ParamDef works with the module
SUSD is the first SUM module to execute. It reads the wakeup source from EcuM, matches it against SUSDWakeUpRelation to determine which modules should start, then distributes PermitExecution bitmasks through SUSD_C_SUMsInfo (one instance per SUM module: SPM, LNM, SSFM, PNC, DIAG, TCS, etc.).

SUSDGeneral handles Vehicle Power Mode (VPM) determination from Primary/Backup Power Mode COM signals, with configurable security level and initial power mode values. Multiple periodicities control how often SUSD polls battery voltage, wakeup sources, RunCrank status, and VPM changes.

SUSDConfigSet configures RunCrank input diagnostics (stuck high/low with fault maturation counters), battery voltage ranges with hysteresis, and Activity Records (DID E0D7) for tracking wakeup history in NvM.
Key relationship: SUSD ↔ PermitExecutionMask
Every SUM module has a PermitExecutionMask parameter (INTEGER, 0..255, default 254). SUSD sets a PermitExecution value based on the wakeup source, and each module checks: if (PermitExecution & PermitExecutionMask) != 0 then execute. This allows fine-grained control over which modules run for each wakeup scenario.

Common Patterns Across Modules

PermitExecutionMask
Found in: TCS, DIAG, PNC, SrvcMgr, SPM, LNM, SOH, SSFM. Always INTEGER 0..255 with default 254. Used by SUSD to control module startup based on wakeup source.
GenerateInitRunnable + InitFuncPeriodicity
Found in: TCS, DIAG, SrvcMgr, and others. A BOOLEAN flag that enables generation of a one-shot init runnable, paired with a FLOAT periodicity (ms). When FALSE, init is called by BswM action list instead.
ServiceBased References
Found in: TCS, DIAG, SrvcMgr. Paired FOREIGN-REFs for DataTypeMappingSet + IMPLEMENTATION-DATA-TYPE-ELEMENT. These enable SOME/IP service-based communication as an alternative to signal-based COM. Presence activates service-based mode.
CHOICE-REFERENCE-DEF
Found in: TCS, DIAG, SrvcMgr, PNC, SSFM. Used when a reference can point to multiple target types (e.g., ComSignal OR ComGroupSignal, SdClientService OR SdServerService). The integrator selects which target type applies for their project.
Reliability Monitor / Detector Pattern (SOH)
SOH uses a highly consistent detector pattern repeated ~20 times: each detector has a Thresh_Init (INT, fault counter), TW_Thresh_Init (INT, time window in seconds), an NvM block reference for persistent storage, and a DcmDspData DID reference for diagnostic readout. Detectors are grouped under 5 Reliability Monitor categories (Reset, MemoryStatus, Communication, WatchdogManager, Platform).
Error Filter Pattern (SSFM)
SSFM uses reusable GeneralEventsFilter containers with FilterType (NONE/BLOCK/X_OF_Y), threshold X, and window Y parameters. Error handlers across all error categories reference these shared filters, allowing consistent error debouncing configuration.
NvM Block References
Found in: SOH (extensively), SSFM, SUSD, TCS. References to NvMBlockDescriptor containers for persistent data storage across power cycles. Used for DID data, counters, and configuration values that must survive reset.
