1. Overview: What is SUM_SOH?

Minimum RTE Version: SOH requires RTE version 7.3.0 or later. Earlier versions do not support the enhanced port interface patterns used by SOH for NvM service port handling. Verify your RTE version before integration.

What

SUM_SOH (State Of Health Manager) is a software module that monitors, filters, counts, and reports the operational health of an automotive ECU. It tracks errors, faults, resets, communication anomalies, and OS protection violations, then stores these metrics in NvM so they survive power cycles and can be read via diagnostic services.

Why

  • How many times has the ECU unexpectedly reset?
  • Are there recurring NvM failures?
  • Is the OS experiencing protection violations?
  • Are there communication security breaches (MAC failures, unauthorized diagnostic sessions)?
  • Is the ECU shutting down properly within its expected timeframe?

SUM_SOH provides a standardized health history of the ECU that service technicians can read through diagnostic tools (via UDS DIDs 0xF08F–0xF094).

Real-World Scenarios

The following scenarios illustrate how SUM_SOH operates in real vehicle situations. Each demonstrates a key capability of the module:

1. Unexpected Reset Tracking

The ECU experiences a watchdog reset while driving. On the next startup, SUM_SOH receives a reset notification from SUM_SUSD, classifies it as an Immediate Reset, increments the SOH_ImmeReset detection counter in NonClearedRAM, and applies the Time Window filter. If the filtered threshold is reached, the DID 0xF08F counter is incremented and persisted to NvM. A service technician can later read DID 0xF08F to see the accumulated reset history and determine if the pattern indicates a systematic hardware fault.

2. NvM Memory Degradation Detection

During normal operation, the NvM stack reports a NVM_REQ_INTEGRITY_FAILED error via SUM_ERRH. SUM_SOH receives this as a BSW event, maps it to the SOH_StatNVM detector, and increments the detection counter. The Time Window filter tracks how many NvM status failures occur within the configured time window. If the threshold is exceeded, the DID 0xF090 counter increments and the data is written to NvM, providing a persistent record of memory subsystem degradation before a complete failure occurs.

3. Stack Overflow Prevention

The OS detects an E_OS_STACKFAULT protection violation in one of the application tasks. The OS ProtectionHook fires and calls SOH_OS_Protection_ErrorHook_CallBack. SUM_SOH classifies the error, increments the SOH_StackOS detector counter in NonClearedRAM (surviving the subsequent reset), and applies the Time Window filter. The accumulated stack fault history in DID 0xF090 helps engineers identify which tasks are at risk of stack overflow during field analysis.

4. Shutdown Coordination

A vehicle shutdown is requested while SUM_SOH has pending NvM writes for recently updated detector counters. SUM_SOH detects the shutdown condition via PermitExecution bit changes and enters the SHUTDOWN state. Instead of immediately signaling readiness, it writes a cycling permission value (0, 1, 2, 3...) to SUSD while NvM writes complete. Once all NvM blocks are safely written, SUM_SOH sends 0xFF (ready) to SUSD, allowing the final power-down to proceed without data loss.

5. Filters: How Events Are Counted

5.1 Threshold Filter

Concept When the detection counter reaches a configured threshold, the DID counter increments by 1. A threshold of 5 means “every 5th occurrence counts as one DID event.”
Figure 6 — Threshold Filter logic

5.2 Time Window Filter

Concept The detection counter must reach the threshold within a configurable time window. If the time window expires first, both counter and window reset.
Why? Distinguishes occasional errors (normal) from error bursts (problematic). 3 NvM errors in a year = OK. 3 NvM errors in 10 seconds = problem.
Figure 7 — Time Window Filter logic (event path + time manager path)

Core Filter Code

boolean SOH_Filter(SOH_DetectorType const* item)
{
    boolean ret = TRUE;

    if (*(item->SOH_TresholdItem.SOH_Cntr) >= item->SOH_TresholdItem.SOH_CntrThreshold())
    {
        *(item->SOH_TresholdItem.SOH_Cntr) = 0x0000;
        if (item->SOH_Filter == SOH_TWFiltering) {
            *(item->SOH_TresholdItem.SOH_TW) = 0x00000000;
            *(item->SOH_TresholdItem.SOH_PrevCounterValue) = 0x00u;
        }
        if (*(item->SOH_TresholdItem.SOH_DIDCntr) < 0xFFFE)
            (*(item->SOH_TresholdItem.SOH_DIDCntr))++;
    }
    else { ret = FALSE; }
    return ret;
}

/* Handle reset occurrence notification from SUSD */
static FUNC(void, SUM_SOH_CODE) Sum_Soh_ResetEventHandler(void)
{
    uint8 resetType;

    /* Read reset type from SUSD */
    (void)Rte_Read_RP_SUSD_SOH_ResetOccurred(&resetType);

    switch (resetType)
    {
        case SOH_IMMEDIATE_RESET:
            SOH_Event_Detector(
                &SOH_DetectorConfig[SOH_ImmeReset]);
            break;

        case SOH_DELAYED_RESET:
            SOH_Event_Detector(
                &SOH_DetectorConfig[SOH_DelayedReset]);
            break;

        default:
            /* No action for expected resets */
            break;
    }
}

Implementation Example — Sum_Soh_NvmErrorClassifier (from SUM_SOH.c) 
/* Classify NvM BSW errors and route to appropriate detector */
static FUNC(void, SUM_SOH_CODE) Sum_Soh_NvmErrorClassifier(
    uint32 bswEventMask)
{
    /* Status errors: HARDWARE, QUEUE_OVERFLOW, INTEGRITY_FAILED */
    if ((bswEventMask & SOH_NVM_STATUS_MASK) != 0u)
    {
        SOH_Event_Detector(
            &SOH_DetectorConfig[SOH_StatNVM]);
    }

    /* Action errors: REQ_FAILED, WRONG_BLOCK_ID, VERIFY_FAILED */
    if ((bswEventMask & SOH_NVM_ACTION_MASK) != 0u)
    {
        SOH_Event_Detector(
            &SOH_DetectorConfig[SOH_ActNVM]);
    }

    /* Privilege errors: WRITE_PROTECTED */
    if ((bswEventMask & SOH_NVM_PRIVILEGE_MASK) != 0u)
    {
        SOH_Event_Detector(
            &SOH_DetectorConfig[SOH_PrivNVM]);
    }
}

Scenario

Implementation Example — Sum_Soh_CheckTransitionToNormal (from SUM_SOH.c) 
/* Check if conditions are met to transition from INIT to NORMAL */
static FUNC(boolean, SUM_SOH_CODE) Sum_Soh_CheckTransitionToNormal(void)
{
    boolean ready = FALSE;
    uint8 permitExec;

    /* Read PermitExecution from SUSD */
    (void)Rte_Read_RP_SUSD_SOH_PermitExecution(&permitExec);

    /* Apply mask: bits set in mask are "don't care" */
    if ((permitExec | SOH_PermitExecution_Mask) == 0xFFu)
    {
        /* All required bits are set → transition allowed */
        ready = TRUE;

        /* Signal immediate shutdown readiness */
        (void)Rte_Write_PP_SOH_SUSD_ShutdownPermission(0xFFu);
    }

    return ready;
}

11. NvM Integration: Persisting Data

NvM ReadAll Behavior: SOH processes NvM_ReadAll results per storage type. Each NvM block used by SOH is checked individually:
  • If the block read succeeds — SOH uses the stored values
  • If the block is invalidated or has a CRC error — SOH uses default (ROM) values and marks the block for re-write
  • If the block read is still pending at SOH init — SOH waits up to a configured timeout before falling back to defaults
This per-block handling ensures SOH can start even if some NvM blocks are corrupted, while preserving valid data from other blocks.

Write Conditions

All three conditions must be met for an NvM write:
  1. The counter value has actually changed
  2. No other NvM write for this detector is currently pending
  3. The battery voltage is in operating range

Scenario Walkthrough — NvM Write Decision Under Battery Voltage Constraints
Scenario
A detector counter has been incremented and the DID counter has changed. SUM_SOH needs to persist the new value to NvM, but the battery voltage drops below the operating threshold during the write attempt. SOH must defer the write to protect flash memory integrity.
Implementation Example — Sum_Soh_CheckConditionAndWrite (from SUM_SOH_Utilities.c) 
/* Evaluate all conditions before writing detector data to NvM */
static FUNC(void, SUM_SOH_CODE) SOH_CheckConditionAndWrite(
    const SOH_DetectorType* item)
{
    boolean didChanged;
    boolean cntrChanged;
    uint8   disableNvmWrite;

    /* Condition 1: DID counter value changed? */
    didChanged = (*(item->DID_Counter) != item->DID_Counter_Previous);

    /* Condition 2: Detection counter changed? (for persistent types) */
    cntrChanged = (*(item->SOH_Cntr) != item->SOH_Cntr_Previous);

    if ((didChanged == TRUE) || (cntrChanged == TRUE))
    {
        /* Condition 3: No pending NvM write */
        if (*(item->WritePending) == FALSE)
        {
            /* Condition 4: Battery voltage OK */
            (void)Rte_Read_RP_SUSD_SOH_DisableNVMWrite(
                &disableNvmWrite);

            if (disableNvmWrite == FALSE)
            {
                SOH_Write(item);
                *(item->WritePending) = TRUE;
                item->DID_Counter_Previous = *(item->DID_Counter);
                item->SOH_Cntr_Previous = *(item->SOH_Cntr);
            }
        }
    }
}

Implementation Example — Sum_Soh_MonitorShutDownTimer (from SUM_SOH_Utilities.c) 
/* Monitor shutdown timer and detect excessive shutdown delay */
static FUNC(void, SUM_SOH_CODE) SOH_MonitorShutDownTimer(void)
{
    if (ShutdownTimerFlag == TRUE)
    {
        /* Increment timer (called every 1 second) */
        SUM_SOH_ShutDown_Timer++;

        if (SUM_SOH_ShutDown_Timer >=
            SOH_ShutdownDelayThreshold)
        {
            /* Shutdown took too long — log the event */
            SOH_Event_Detector(
                &SOH_DetectorConfig[SOH_ShutdownDelay]);

            /* Reset timer and flag to prevent re-triggering */
            SUM_SOH_ShutDown_Timer = 0u;
            ShutdownTimerFlag = FALSE;
        }
    }
}

How SOH ParamDef works with the module
SOH's paramdef is built around a Reliability Monitor architecture with 5 monitor categories:
  • Reset Monitor: Tracks immediate, delayed, and diagnostic resets. Each detector counts occurrences within a time window (TW) and reports via DID F08F.
  • Memory Status Monitor: Tracks NvM errors (Status/Action/Privilege classes) and OS errors (6 OS error categories). Reports via DID F090.
  • Communication Monitor: Tracks diagnostic session activity, security access failures, MAC failures, replay attacks, and SecP errors. Reports via DID F092.
  • Watchdog Monitor: Tracks WdgM local supervision failures and DEM supervision errors, including ERRH-reported supervision status. Reports via DID F093.
  • Platform Monitor: Tracks shutdown delay patterns. Reports via DID F091.
The 21 SupportEnabled flags in SOHGeneral allow project-specific detector selection. Each detector's Thresh_Init and TW_Thresh_Init are calibratable, and NvM blocks ensure data persists across power cycles. This modular architecture lets integrators enable only the health monitoring relevant to their ECU.

How SSFM ParamDef
How SSFM ParamDef works with the module
SSFM's ParamDef mirrors its complex dual sub-module architecture:
  • SSM side: Sum_Ssfm_SerialData instances define every CAN/Ethernet signal the module monitors. Each links to an RteSerialData callback, a Channel, optional SecOC/PN/SD references, and FcI/FoI/FpI/FsI debouncers. GroupInfo organizes these by ECU, LIN responder, or target device with per-group DEM event mappings and debounce timers.
  • ERRH side: ErrorsHandlers categorizes errors by source (BSW, LNM, SUSD, SSC, SrvcMgr, Safety/Security) with individual DTC process flags. ErrorFilter provides reusable filtering methods (X_OF_Y windowing or BLOCK) that any error handler can reference.
  • DID/NvM: Errh_DID configures diagnostic DIDs (E0B8–E0BB, F094) and their NvM block storage for persistent error data across power cycles.
The two separate PermitExecutionMasks (SSM vs ERRH) allow SUSD to independently control startup of each sub-module based on wakeup source.

How SUSD ParamDef
How SUSD ParamDef works with the module
SUSD is the first SUM module to execute. It reads the wakeup source from EcuM, matches it against SUSDWakeUpRelation to determine which modules should start, then distributes PermitExecution bitmasks through SUSD_C_SUMsInfo (one instance per SUM module: SPM, LNM, SSFM, PNC, DIAG, TCS, etc.).

SUSDGeneral handles Vehicle Power Mode (VPM) determination from Primary/Backup Power Mode COM signals, with configurable security level and initial power mode values. Multiple periodicities control how often SUSD polls battery voltage, wakeup sources, RunCrank status, and VPM changes.

SUSDConfigSet configures RunCrank input diagnostics (stuck high/low with fault maturation counters), battery voltage ranges with hysteresis, and Activity Records (DID E0D7) for tracking wakeup history in NvM.
Key relationship: SUSD ↔ PermitExecutionMask
Every SUM module has a PermitExecutionMask parameter (INTEGER, 0..255, default 254). SUSD sets a PermitExecution value based on the wakeup source, and each module checks: if (PermitExecution & PermitExecutionMask) != 0 then execute. This allows fine-grained control over which modules run for each wakeup scenario.

Common Patterns Across Modules

PermitExecutionMask
Found in: TCS, DIAG, PNC, SrvcMgr, SPM, LNM, SOH, SSFM. Always INTEGER 0..255 with default 254. Used by SUSD to control module startup based on wakeup source.
GenerateInitRunnable + InitFuncPeriodicity
Found in: TCS, DIAG, SrvcMgr, and others. A BOOLEAN flag that enables generation of a one-shot init runnable, paired with a FLOAT periodicity (ms). When FALSE, init is called by BswM action list instead.
ServiceBased References
Found in: TCS, DIAG, SrvcMgr. Paired FOREIGN-REFs for DataTypeMappingSet + IMPLEMENTATION-DATA-TYPE-ELEMENT. These enable SOME/IP service-based communication as an alternative to signal-based COM. Presence activates service-based mode.
CHOICE-REFERENCE-DEF
Found in: TCS, DIAG, SrvcMgr, PNC, SSFM. Used when a reference can point to multiple target types (e.g., ComSignal OR ComGroupSignal, SdClientService OR SdServerService). The integrator selects which target type applies for their project.
Reliability Monitor / Detector Pattern (SOH)
SOH uses a highly consistent detector pattern repeated ~20 times: each detector has a Thresh_Init (INT, fault counter), TW_Thresh_Init (INT, time window in seconds), an NvM block reference for persistent storage, and a DcmDspData DID reference for diagnostic readout. Detectors are grouped under 5 Reliability Monitor categories (Reset, MemoryStatus, Communication, WatchdogManager, Platform).
Error Filter Pattern (SSFM)
SSFM uses reusable GeneralEventsFilter containers with FilterType (NONE/BLOCK/X_OF_Y), threshold X, and window Y parameters. Error handlers across all error categories reference these shared filters, allowing consistent error debouncing configuration.
NvM Block References
Found in: SOH (extensively), SSFM, SUSD, TCS. References to NvMBlockDescriptor containers for persistent data storage across power cycles. Used for DID data, counters, and configuration values that must survive reset.
