RTA-SUM PNC — Partial Network Controller

Complete training guide covering what PNC does, why it exists, and how it works — from high-level architecture down to individual functions and configuration parameters.

Audience: Developers, Integrators, Reviewers Module: sum_pnc Platform: AUTOSAR / GM SUM

1. What is PNC?

PNC (Partial Network Controller) is a software component (SW-C) in the RTA-SUM product family for AUTOSAR-based automotive ECUs. It manages Partial Network (PN) communication control — deciding when each partial network should be active or inactive, and coordinating the enabling/disabling of the corresponding PDU groups (message groups) on the communication bus.

In plain terms: modern vehicles have dozens of ECUs sharing CAN/Ethernet buses. Not every ECU needs to be fully awake all the time. Partial Networks allow groups of ECUs to selectively wake up and communicate based on specific triggers (a sensor reading, a diagnostic request, an NM message from another ECU). PNC is the brain that orchestrates this per-PN lifecycle.

2. Why Does PNC Exist?

The Problem

In a full-communication model, every ECU is always awake and every message is always transmitted. This wastes power, generates unnecessary bus load, and prevents the vehicle from entering low-power states.

The Solution: Partial Networks

The AUTOSAR Partial Networking concept (defined in GM specifications GB8002, GB5280) allows:

  • ECUs to selectively wake only when needed
  • Communication to be scoped to the relevant PDU groups
  • Power savings by letting uninvolved ECUs stay asleep

Why Not Just Use ComM/BswM Directly?

ComM and BswM provide the mechanism (mode switching, PDU group control), but they don't contain the application logic for:

  • Evaluating multiple sensor/signal activation criteria per PN
  • Coordinating activation timing (sync times between Rx and Tx)
  • Tracking wakeup reasons for diagnostics
  • Managing deadline monitoring for remote activations
  • Gating DTC reporting based on PN stability
Key Insight
PNC bridges the gap between application-level activation decisions and BSW-level communication control.

Real-World Scenarios

Before diving into architecture and implementation details, here are four concrete vehicle scenarios that illustrate how PNC operates in practice. These scenarios cover the most common activation and deactivation patterns you will encounter.

Scenario Walkthrough — PN Activation via Sensor Wakeup
Scenario
A driver approaches the vehicle and pulls the door handle. The door handle sensor triggers an ECU wakeup. PNC detects the sensor activation, evaluates which PNCs need to be activated for comfort features (interior lights, seat memory, mirror adjustment), and sends an ERA (Extended Range Active) indication to NM so the relevant partial networks wake up.
Scenario Walkthrough — Signal-Based PNC Activation
Scenario
The climate control module sends an HVAC activation signal via an I-PDU. The I-PDU carries PNC bits indicating that the HVAC partial network should be activated. PNC unpacks the signal value and its status, confirms both are TRUE, and transitions the HVAC PNC to the active state so that all HVAC-related ECUs can begin communicating.
Scenario Walkthrough — NM Frame PNC Indication
Scenario
The PN Coordinator ECU broadcasts an NM frame on the CAN bus with an updated PNC bit vector. Byte 0 carries the Coordinator ECU ID, and bytes 2–7 contain the PN request bits. PNC receives this frame via the NM callback, validates the coordinator ID, extracts each PN bit, and updates the internal remote activation state. The affected PNs take the fast path through the FSM to REMOTELY_ACTIVE.
Scenario Walkthrough — PNC Shutdown / Release
Scenario
All activation sources (sensor, signal, and NM) release a PNC simultaneously. The driver has exited the vehicle, the climate system is off, and the Coordinator clears the PN bit in NM frames. The PNC transitions the affected PN to released state after timer expiry, notifies NM to release the network, and permits system shutdown through SUSD.

3. Where PNC Sits in the Architecture

PNC is an Application Layer SW-C. It communicates with BSW modules exclusively through RTE ports:

BswM

Mode requests (PN state), PDU group switches, deadline monitoring notifications

ComM

Channel state queries (is the bus in FULL_COMMUNICATION?)

CanNm / UdpNm

NM frame indication callback, repeat message time

Dcm

DID read services for PN status reporting

It also interfaces with peer SUM modules:

SUSD

Startup/shutdown gating (PermitExecution, ShutdownPermission, UpdateRecord)

SSFM

Signal feedback and individual PDU disable

SOH / ERRH / SSC

Publish ActiveTxPDUEnable, PN_DTC_Allowed signals

DIAG

Receives DisableNormalComm status to inhibit remote activation during diagnostic sessions

4. Feature Overview

4.1 Local Activation

WHAT A local sensor (e.g., ignition switch) or an application signal (e.g., charging request) activates the PN.

WHY The ECU itself determines it needs communication — it has a reason to talk on the bus.

HOW

  1. Activation_Sensor() polls each configured sensor via RTE
  2. Activation_Signal_In() polls each configured signal + its status via RTE
  3. If any sensor OR (signal AND status) is TRUE, local activation criteria = TRUE
  4. FSM progresses: ENABLE_CHECK → MONITOR_ACTIVATION → ACK_ACTIVATION → TX_ENABLE → LOCALLY_ACTIVE

4.2 Remote Activation

WHAT Another ECU (the PN Coordinator) sends an NM frame with the PN's bit set.

WHY A remote ECU needs this ECU to participate in communication.

HOW

  1. PNC_NM_Frame_Indication() callback fires when an NM frame arrives
  2. Callback checks Coordinator ECU ID and extracts PN bits from NM PDU
  3. If PN bit set: SUM_PNC_Criteria_NM_Act_Remote[PN] = TRUE
  4. FSM takes fast path: ENABLE_CHECK → TX_ENABLE → REMOTELY_ACTIVE

4.3 Deactivation

WHAT A PN transitions back to idle when its activation criteria are no longer met.

WHY Save power, reduce bus load, allow the ECU to sleep.

HOW

  • From LOCALLY_ACTIVE: Local criteria FALSE + Repeat Message Timer expired → REMOTELY_ACTIVE or ENABLE_CHECK
  • From REMOTELY_ACTIVE: Deadline Monitoring timer expires → ENABLE_CHECK
  • Sleep notification: BswM notifies PREPARE_SLEEP → disable PDU groups → ENABLE_CHECK

6. The PN Mode FSM (Finite State Machine)

Each configured PN has its own independent FSM instance. The FSM is evaluated every main function cycle (default: 6.25 ms).

6.1 State Diagram

6.2 State-by-State Explanation

STATE 0: PNC_ENABLE_CHECK ENTRY

Handler: Status_PNC_Enable_Check()

WHAT The idle/entry state. Waits for conditions to allow activation.

WHY Before activating a PN, the ComM channel must be ready and BswM must not be processing a conflicting state transition.

HOW

  1. Calls Activation_Sensor() to read local sensor inputs
  2. Determines local activation = sensor_act OR signal_act
  3. Checks for remote NM activation via SUM_PNC_Criteria_NM_Act_Remote[]
  4. If remote activation (NM bit set, ComM ready, no diag disable): Enables Rx PDU group, starts passive timer, transitions to PNC_TX_ENABLE (fast path)
  5. If local activation: Requests SUM_PNC_REQUESTED from BswM, transitions to PNC_MONITOR_ACTIVATION
  6. Otherwise: stays in ENABLE_CHECK
Key Detail
If a NO_COMMUNICATION request is in progress (being processed by BswM), the handler waits for it to complete before allowing new transitions. This prevents state conflicts.

STATE 1: PNC_MONITOR_ACTIVATION MONITORING

Handler: Status_PNC_Monitor_Activation()

WHAT Monitors whether local activation criteria remains true after initial detection.

WHY Debouncing — ensures the activation is sustained before committing to the full sequence.

HOW

  • If local activation lost: Requests NO_COMMUNICATION, returns to PNC_ENABLE_CHECK
  • If sustained: Requests REQUESTED, starts activation request timer, transitions to PNC_ACK_ACTIVATION

STATE 2: PNC_ACK_ACTIVATION WAITING

Handler: Status_PNC_Ack_Activation()

WHAT Waits for BswM and ComM to acknowledge PN activation and bring the bus to FULL_COMMUNICATION.

WHY BswM needs time to process the mode request and instruct ComM to wake the bus.

HOW

  • If ComM = FULL_COMM + BswM ok + criteria still TRUE: Enables Rx PDU, starts active timer (60 ms), transitions to PNC_TX_ENABLE
  • If timeout: Returns to PNC_MONITOR_ACTIVATION for retry
  • If activation lost: Requests NO_COMMUNICATION, returns to PNC_ENABLE_CHECK

STATE 3: PNC_TX_ENABLE SYNC

Handler: Status_PNC_Tx_Enable()

WHAT Synchronization state — introduces a time delay between Rx and Tx PDU group activation.

WHY Rx is enabled first so the ECU can receive/process messages before transmitting, preventing stale data. Active sync (60 ms) gives more time for local; passive sync (10 ms) is faster for remote.

HOW

  • Active timer expires: Enable Tx, set repeat msg timer, update local DID, apply SSFM disable → PNC_LOCALLY_ACTIVE
  • Passive timer expires: Enable Tx, update remote DID, apply SSFM disable → PNC_REMOTELY_ACTIVE

STATE 4: PNC_LOCALLY_ACTIVE ACTIVE

Handler: Status_PNC_Locally_Active()

WHAT PN is fully active due to local sensor/signal. Communication is flowing.

WHY Steady-state for local activation. Continuously monitors for deactivation.

HOW

  • Local criteria FALSE + repeat msg expired + NM active: Transitions to PNC_REMOTELY_ACTIVE (handoff)
  • Local criteria FALSE + no NM: Requests NO_COMMUNICATION, disables PDUs → PNC_ENABLE_CHECK
  • ComM = PREPARE_SLEEP: Disables PDUs, allows shutdown → PNC_ENABLE_CHECK
  • While active: Sets SHUTDOWN_DISABLE to block system shutdown

STATE 5: PNC_REMOTELY_ACTIVE ACTIVE

Handler: Status_PNC_Remotely_Active()

WHAT PN is active due to remote NM signal. The Coordinator ECU requested this ECU to wake up.

WHY This ECU doesn't have a local reason but another ECU needs it. Deadline monitoring ensures deactivation if the Coordinator stops requesting.

HOW

  • Runs PNC_DeadlineMonitoring() every cycle
  • If local activation detected: Local takeover → PNC_LOCALLY_ACTIVE
  • If DM timer expires: PN deactivates → PNC_ENABLE_CHECK
  • If ComM = PREPARE_SLEEP: Disable PDUs, allow shutdown → PNC_ENABLE_CHECK

7. Activation Criteria — Local and Remote

7.1 Local Activation: Sensors

Function: Activation_Sensor() (called every FSM cycle per PN)

Sensors are physical inputs (ignition switch, door latch, charge connector, etc.) connected to the ECU. Each sensor has an RTE client-server port.

Rule
One sensor is enough to activate the PN locally.
Scenario Walkthrough — Door Handle Sensor Triggers PN Wakeup
Scenario
The driver touches the passive entry door handle on a parked vehicle. The door handle capacitive sensor is mapped to PN_COMFORT (0x21). PNC polls this sensor in its activation loop and detects it as active, triggering the comfort partial network so interior lights, seat memory, and mirror adjustment ECUs can communicate.
Implementation Example — Sum_Pnc_Activation_Sensor (from Sum_Pnc.c) 
/* Polls all configured sensors for the current PN and sets
 * the sensor activation criteria flag if any sensor is active. */
static FUNC(void, SUM_PNC_CODE) Sum_Pnc_Activation_Sensor(void)
{
    uint8 lu8_SensorIdx;
    SUM_PNC_SensorType lt_SensorValue;
    Std_ReturnType lu8_RteStatus;

    for (lu8_SensorIdx = 0u;
         lu8_SensorIdx < SUM_PNC_Cfg[PNC_Number].Number_of_PNC_Activation_Sensors;
         lu8_SensorIdx++)
    {
        /* Read sensor value via RTE client-server port */
        lu8_RteStatus = SUM_PNC_Cfg[PNC_Number].ptr_Activation_Sensor[lu8_SensorIdx](&lt_SensorValue);

        if ((lu8_RteStatus == E_OK) && (lt_SensorValue.active == TRUE))
        {
            /* One active sensor is enough → set criteria flag */
            SUM_PNC_Criteria_Sensor_Act[PNC_Number] = TRUE;

            /* Record which sensor triggered activation for SUSD wakeup reason */
            SUM_PNC_Activation_Buffer[PNC_Number] |= (uint8)(1u << lu8_SensorIdx);
            return;
        }
        else
        {
            /* Sensor inactive → add to deactivation buffer */
            SUM_PNC_Deactivation_Buffer[PNC_Number] |= (uint8)(1u << lu8_SensorIdx);
        }
    }

    /* No sensor active → clear criteria flag */
    SUM_PNC_Criteria_Sensor_Act[PNC_Number] = FALSE;
}

7.2 Local Activation: Signals

Function: Activation_Signal_In() (called periodically at PNC_t_RemoteSignals_Periodicity)

Safety Feature
Both the signal value AND its status (validity) must be TRUE. This prevents false activation from corrupted or uninitialized signals.
Scenario Walkthrough — Climate Control Signal Activates HVAC Partial Network
Scenario
The driver presses the AUTO climate button on the center console. The climate control ECU sets the HVAC activation signal to TRUE in its outgoing I-PDU. This ECU receives the I-PDU, and PNC’s signal polling function reads both the signal value and the signal status. Since both are TRUE, the HVAC partial network (PN_0x22) is activated, enabling communication between compressor, blower motor, and temperature sensor ECUs.
Implementation Example — Sum_Pnc_Activation_Signal_In (from Sum_Pnc.c) 
/* Reads all configured activation signals for the current PN.
 * Both signal value and signal status must be TRUE to activate. */
static FUNC(void, SUM_PNC_CODE) Sum_Pnc_Activation_Signal_In(void)
{
    uint8 lu8_SignalIdx;
    boolean lb_SignalValue;
    boolean lb_SignalStatus;
    Std_ReturnType lu8_RteRetVal;
    Std_ReturnType lu8_RteRetSts;

    for (lu8_SignalIdx = 0u;
         lu8_SignalIdx < SUM_PNC_Cfg[PNC_Number].Number_of_PNC_Activation_Signals;
         lu8_SignalIdx++)
    {
        /* Read signal value from I-PDU via RTE */
        lu8_RteRetVal = SUM_PNC_Cfg[PNC_Number].ptr_Activation_Signal_Value[lu8_SignalIdx](&lb_SignalValue);

        /* Read signal status (validity) via RTE */
        lu8_RteRetSts = SUM_PNC_Cfg[PNC_Number].ptr_Activation_Signal_Status[lu8_SignalIdx](&lb_SignalStatus);

        if ((lu8_RteRetVal == E_OK) &&
            (lu8_RteRetSts == E_OK) &&
            (lb_SignalValue == TRUE) &&
            (lb_SignalStatus == TRUE))
        {
            /* Valid active signal → set criteria flag */
            SUM_PNC_Criteria_Signal_Act[PNC_Number] = TRUE;
            return;
        }
    }

    /* No valid active signal found → clear criteria */
    SUM_PNC_Criteria_Signal_Act[PNC_Number] = FALSE;
}

7.3 Remote Activation: NM Frames

Function: PNC_NM_Frame_Indication() (NM callback, not polled)

Scenario Walkthrough — Receiving NM PDU with Updated PNC Bit Vector
Scenario
The vehicle’s PN Coordinator (typically the gateway ECU) broadcasts an NM frame on the CAN bus. The frame’s byte 0 contains the Coordinator ECU ID (e.g., 0x10). Bytes 2 through 7 carry a bit vector where each bit represents a specific partial network. This ECU receives the NM frame, and the PNC_NM_Frame_Indication callback fires. PNC validates the source ECU ID, then iterates through all configured PNs, extracting each PN’s bit from the correct byte and bit offset position.
Implementation Example — Sum_Pnc_NM_Frame_Indication (from Sum_Pnc.c) 
/* NM callback: processes received NM PDU and extracts PNC bits
 * for each configured partial network. Not polled — event-driven. */
FUNC(void, SUM_PNC_CODE) Sum_Pnc_NM_Frame_Indication(
    NetworkHandleType NetworkHandle)
{
    uint8 lau8_NmPduData[8u];
    uint8 lu8_PnIdx;
    uint8 lu8_ByteIndex;
    uint8 lu8_BitOffset;
    uint8 lu8_BitValue;

    /* Step 1: Read NM PDU data from the NM layer */
    (void)CanNm_GetPduData(NetworkHandle, lau8_NmPduData);

    /* Step 2: Validate coordinator ECU ID (byte 0) */
    if (lau8_NmPduData[0u] != PNC_PN_COORDINATOR_ID)
    {
        return;  /* Not from coordinator → ignore */
    }

    /* Step 3: Extract PN bits for each configured PN */
    for (lu8_PnIdx = 0u; lu8_PnIdx < SUM_PNC_NUMBER_OF_PNS; lu8_PnIdx++)
    {
        lu8_ByteIndex = 2u + (SUM_PNC_Cfg[lu8_PnIdx].DID_Bit_Position / 8u);
        lu8_BitOffset = SUM_PNC_Cfg[lu8_PnIdx].DID_Bit_Position % 8u;
        lu8_BitValue  = (lau8_NmPduData[lu8_ByteIndex] >> lu8_BitOffset) & 1u;

        if (lu8_BitValue == 1u)
        {
            SUM_PNC_Criteria_NM_Act_Remote[lu8_PnIdx] = TRUE;
            /* Reset deadline monitoring timer on each valid reception */
            SUM_GaaPNC[lu8_PnIdx].DM_Timer = SUM_PNC_Cfg[lu8_PnIdx].DM_Max_Timer;
        }
        else
        {
            SUM_PNC_Criteria_NM_Act_Remote[lu8_PnIdx] = FALSE;
        }
    }
}

7.4 Combined Activation Logic

Scenario Walkthrough — Multiple Simultaneous Activation Sources
Scenario
The driver opens the door (sensor activation) at the same moment the PN Coordinator sends an NM frame requesting the same partial network (remote activation). PNC must handle both local and remote activation sources simultaneously and resolve which FSM path to follow. The local path takes priority since it was detected first in the evaluation order, but the remote activation ensures the PN remains active even after the sensor is released.
Implementation Example — Sum_Pnc_Evaluate_Activation (from Sum_Pnc.c) 
/* Main evaluation function: combines all activation sources
 * (sensor, signal, NM) and determines the resulting PN state. */
static FUNC(PNC_ActivationResult, SUM_PNC_CODE) Sum_Pnc_Evaluate_Activation(void)
{
    boolean lb_LocalActive;
    boolean lb_RemoteActive;
    PNC_ActivationResult le_Result;

    /* Local activation = sensor OR signal */
    lb_LocalActive = (SUM_PNC_Criteria_Sensor_Act[PNC_Number] == TRUE) ||
                     (SUM_PNC_Criteria_Signal_Act[PNC_Number] == TRUE);

    /* Remote activation = NM bit from coordinator */
    lb_RemoteActive = (SUM_PNC_Criteria_NM_Act_Remote[PNC_Number] == TRUE);

    if (lb_LocalActive == TRUE)
    {
        /* Local takes priority → full 4-state path */
        le_Result = PNC_ACTIVATION_LOCAL;

        /* Set ERA indication for NM */
        SUM_GaaPNC[PNC_Number].PN_DeActState = LOCAL_DEACTIVE;
    }
    else if (lb_RemoteActive == TRUE)
    {
        /* Remote only → fast path (skip MONITOR + ACK) */
        le_Result = PNC_ACTIVATION_REMOTE;
        SUM_GaaPNC[PNC_Number].PN_DeActState = REMOTE_DEACTIVE;
    }
    else
    {
        /* No activation source → PN should be inactive */
        le_Result = PNC_ACTIVATION_NONE;
    }

    return le_Result;
}

9. Deadline Monitoring

9.1 Purpose

When a PN is remotely active (driven by NM frames from the Coordinator), PNC must verify that the Coordinator continues to request activation. If NM frames stop arriving, the PN should deactivate.

9.2 Two-State DM FSM

9.3 Detailed Behavior

Function: PNC_DeadlineMonitoring() (called every main function cycle for each remotely active PN)

DM_ACTIVE state:

  • Decrements DM_Timer by PNC_MAIN_FUNCTION_PERIOD each cycle
  • If DM_Timer < PNC_MAIN_FUNCTION_PERIOD (about to reach zero):
    • Sets DM_Status = PNC_DM_INACTIVE
    • Notifies BswM: PNC_DM_DISABLE
    • Resets DTC timer to default (blocks DTC reporting)
    • Clears SUM_PNC_Criteria_NM_Act_Remote[PN] = FALSE
    • Removes PN from NM activation history

DM_INACTIVE state:

  • Waits for PNC_NM_Frame_Indication() to reset DM_Timer
  • If DM_Timer >= PNC_MAIN_FUNCTION_PERIOD (new NM frame arrived):
    • Sets DM_Status = PNC_DM_ACTIVE
    • Notifies BswM: PNC_DM_ENABLE

DIDs (Data Identifiers) are standardized diagnostic data elements readable by diagnostic tools.

15. NM Frame Indication Callback

Function: PNC_NM_Frame_Indication(NetworkHandleType NetworkHandle)

This is a callback function invoked by CanNm or UdpNm when an NM frame is received. It is NOT polled.

Processing Steps

  1. Read NM PDU data via CanNm_GetPduData() or UdpNm_GetPduData()
  2. Validate coordinator — check byte 0 matches PNC_PN_COORDINATOR_ID
  3. For each configured PN:
    • Extract PN bit from NM user data bytes (starting at byte 2)
    • If bit set: mark as remotely activated, reset DM timer
    • If bit clear: mark as deactivated
  4. Update activation/deactivation history for SUSD record tracking

Scenario Walkthrough — NM Callback Fires During Active Communication
Scenario
The ECU is already in REMOTELY_ACTIVE state for PN_0x21. The PN Coordinator periodically sends NM frames every 500ms as a heartbeat. Each reception resets the Deadline Monitoring timer, keeping the PN alive. If the Coordinator stops sending (e.g., bus-off condition), the DM timer will eventually expire and the PN will deactivate. This scenario shows how the callback maintains remote activation liveness.

Scenario Walkthrough — PNC Release Timer Prevents Premature Network Sleep
Scenario
A PN is LOCALLY_ACTIVE because the ignition sensor was on. The driver turns off the ignition, so the sensor deactivates. Without the Repeat Message Timer, the PN would immediately attempt to deactivate, potentially cutting off other ECUs mid-transmission. The timer provides a cooldown window where the PN continues sending NM repeat messages, giving other ECUs time to finish their transmissions before the network shuts down.
Implementation Example — Sum_Pnc_Check_Release_Timer (from Sum_Pnc.c) 
/* Checks whether the PNC release timer (Repeat Message Timer) has expired.
 * Called from the LOCALLY_ACTIVE state handler when local criteria drop. */
static FUNC(boolean, SUM_PNC_CODE) Sum_Pnc_Check_Release_Timer(void)
{
    boolean lb_TimerExpired = FALSE;
    uint16 lu16_Threshold;

    /* Calculate threshold in ticks from configured microseconds */
    lu16_Threshold = (uint16)(SUM_PNC_Cfg[PNC_Number].Repeat_Message_Time
                              / PNC_MAIN_FUNCTION_PERIOD);

    if (SUM_GaaPNC[PNC_Number].Flag_Counter_Repeat_Msg_Time_Timer == PNC_TIMER_INVALID)
    {
        /* Timer not started yet → initialize it */
        SUM_GaaPNC[PNC_Number].Counter_Repeat_Msg_Time_Timer = 0u;
        SUM_GaaPNC[PNC_Number].Flag_Counter_Repeat_Msg_Time_Timer = PNC_TIMER_INIT;
    }
    else if (SUM_GaaPNC[PNC_Number].Flag_Counter_Repeat_Msg_Time_Timer == PNC_TIMER_INIT)
    {
        /* Timer running → check if threshold reached */
        if (SUM_GaaPNC[PNC_Number].Counter_Repeat_Msg_Time_Timer >= lu16_Threshold)
        {
            SUM_GaaPNC[PNC_Number].Flag_Counter_Repeat_Msg_Time_Timer = PNC_TIMER_EXPIRED;
            lb_TimerExpired = TRUE;
        }
    }
    else
    {
        /* PNC_TIMER_EXPIRED → already done */
        lb_TimerExpired = TRUE;
    }

    return lb_TimerExpired;
}

PNC source code is generated from Xpand templates, not hand-written, because:

  • Manual maintenance of configuration-dependent code is error-prone and unscalable
