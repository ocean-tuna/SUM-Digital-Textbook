Signal Status and Fault Monitor — Complete Feature Guide

1. Module Overview

What is SSFM?

SSFM (Signal Status and Fault Monitor) is an AUTOSAR Software Component (SW-C) that is part of the ETAS RTA-SUM (Standard Utility Module) product. It runs on GM (General Motors) AUTOSAR ECUs and provides two critical functions:

  1. SSM (Signal Status Monitor) SSM — Monitors the quality and availability of signals received via CAN, Ethernet, and LIN buses. It evaluates whether signals are authenticated (SecOC), have valid alive counters (E2E ARC), valid CRC (E2E CRC), and whether the signal provider is in communication.
  2. ERRH (Error Handler) ERRH — Manages diagnostic error reporting to the AUTOSAR Dem (Diagnostic Event Manager) and Dcm (Diagnostic Communication Manager). It handles DTCs (Diagnostic Trouble Codes), UDS DID/RID services, and debouncing logic.

Why does SSFM exist?

Modern vehicles contain dozens of ECUs (Electronic Control Units) communicating over CAN, Ethernet, and LIN networks. Each ECU depends on signals from other ECUs to operate safely — for example, an ABS module depends on wheel speed signals, and a body control module depends on door lock/unlock commands. When these signals are corrupted, spoofed, delayed, or lost, the consequences range from degraded features to safety-critical failures.

The core problems SSFM solves

1. Signal Trust

How does an ECU know if a received signal is genuine and uncorrupted? SSFM continuously monitors four independent quality dimensions for every configured signal:

  • Authentication (FcI) — Is the message sender who they claim to be? (via SecOC MAC verification)
  • Continuity (FoI) — Is the sender still actively transmitting? (via E2E alive rolling counter)
  • Integrity (FpI) — Has the data been corrupted in transit? (via E2E CRC check)
  • Safety (FsI) — Composite: is the signal safe to use? (FoI OR FpI)
2. Communication Loss Detection
If an ECU stops transmitting, downstream ECUs must detect this quickly and take appropriate action (use default values, enter safe state, etc.). SSFM implements a 2-level detection system: first at the individual signal level, then aggregated at the ECU/node level.
3. Diagnostic Compliance
Automotive regulations (OBD-II, GM-specific specifications) require that communication failures are recorded as standardized DTCs (Diagnostic Trouble Codes) so service technicians can identify and repair faults. SSFM translates signal-level failures into the required DTC format with proper debouncing, enable conditions, and UDS diagnostic service support.
4. Cybersecurity Monitoring
With connected vehicles, in-vehicle networks are attack surfaces. SSFM monitors SecOC MAC authentication per key slot and can detect ongoing authentication failures that may indicate a security breach.
What happens without SSFM?

Without SSFM, each application SW-C would need to implement its own signal monitoring, debouncing, DTC management, and diagnostic service handlers. This would lead to:

  • Duplicated monitoring logic across dozens of SW-Cs
  • Inconsistent fault detection and reporting
  • Missed regulatory requirements for OBD-II compliance
  • No centralized view of communication health across the vehicle network

SSFM centralizes all of this into a single, configurable component that serves the entire ECU.

Real-World Scenarios

To understand why SSFM matters, consider these concrete vehicle scenarios:

Scenario 1: Loss of Communication with a Remote ECU

A gateway ECU detects that an upstream ECU (e.g., the HVAC controller) has stopped communicating. The gateway publishes a NodeStatusECU indication. SSFM's Node Status Manager receives this, marks all signals from that ECU as Unavailable, sets the loss-of-communication DTC (U0XXX_87) after debouncing, and sends a DTC Triggered Message to other ECUs.

The application SW-Cs don't need to know the vehicle architecture details — they simply see Av = Unavailable and use their fallback logic.

Scenario 2: Cybersecurity Attack Detection

An attacker attempts to inject spoofed messages on the Ethernet bus. SecOC MAC verification fails repeatedly. SSFM's Security Status Manager sets FcI=TRUE for each failure, the Availability FSM marks the signal as Unavailable (preventing the application from using spoofed data), and the Key Slot Verify handler tracks the failure count per key slot.

After the calibrated threshold is exceeded, DTC U19A3_8A (Authentication Failure) is set, alerting the fleet management system.

Scenario 3: Transient EMI Interference

Electromagnetic interference from a nearby vehicle causes a single CAN frame CRC error. SSFM's FpI detects the CRC mismatch, but the X-of-Y debouncer absorbs this transient fault (e.g., "3 failures within 10 events" threshold not met). No DTC is set. The next valid frame resets the debouncer.

Without debouncing, this single glitch would have generated a false DTC and an unnecessary workshop visit.

Scenario 4: Diagnostic Session

A service technician connects a diagnostic tool and disables normal communication for testing. SSFM's Availability Manager detects the DisableNormalComm flag and moves all affected signals to Disabled state. No loss-of-comm DTCs are set during this window (DTC enable conditions not met).

When the diagnostic session ends, signals transition back to Uninitialized and re-evaluate on first reception.

Key Architectural Benefits

  1. Abstraction: Functional SW-Cs see only "Available" or "Unavailable" without needing to understand CAN/LIN/Ethernet specifics
  2. Centralization: Single point of truth for signal quality prevents inconsistent fault reporting across SW-Cs
  3. Configurability: Debouncing thresholds, DTC mappings, and preconditions are calibration-driven (via function pointers to RTE calibration data), not hard-coded
  4. Reusability: SSFM can be deployed across different GM vehicle platforms with different network topologies — only the ECUC configuration changes, not the code
  5. Compliance: Meets GM SDV specifications and OBD-II regulations for signal monitoring and diagnostic reporting

/* Sum_Ssfm_SsmInit initializes SSM subsystem */
static FUNC(void,SUM_SSFM_CODE) Sum_Ssfm_SsmInit(void)
{
    uint16 i;
    if (Sum_Ssfm_SsmInitialization == FALSE)
    {
        /* Disable configured PDU in transmission */
        Sum_Ssfm_SsmDisablePdu_Tx();
        /* Set SerialDatas' providers */
        Sum_Ssfm_SetSerialDatasProviders();
        /* Restore DID data from NvM */
        Sum_Ssfm_DID_E0B8_RestoreData();
        Sum_Ssfm_DID_E0BA_RestoreData();
        Sum_Ssfm_DID_E0BB_RestoreData();
        Sum_Ssfm_RestoreMessageAvDidE0B9();
        /* Initialize non-discoverable PDUs to Always Available */
        for (i = 0u; i < SSFM_SSM_NUM_OF_SERIALDATAS; i++)
        {

            {
                Sum_Ssfm_SerialDatas[i].MsgInfoGrp->SigSts = SUM_SSFM_SigSts_Available;
                (void) Sum_Ssfm_SerialDatas[i].MsgInfoGrp->FP_RxMonitoredSignal_Av(
                    (uint8) SUM_SSFM_SigSts_Available);
            }
        }
        Sum_Ssfm_SsmInitialization = TRUE;
    }
}

/* ERRH Execution Manager - runs first each cycle */
Sum_Ssfm_prv_ErrhExecutionManager()
{

    {
        // Read PermitExecution from SUSD

        {

                        Errh_Execution_State = SUM_SSFM_Shutdown_Mode;
                    break;

                    Errh_Execution_State = SUM_SSFM_Shutdown_Mode;
                    break;
            }
        }
        else
        {
            Errh_Execution_State = SUM_SSFM_Invalid_Mode;
        }
        // Notify SUSD about shutdown permission
        // Notify WdgM that ERRH is alive
    }
}

3.1 Initialization

Sum_Ssfm_Initialization.c

SSFM initialization prepares both SSM and ERRH sub-modules for operation. It supports two initialization paths and performs NvM data restoration, PDU configuration, and queue setup.

Two-Path Initialization

The initialization mechanism is controlled by the SsfmGenerateInitRunnable configuration parameter:

SsfmGenerateInitRunnableInit MechanismFunctions
TRUE Runnable_SSFM_Init (INIT-EVENT runnable) Calls Sum_Ssfm_ErrhInit() and Sum_Ssfm_SsmInit() as static functions
FALSE BswM action list (external trigger) Calls Sum_Ssfm_ErrhInit() and Sum_Ssfm_SsmInit() as global functions from BswM Init rule

Initialization Sequence

Both Sum_Ssfm_ErrhInit and Sum_Ssfm_SsmInit execute the following steps in order:

  1. Disable configured Tx PDUs — Sum_Ssfm_SsmDisablePdu_Tx() disables PDUs configured for transmit suppression
  2. Set SerialData providers — Sum_Ssfm_SetSerialDatasProviders() checks each calibration parameter status and records the current provider for multi-provider SerialDatas
  3. Restore DID E0B8 data — Sum_Ssfm_DID_E0B8_RestoreData() reads NvM block to restore fault indication counters and QoS metrics
  4. Restore DID E0BB data — Sum_Ssfm_DID_E0BB_RestoreData() reads NvM block to restore extended learning table data
  5. Restore DID E0B9 availability — Sum_Ssfm_RestoreMessageAvDidE0B9() restores message availability states from NvM
  6. Initialize non-discoverable SOME/IP PDUs — For each SerialData with IsNonDiscoverable = TRUE, sets internal signal status to SUM_SSFM_SigSts_Available and notifies RTE consumers via the availability port. These PDUs remain Available throughout the ECU lifecycle
  7. Check extended learning table format — Reads SdEnableExtendedLearningTableFormat calibration parameter at runtime
  8. Initialize queues — Sum_Algo_Deque_Init() initializes the internal deque for deferred event processing
Non-Discoverable SOME/IP PDUs
PDUs flagged IsNonDiscoverable = TRUE skip the normal Service Manager availability FSM. At initialization, they are immediately set to Available and remain so permanently. Their LostCommInfo pointer is NULL_PTR, so they are excluded from loss-of-communication monitoring.

Implementation Example — CheckDisableCondition & Uninitialized State Handler 
/* Check if disable conditions are met */
static boolean Sum_Ssfm_CheckDisableCondition(const Sum_Ssfm_SerialData* serialData)
{
    boolean PNActive_Flag = Sum_Ssfm_Is_ServiceOrAtLeastOnePNActive(serialData);
    boolean DisableNormalComm_Status = Sum_Ssfm_Is_DisableNormalComm(serialData);
    boolean DisableRxPDU_Status = Sum_Ssfm_Is_DisablePdu_Rx(serialData);
    boolean ServiceActive_Status = (serialData->ServiceInfo != NULL_PTR)
                                    ? serialData->ServiceInfo->IsActive : TRUE;

    if ((FALSE == ServiceActive_Status) || (TRUE == DisableRxPDU_Status) ||
        (FALSE == PNActive_Flag) || (TRUE == DisableNormalComm_Status))
    {
        return TRUE;  /* Disable condition fulfilled */
    }
    return FALSE;
}

/* Uninitialized state handler - transition logic */
static void Sum_Ssfm_SigSts_Uninitialized_State_Handler(
    const Sum_Ssfm_SerialData* serialData, boolean SecOCVerification_Status)
{
    boolean ServiceActive = (serialData->ServiceInfo != NULL_PTR)
                            ? serialData->ServiceInfo->IsActive : TRUE;
    boolean loss_of_comm = Sum_Ssfm_IsSerialDataNodeStsForAvailability(serialData);

    if (TRUE == Sum_Ssfm_CheckDisableCondition(serialData))
    {
        serialData->MsgInfoGrp->SigSts = SUM_SSFM_SigSts_Disabled;
    }
    else if (((SUM_SSFM_SigSts_Supervision_Timeout ==
               serialData->MsgInfoGrp->SigSts_Supervision) &&
              (TRUE == ServiceActive)) || (TRUE == loss_of_comm))
    {
        serialData->MsgInfoGrp->SigSts = SUM_SSFM_SigSts_Unavailable;
    }
    else if ((SUM_SSFM_SigSts_Supervision_Received ==
              serialData->MsgInfoGrp->SigSts_Supervision) &&
             (FALSE == SecOCVerification_Status))
    {
        serialData->MsgInfoGrp->SigSts = SUM_SSFM_SigSts_Available;
    }
}
Non-Discoverable SOME/IP PDUs
These are always available and bypass the FSM. During init, they are set to SUM_SSFM_SigSts_Available and remain there throughout the ECU lifecycle.

4.6 Protection Status (FpI)

Sum_Ssfm_FIM_ProtStatus_Manager.c SSM

Evaluates E2E CRC protection. The FpI (Fault Indication for Protection) tracks whether CRC verification has passed or failed. Two entry points:

  1. Sum_Ssfm_ProtStatus_Manager_Set_FpI — Direct set/reset
  2. Sum_Ssfm_ProtStatus_Manager_Set_FpI_Given_Transformer_Error — Set based on E2E transformer error
  3. Sum_Ssfm_ProtStatus_Manager_Set_FpI_Given_FcI — Set based on SecOC FcI status (for authenticated-only signals, successful MAC means FpI = FALSE)

Transformer Error → FpI Mapping

The Set_FpI_Given_Transformer_Error function maps the E2E transformer error code to a boolean FpI value. Note: FpI uses *_ERR variants (CRC/data errors), whereas FoI uses *_REP/*_SEQ variants (alive counter errors).

4.7 Safety Status (FsI)

4.9 Fault Indications Data Manager

Sum_Ssfm_FaultIndications_DataManager.c SSM

Received SerialData Handler (Entry Point)

Runnable_SSFM_Received_SerialData_<name> is the primary callback triggered on each signal reception. It orchestrates the full fault indication processing chain:

  1. Reset FcI — Asks the Security Status Manager to reset the FcI (successful reception implies no MAC failure)
  2. Set FoI — If safety-protected (E2E configured): sets FoI based on the E2E transformer error code
  3. Set FpI — If protected (authenticated or E2E): sets FpI from transformer error. If authenticated-only (no E2E): FpI = FALSE (successful MAC verification implies protection OK)
  4. Update FsI — If any FxI is available: FsI = FoI OR FpI (safety summary)
  5. Update Node Status — If LcFA enabled: checks test enable conditions, then updates loss-of-comm via Sum_Ssfm_NodeSts_Manager_UpdateSerialDataLostComm. For service-based data, resolves provider DTC via Sum_Ssfm_ResolveServiceDemEvent first

The central coordinator for fault indication processing. It handles:

  1. Debouncing Handler (Sum_Ssfm_FxI_Debouncing_Handler): Processes instantaneous FxI values through the event debouncer. Before setting DTCs, ALL 6 preconditions must be TRUE:
    1. Battery voltage is in normal range (Rte_Read_RP_SUSD_SSFM_Errh_BatteryVoltage)
    2. At least one PN/AP is active (Sum_Ssfm_Is_ServiceOrAtLeastOnePNActive)
    3. PN/AP has been active for ≥5 seconds (Sum_Ssfm_Is_ServiceOrAtLeastOnePNActive_StabilityCheck)
    4. Battery voltage recovery timer has elapsed (Sum_Ssfm_Errh_GetBatteryVoltageRecoveryTimerFlag)
    5. Reset/power-up recovery timer has elapsed (Sum_Ssfm_Errh_GetResetPowerUpRecoveryTimerFlag)
    6. DTC is enabled by calibration (Sum_Ssfm_Errh_C_DTC_UXXXX_83_SignalProtectionIncorrect)
    On failed debounce result: resolves service DEM event (if service-based), keeps FxFA state, and sets DEM event. On passed result: calls Sum_Ssfm_FIM_Debouncer_MUX for multiplexing.
  2. MUX Logic (Sum_Ssfm_FIM_Debouncer_MUX): Multiplexing logic for mapping multiple serial data faults to shared DTCs. Resolves service-based DEM events before applying multiplexing.
  3. DeMUX Logic (Sum_Ssfm_FIM_DTCStatusChanged): Demultiplexing logic when a DTC status changes — propagates FxFA status back to individual serial data. If TestFailed, all corresponding FxFAs are set TRUE. If TestPassed, all FxFAs are set FALSE (AND logic not satisfied).
  4. Service DEM Resolution (Sum_Ssfm_ResolveServiceDemEvent): For service-based serial data, resolves the DTC by querying SPM_GetDTCIdentifier for the high bytes of the DTC value, concatenating with the predefined low byte, and searching for a match in Sum_Ssfm_FxI_DemEvents. Also updates LcFA: for signal-based, LcFA is set when provider has LossOfComm or NodeStsECU set; for service-based, LcFA requires both provider LossOfComm AND the SerialData's own LostCommSts = MISSINGMSG. Failure to resolve causes Sum_Ssfm_UnassignFxIDemFromService.
DTC Confirm Callback Chain
When Dem confirms a DTC, it calls Ssfm_Dem_CB_DTCStatusChanged, which dispatches to up to 5 sub-handlers (conditionally compiled):
  1. Sum_Ssfm_FIM_Dem_CB_DTCStatusChanged → matches DTC to configured DEM events → calls Sum_Ssfm_FIM_DTCStatusChanged (DeMUX) (always)
  2. Sum_Ssfm_LoC_Dem_CB_DTCStatusChanged → matches DTC to ECU DTC values → updates Signal LcFA indications and NodeStatusECU (gateway only) (always)
  3. Sum_Ssfm_IeF_Dem_CB_DTCStatusChanged → updates LIN IeF (Internal Electronic Fault) indications (if LIN responder IeF configured)
  4. Sum_Ssfm_Errh_CheckDTCStatus_And_Enqueue → enqueues DTC into triggered message queue on TestFailed 0→1 (if DTC Triggered Message enabled)
  5. Sum_Ssfm_RunCrank_DTCStatusChanged → updates Run/Crank fault DTC confirm status (if Run/Crank configured)
  6. Sum_Ssfm_KeySlotNumber_DTCStatusChanged → updates key slot verification DTC status (if U19A3_8A + SSC KeySlot configured)

Manages loss-of-communication detection at two levels:

For service-based SerialDatas, Sum_Ssfm_prv_UpdateTrgDvcLostComm replaces ECU-level aggregation. Unlike ECU-level (which uses pre-configured FaultAndRecoveryList/RecoveryOnlyList), target device aggregation is dynamic:

5.1 Event Debouncer (X-of-Y)

MovingWindow_EventBasedX failures within Y events

X-of-Y Moving Window Algorithm

Implementation Example — Debouncer Execution 
Sum_Ssfm_EvaluationStatus Sum_Ssfm_ErrhDebouncerExecution(
    Sum_Ssfm_Debouncer* self, Sum_Ssfm_EventStatus new_event_notification)
{
    Sum_Ssfm_EvaluationStatus ret_val;

    switch (self->error_filter_type)
    {
        case SUM_SSFM_ErrorFilter_None:
            ret_val = (new_event_notification == SUM_SSFM_EventSts_Passed)
                      ? SUM_SSFM_EvaluationSts_Passed
                      : SUM_SSFM_EvaluationSts_Failed;
            break;

        case SUM_SSFM_ErrorFilter_Block:
            ret_val = SUM_SSFM_EvaluationSts_Passed;  /* Always pass */
            break;

        case SUM_SSFM_ErrorFilter_MovingWindow_TimeBased:
        case SUM_SSFM_ErrorFilter_MovingWindow_EventBased:
            ret_val = Sum_Ssfm_ErrhDebouncerMovingWindow(self, new_event_notification);
            break;

        default:
            ret_val = SUM_SSFM_EvaluationSts_Unknown;
            break;
    }
    return ret_val;
}

Provides up to 16 messages ranked by total FpI+FoI failure counts. Updated via Sum_Ssfm_DID_E0BA_Update_Message_Protection with automatic sorting by total failure count (ascending). Each entry: Message ID (4 bytes) + FoI count (1 byte) + FpI count (1 byte) = 6 bytes. Fixed 96-byte NvM buffer. FoI/FpI counters are capped at 255 to prevent overflow. If a new message is not in the list and the buffer is full, the entry with the lowest total count is replaced.

DID E0BB — MAC Verification Per Key Slot

Reports per-key-slot SecOC verification status. Runnable_SSFM_DID_E0BB computes the number of supported key slots (rounded up to: 0, 10, 20, 50, 100, 150, 200, or 255). Key Slot 1 (ECU Unlock Key) is excluded. Each entry: status ($0=Unknown, $1=Passed, $2=Failed, $3=Unused filler), DTC ID, and failure timer. Payload length: 1 + 3 × (supportedSlots - 1) bytes. Saved/restored via NvM block referenced by Sum_Ssfm_MACVerPerKSNvmRef.

5.12 DTC Multiplexing and Demultiplexing

Sum_Ssfm_FaultIndications_DataManager.c ERRH

A critical runtime mechanism that handles the many-to-one and one-to-many relationships between SerialData fault indications and DTCs.

Multiplexing (Many SerialDatas → One DTC)

Multiple SerialDatas can map to the same DTC (e.g., two wheel speed signals from the same ECU share one loss-of-comm DTC). The multiplexer uses OR logic: the DTC is set to FAILED if any mapped SerialData reports a fault.

StepActionLogic
1Collect all SerialDatas mapped to the same DTCConfiguration-driven (shared debouncer instance)
2Evaluate fault status per SerialDataEach FxI evaluated independently through debouncer
3Aggregate resultsDTC_Status = FxI_A OR FxI_B OR ... OR FxI_N
4Set DEM eventDem_SetEventStatus(DTC, FAILED) if any source faulted
5Clear DEM eventDem_SetEventStatus(DTC, PASSED) only when ALL sources clear

Demultiplexing (One DTC Confirmation → Many FxFA Outputs)

When DEM confirms a DTC (via Ssfm_Dem_CB_DTCStatusChanged), the confirmation must be distributed to all affected FxFA ports. The demultiplexer uses AND logic:

FxFA = FxI (instantaneous) AND DEM TestFailed
Each SerialData's FxFA is TRUE only if both its own instantaneous fault indication is TRUE and the shared DTC is confirmed by DEM. This ensures application SW-Cs see fault-active status only for signals that are actually faulting, even though they share a DTC.

Service-Based DTC Resolution

For SOME/IP service-based SerialDatas, the DTC value is resolved at runtime:

  1. Low byte is standard (e.g., 0x87 for missing message)
  2. High bytes are resolved via Sd_GetNodeAddress (IP address) + SPM_SSFM_GetDTCIdentifier (IP → DTC)
  3. The combined DTC uniquely identifies the service provider

/* Simplified test enable evaluation */
static boolean Sum_Ssfm_CheckTestEnableConditions(void)
{
    /* 1. Battery voltage must be in normal range */
    if (BatteryVoltage == UNDER_VOLTAGE) return FALSE;
    if ((BatteryVoltage == OVER_VOLTAGE) && (!OBD_Supported)) return FALSE;

    /* 2. 5-second power-up recovery */
    if (ResetPowerUpTimer < 5000u) return FALSE;

    /* 3. 5-second battery voltage recovery */
    if (BatteryRecoveryTimer < 5000u) return FALSE;

    /* 4. At least one PN active and stable for 5s */
    if (!Sum_Ssfm_Is_AnyPNActiveAndStable()) return FALSE;

    /* 5. Global DTC disable not active */
    if (Sum_Ssfm_DTCsDisabled == TRUE) return FALSE;

    return TRUE;
}

How SSFM ParamDef works with the module
SSFM's ParamDef mirrors its complex dual sub-module architecture:
  • SSM side: Sum_Ssfm_SerialData instances define every CAN/Ethernet signal the module monitors. Each links to an RteSerialData callback, a Channel, optional SecOC/PN/SD references, and FcI/FoI/FpI/FsI debouncers. GroupInfo organizes these by ECU, LIN responder, or target device with per-group DEM event mappings and debounce timers.
  • ERRH side: ErrorsHandlers categorizes errors by source (BSW, LNM, SUSD, SSC, SrvcMgr, Safety/Security) with individual DTC process flags. ErrorFilter provides reusable filtering methods (X_OF_Y windowing or BLOCK) that any error handler can reference.
  • DID/NvM: Errh_DID configures diagnostic DIDs (E0B8–E0BB, F094) and their NvM block storage for persistent error data across power cycles.
The two separate PermitExecutionMasks (SSM vs ERRH) allow SUSD to independently control startup of each sub-module based on wakeup source.

11.1 Adding a New CAN SerialData with E2E Protection

Step-by-Step Guide
  1. Create Sum_Ssfm_SerialData: Add a new instance in Sum_Ssfm_ConfigSet
  2. Set Channel Reference: Point Sum_Ssfm_Channel_Ref to the CAN channel
  3. Configure RteSerialData: Set Sum_Ssfm_RteSerialData_Ref, configure RteCallBackFunction name, set RteSerialDataE2EInTransformerChain = TRUE
  4. Set Partial Network: Point Sum_Ssfm_Partial_Network_Ref to the PN ID
  5. Configure Fault Indication Debouncers: Create Sum_Ssfm_FoI_Debouncer, Sum_Ssfm_FpI_Debouncer, and Sum_Ssfm_FsI_Debouncer sub-containers with Sum_Ssfm_EventFilter_Ref
  6. Add to ECUInfo: Create Sum_Ssfm_ECUInfo_SerialData entry with Sum_Ssfm_FaultDetectionUsage = FaultAndRecovery
  7. Set MessageID: Point Sum_Ssfm_MessageID_Ref for DID E0B9 tracking
  8. Configure DEM: Set DemCallbackDTCStatusChanged with callback Ssfm_Dem_CB_DTCStatusChanged
  9. Configure COM: Set ComTimeoutNotification to Sum_Ssfm_COMCbkTOut_<SerialData>
  10. Regenerate: Run python 60_Workflow/step_03_sums_codegen.py

11.2 Configuring Loss of Communication for an ECU

Step-by-Step Guide
  1. Create Sum_Ssfm_ECUInfo: In Sum_Ssfm_Group_Info, add a new ECU entry
  2. Set Loss Comm ID: Assign unique Sum_Ssfm_LossCommID (0–255, must be unique across all ECUInfo)
  3. Add SerialDatas: Create Sum_Ssfm_ECUInfo_SerialData for each signal from this ECU
    • FaultDetectionUsage = FaultAndRecovery for signals that can trigger AND clear the fault
    • FaultDetectionUsage = RecoveryOnly for signals needed only for recovery
  4. Set Routing Method: Direct (signal from ECU directly), PDURouted (via gateway), or SignalRouted
  5. Configure DEM Event: Create Sum_Ssfm_ECUInfo_Event for each channel, reference Sum_Ssfm_LossofComm_DemEvent_Ref
  6. Set Timer: Sum_Ssfm_LC_ECU_Timer_Ref (0–12000ms) for node loss debouncing
  7. Enable DTC Processing: Set Sum_Ssfm_Errh_C_DTCProcess_SsmNodeLoss = TRUE
  8. Gateway (if CGM): Set Sum_Ssfm_IsGateway = TRUE and Sum_Ssfm_IsThisECUGateway = TRUE in General

11.3 Setting Up DID E0B8 with Correct Sizing

Step-by-Step Guide
  1. Determine Entry Count (N): N = number of SerialDatas you want to track (max 255)
  2. Calculate DCM Length: DcmDspDataByteSize = 1 + N × 10 bytes
    • Example: 50 signals → 1 + 50×10 = 501 bytes
  3. Configure DCM: Set DcmDspDidIdentifier = 57528 (0xE0B8) and the calculated DcmDspDataByteSize
  4. Configure NvM: Set NvMNvBlockLength = same value as DcmDspDataByteSize (must match exactly)
  5. Connect NvM Port: Link PS_NvM_SUM_SSFM_Sum_Ssfm_E0B8_Array to RP_NvM_SSFM_NvMService_DID_E0B8_Data
  6. Set Reference: Point Sum_Ssfm_CommFigureOfMeritNvmRef to the NvM block
Validation Rules
Rule 1: (DcmDspDataByteSize - 1) must be divisible by 10.
Rule 2: Entry count N = (DcmDspDataByteSize - 1) / 10 must be in range [1, 255].
Rule 3: NvMNvBlockLength must equal DcmDspDataByteSize.

11.4 RTE Generation Command

After SSFM code generation, generate RTE using these specific command-line options:

--strict-unconnected-rport-check=off --samples=memmap -eao=disable --os-define-osenv=RTAOS40 -dv8aur=1

--strict-unconnected-rport-check=off is required because SSFM generates ports that may not be connected in all configurations.
