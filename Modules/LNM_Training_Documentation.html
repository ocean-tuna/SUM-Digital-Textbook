1. What is LNM? (Purpose and Context)

What

LNM (LIN Network Manager) is a software module that runs on automotive Electronic Control Units (ECUs). It manages all aspects of LIN bus communication from the Commander (master) side:

  • Deciding when to activate or deactivate LIN networks
  • Deciding which schedule table to run on each LIN channel
  • Detecting communication failures with responder (slave) nodes
  • Providing diagnostic information about network status to service tools

Where It Fits

LNM is one module in the RTA-SUM (Standardized Utility Modules) product suite from ETAS, designed for GM’s AUTOSAR-based ECU platform. It sits in the Application Layer of the AUTOSAR stack:

The LIN Bus (Quick Background)

LIN (Local Interconnect Network) is a low-cost, single-wire serial bus used in vehicles for simple actuators and sensors (e.g., seat controls, mirror adjusters, rain sensors).

CharacteristicDetail
TopologySingle Commander, multiple Responders
CommunicationSchedule-driven — Commander triggers each frame at a specific time slot
SpeedUp to 20 kbit/s (vs CAN at 1 Mbit/s)
Typical usage1–4 LIN networks per ECU, each with 1–6 responder nodes

2. Why Does LNM Exist? (Problem It Solves)

Without LNM, each ECU project would need custom code to handle all aspects of LIN management. LNM solves this by providing a reusable, configuration-driven solution:

Real-World Scenarios

These scenarios illustrate how LNM features work together in typical vehicle situations:

1. LIN Bus Wakeup for Seat Control

Driver presses seat adjustment button. LNM detects the wakeup source, activates the LIN schedule table for the seat motor controller, and begins monitoring the LIN responder node status.

2. LIN Responder Node Fault Detection

A LIN slave (e.g., rain sensor) stops responding. LNM detects the missing response in the schedule slot, reports the fault to ERRH, and isolates the faulty node without disrupting other LIN communication.

3. Schedule Table Switching

Vehicle transitions from normal driving to parking mode. LNM switches from the high-frequency driving schedule to the low-power parking schedule, adjusting which LIN nodes are active.

4. LIN Bus-Off Recovery

Electrical noise causes LIN bus errors. LNM detects the bus-off condition, attempts recovery by reinitializing the LIN driver, and reports the event to diagnostics.

4. Architecture Overview

Design Principles

Configuration-Driven via Function Pointers The core hand-written logic never contains project-specific #if NETWORK_0 branches. Instead, it iterates over LNM_Network_Info[], an array of structs filled with function pointers to the correct RTE ports for each network.
Separation of Generated vs Hand-Written Code Project-specific logic (how many networks, which RTE ports, what rules) lives in generated files. Generic logic (how to manage activation, schedules, faults) lives in hand-written source files.
Periodic Execution Model All functions execute in fixed-period OS runnables. Timing is deterministic and synchronized with the AUTOSAR task scheduler.

7. Global State Machine (Startup/Shutdown FSM)

LNM coordinates its lifecycle with SUSD (Startup/Shutdown Coordinator) via two signals:

  • PermitExecution (input from SUSD): tells LNM when it’s allowed to run
  • ShutdownPermission (output to SUSD): tells SUSD when LNM is ready to shut down

State Transitions

How It Works (LNM_MainFunction)

Runnable_MainFunction is called periodically (default: every 10ms). Each invocation:

Read PermitExecution from SUSD via RTE If reset bit (bit 6) is cleared: immediate transition to LNM_SHUTDOWN. If PermitExecution ANDed with mask equals mask: transition to LNM_RUNNING.
Report WdgM checkpoint Calls Rte_Call_RP_WdgM_LNM_LocalSupervision_CheckpointReached() for watchdog supervision.
Manage ShutdownPermission If LNM_SHUTDOWN: send 0xFF (allow shutdown). If any network active: send rolling counter (0→1→2→3→0). If all inactive: send 0xFF.
Monitor Vehicle Power Mode Track if vehicle is in RUN or PROPULSION for ≥5 seconds (enables bus-off diagnostics).
💡

Why the Rolling Counter? SUSD monitors this value — if it stops incrementing, SUSD knows LNM has crashed and can proceed with forced shutdown. This prevents a hung LNM from blocking ECU shutdown indefinitely.

Implementation Example — Sum_Lnm_MainFunction (from Sum_Lnm.c) 
/* Main cyclic function processing the global state machine */
static FUNC(void, SUM_LNM_CODE) Sum_Lnm_MainFunction(void)
{
    uint8 PermitExec;
    uint8 ShutdownPerm;

    /* Step 1: Read PermitExecution from SUSD via RTE */
    (void)Rte_Read_RP_SUSD_PermitExecution(&PermitExec);

    /* Step 2: Check reset bit (bit 6) for immediate shutdown */
    if ((PermitExec & LNM_RESET_BIT_MASK) == 0u)
    {
        Sum_Lnm_GlobalState = LNM_SHUTDOWN;
    }
    else if ((PermitExec & LNM_PERMIT_MASK) == LNM_PERMIT_MASK)
    {
        /* PermitExecution granted → transition to RUNNING */
        Sum_Lnm_GlobalState = LNM_RUNNING;
    }
    else
    {
        /* Remain in current state */
    }

    /* Step 3: Report WdgM checkpoint */
    (void)Rte_Call_RP_WdgM_LNM_LocalSupervision_CheckpointReached(0u);

    /* Step 4: Manage ShutdownPermission */
    if (Sum_Lnm_GlobalState == LNM_SHUTDOWN)
    {
        ShutdownPerm = 0xFFu;
    }
    else if (Sum_Lnm_AnyNetworkActive == TRUE)
    {
        /* Rolling counter: 0 → 1 → 2 → 3 → 0 */
        Sum_Lnm_RollingCounter = (Sum_Lnm_RollingCounter + 1u) & 0x03u;
        ShutdownPerm = Sum_Lnm_RollingCounter;
    }
    else
    {
        ShutdownPerm = 0xFFu;
    }
    (void)Rte_Write_PP_LNM_ShutdownPermission(ShutdownPerm);
}
Implementation Example — Sum_Lnm_ShutdownCoordination (from Sum_Lnm.c) 
/* Shutdown coordination: deactivate all networks and signal readiness */
static FUNC(void, SUM_LNM_CODE) Sum_Lnm_ShutdownCoordination(void)
{
    uint8 netIdx;

    for (netIdx = 0u; netIdx < LNM_NUM_NETWORKS; netIdx++)
    {
        /* Request NO_COMMUNICATION for each active network */
        if (Sum_Lnm_NetworkStatus[netIdx].comm_mode == LNM_FULL_COMMUNICATION)
        {
            (void)Sum_Lnm_RequestComMode(
                Sum_Lnm_NetworkConfig[netIdx].ComM_ChannelId,
                LNM_NO_COMMUNICATION
            );
            Sum_Lnm_NetworkStatus[netIdx].schedule_enabled = FALSE;
        }
    }

    /* Signal shutdown readiness to SUSD */
    (void)Rte_Write_PP_LNM_ShutdownPermission(0xFFu);
}

8. Network Activation Management

For each LIN network, LNM decides whether the network should be in FULL_COMMUNICATION (active) or NO_COMMUNICATION (sleeping).

Three Activation Mechanisms

Mechanism 1: Signal-Based Activation (Standard Variant)

💡

Why masks? Masks specify which bits of a signal are relevant. The default mask 0xFE means “only the LSB matters” — setting bit 0 activates, clearing bit 0 deactivates.

Mechanism 2: Rule-Based Activation (Standard Variant)

Rules are Boolean expressions combining multiple conditions. Example from a real project:

// Activation rule: activate if ANY condition is TRUE
Rule_DvcActv_PSM = VPM_is_RUN OR RemoteStart_Active OR CTPSF_InOperation

// Deactivation rule: deactivate only if ALL conditions are TRUE
Rule_DvcDeactv_PSM = VPM_is_OFF AND RemoteStart_NotActive AND CTPSF_NotInOperation

Mechanism 3: User-Function Activation (GM SDV Variant)

An external SW-C provides activation decisions:

// External function (implemented outside LNM)
LNM_ComModeType LNM_GetRequiredChannelState(NetworkHandleType ComM_ChannelID);
// Returns: LNM_FULL_COMMUNICATION or LNM_NO_COMMUNICATION

Wakeup Sequence

Implementation Example — Sum_Lnm_EvaluateActivation (from Sum_Lnm_Activation.c) 
/* Evaluate network activation based on signal or rule */
static FUNC(void, SUM_LNM_CODE) Sum_Lnm_EvaluateActivation(
    uint8 NetworkIndex
)
{
    uint8 ActivationSignal;
    uint8 ActivationMask;
    uint8 DeactivationMask;

    /* Read activation signal from RTE */
    (void)Sum_Lnm_NetworkConfig[NetworkIndex].ReadActivationSignal(&ActivationSignal);

    ActivationMask   = Sum_Lnm_NetworkConfig[NetworkIndex].ActivationMask;
    DeactivationMask = Sum_Lnm_NetworkConfig[NetworkIndex].DeactivationMask;

    /* Check activation: (signal | mask) must equal 0xFF */
    if ((ActivationSignal | ActivationMask) == 0xFFu)
    {
        /* Request FULL_COMMUNICATION and start commander timer */
        (void)Sum_Lnm_RequestComMode(
            Sum_Lnm_NetworkConfig[NetworkIndex].ComM_ChannelId,
            LNM_FULL_COMMUNICATION
        );
        Sum_Lnm_NetworkStatus[NetworkIndex].commander_timer = LNM_COMMANDER_WAKEUP_TIME;
    }
    /* Check deactivation: (signal & mask) must equal mask */
    else if ((ActivationSignal & DeactivationMask) == DeactivationMask)
    {
        /* Request NO_COMMUNICATION */
        (void)Sum_Lnm_RequestComMode(
            Sum_Lnm_NetworkConfig[NetworkIndex].ComM_ChannelId,
            LNM_NO_COMMUNICATION
        );
        Sum_Lnm_NetworkStatus[NetworkIndex].schedule_enabled = FALSE;
    }
    else
    {
        /* No change in activation state */
    }
}

9. Schedule Management

Each LIN network runs a schedule table — a timed sequence of LIN frames. LNM manages a per-network state machine that determines which schedule table should be active.

Schedule State Machine

How Schedule Transitions Work

Generated schedule manager runs periodicallyLNM_ScheduleManagement_<Network>() checks current_schedule_state
Evaluate transition rule for current stateIf rule returns TRUE, update current_schedule_state to the target state
Set desired_schedule to new state's tableSet schedule_request_success = FALSE to trigger a request
LNM_ScheduleTable_Request sends request to LinSMOnce LinSM confirms the new schedule is active, schedule_request_success = TRUE

Pre-Sleep Delay

Before transitioning to the SLEEP state, LNM applies a configurable delay (default: 25ms) to allow ongoing LIN frames to complete gracefully.

⚠️

The pre-sleep timer is only available in the Standard variant (LNM_CHANNEL_SCHEDULE_USRFUNCS_ENABLED == STD_OFF). The GM SDV variant does not compile this feature.

Implementation Example — Sum_Lnm_ScheduleManagement (from Sum_Lnm_Schedule.c) 
/* Per-network schedule state machine processing */
static FUNC(void, SUM_LNM_CODE) Sum_Lnm_ScheduleManagement(
    uint8 NetworkIndex
)
{
    uint8 CurrentState;
    uint8 TargetState;
    boolean RuleResult;

    CurrentState = Sum_Lnm_NetworkStatus[NetworkIndex].current_schedule_state;

    /* Only process if schedule management is enabled */
    if (Sum_Lnm_NetworkStatus[NetworkIndex].schedule_enabled == TRUE)
    {
        /* Evaluate the transition rule for the current state */
        RuleResult = Sum_Lnm_ScheduleConfig[NetworkIndex].
            TransitionRules[CurrentState].EvaluateRule();

        if (RuleResult == TRUE)
        {
            /* Get target state from transition table */
            TargetState = Sum_Lnm_ScheduleConfig[NetworkIndex].
                TransitionRules[CurrentState].TargetState;

            /* Update schedule state and request new table */
            Sum_Lnm_NetworkStatus[NetworkIndex].current_schedule_state = TargetState;
            Sum_Lnm_NetworkStatus[NetworkIndex].desired_schedule =
                Sum_Lnm_ScheduleConfig[NetworkIndex].StateToTable[TargetState];
            Sum_Lnm_NetworkStatus[NetworkIndex].schedule_request_success = FALSE;
        }
    }

    /* Request schedule table if not yet confirmed */
    if (Sum_Lnm_NetworkStatus[NetworkIndex].schedule_request_success == FALSE)
    {
        Sum_Lnm_ScheduleTable_Request(NetworkIndex);
    }
}

10. MSCL and DID F1BE Diagnostics

What is MSCL?

MSCL (Master Schedule Channel List) is a 16-bit status word per LIN network that records which responder nodes are present on the bus.

DID F1BE (Diagnostic Read)

DID F1BE is a read-only diagnostic identifier that allows service tools to query the MSCL. The response is 128 bytes:

Functions

NvM Block Sizing: The MSCL NvM block size must be calculated as 2 × n bytes, where n is the number of messages tracked by the MSCL. Each message requires 2 bytes of storage (one byte for the sequence counter value, one byte for the validation flag). Undersized NvM blocks will cause data corruption during NvM read/write operations.

11. Fault Detection and Reporting

LNM detects four categories of faults, all reported to ERRH (Error Handler) which manages DTC setting.

11.1 Loss-of-Communication with Device (Per Responder)

What: Detects when an individual responder stops communicating.

Enable criteria: LNM_C_DTC_LostCommWithLinResp = TRUE, network in FULL_COMMUNICATION, responder present in MSCL.

11.2 Loss-of-Communication with Bus (Per Network)

What: Detects when the entire LIN bus is unreachable. Two conditions (either triggers the fault):

ConditionDetection Logic
All Responders Lost(LoC_WithDevice_Status & MSCL_bits) == MSCL_bits → all present responders timed out
Cannot Achieve FULL_COMMFULL_COMM_requested == TRUE AND retries ≥ LNM_WupTxRetries_Commander (default: 10)
💡

Why the 5-second VPM gate? During power mode transitions (e.g., key-on), the LIN bus may be temporarily unavailable. The 5-second delay prevents false-positive bus-off faults.

11.3 Internal Electronic Failure / IEF (Per Responder)

Two configurable detection mechanisms per responder:

MechanismSignalLogicThreshold

11.4 Responder Not Configured (Per Responder)

Monitors APINFO3 signal. If APINFO3=1: increment not_configured_counter. If counter reaches LNM_Config_Retries (default: 3): report ACTIVE.

Implementation Example — Sum_Lnm_EvaluateNodeStatus (from Sum_Lnm_Fault.c) 
/* Evaluate loss-of-communication status for a single responder */
static FUNC(void, SUM_LNM_CODE) Sum_Lnm_EvaluateNodeStatus(
    uint8 NetworkIndex,
    uint8 ResponderIndex
)
{
    uint8 NodeTimeoutSignal;
    uint16 MsclBitMask;

    /* Only evaluate if DTC reporting is enabled for this responder */
    if (Sum_Lnm_ResponderConfig[NetworkIndex][ResponderIndex].DTC_LostComm_Enabled == TRUE)
    {
        /* Check that network is in FULL_COMMUNICATION */
        if (Sum_Lnm_NetworkStatus[NetworkIndex].comm_mode == LNM_FULL_COMMUNICATION)
        {
            MsclBitMask = (uint16)(1u << ResponderIndex);

            /* Only check responders that are present in MSCL */
            if ((Sum_Lnm_NetworkStatus[NetworkIndex].mscl_value & MsclBitMask) != 0u)
            {
                /* Read timeout signal from SSM */
                (void)Sum_Lnm_ResponderConfig[NetworkIndex][ResponderIndex].
                    ReadNodeTimeout(&NodeTimeoutSignal);

                if (NodeTimeoutSignal == TRUE)
                {
                    /* Set LoC bit and report ACTIVE to ERRH */
                    Sum_Lnm_NetworkStatus[NetworkIndex].LoC_WithDevice_Status |= MsclBitMask;
                    (void)Rte_Call_RP_ERRH_SetEventStatus(
                        Sum_Lnm_ResponderConfig[NetworkIndex][ResponderIndex].FaultEventId,
                        ERRH_EVENT_ACTIVE
                    );
                }
                else
                {
                    /* Clear LoC bit and report INACTIVE to ERRH */
                    Sum_Lnm_NetworkStatus[NetworkIndex].LoC_WithDevice_Status &= ~MsclBitMask;
                    (void)Rte_Call_RP_ERRH_SetEventStatus(
                        Sum_Lnm_ResponderConfig[NetworkIndex][ResponderIndex].FaultEventId,
                        ERRH_EVENT_INACTIVE
                    );
                }
            }
        }
    }
}

    boolean BusOffDetected;

    BusOffDetected = FALSE;
    LoC_Status = Sum_Lnm_NetworkStatus[NetworkIndex].LoC_WithDevice_Status;
    MsclBits   = Sum_Lnm_NetworkStatus[NetworkIndex].mscl_value;

    /* Check if VPM has been in RUN/PROPULSION for >5 seconds */
    if (Sum_Lnm_VpmQualified == TRUE)
    {
        /* Condition 1: All configured responders lost communication */
        if ((MsclBits != 0u) && ((LoC_Status & MsclBits) == MsclBits))
        {
            BusOffDetected = TRUE;
        }

        /* Condition 2: Cannot achieve FULL_COMMUNICATION after max retries */
        if ((Sum_Lnm_NetworkStatus[NetworkIndex].full_comm_requested == TRUE) &&
            (Sum_Lnm_NetworkStatus[NetworkIndex].wakeup_retry_count >=
             Sum_Lnm_NetworkConfig[NetworkIndex].WupTxRetries_Commander))
        {
            BusOffDetected = TRUE;
        }

        /* Report bus-off status to ERRH */
        if (BusOffDetected == TRUE)
        {
            (void)Rte_Call_RP_ERRH_SetEventStatus(
                Sum_Lnm_NetworkConfig[NetworkIndex].BusOffFaultEventId,
                ERRH_EVENT_ACTIVE
            );
        }
        else
        {
            (void)Rte_Call_RP_ERRH_SetEventStatus(
                Sum_Lnm_NetworkConfig[NetworkIndex].BusOffFaultEventId,
                ERRH_EVENT_INACTIVE
            );
        }
    }
}

12. CyberFill Feature

CyberFill is an optional security feature. At initialization, LNM publishes a configured byte value to a specific RTE port used as a “fill value” for unused/padding bytes in LIN frames.

// During LNM_Init(), if CYBERFILL_SUPPORT == LNM_ON:
Rte_Write_PP_LNM_Cyberfill_DataElements_VariableDataPrototype(LNM_CYBERFILL_VALUE);
🔒

Why? Predictable padding values in LIN frames (like 0x00 or 0xFF) could be exploited by attackers who know the frame structure. Using a configurable, non-obvious value adds a layer of defense-in-depth.

Timer Parameters: The TWuDelay timer defines the delay between receiving a wakeup indication and starting the LNM wakeup sequence. This delay allows the transceiver and physical layer to stabilize before LNM begins transmitting. Typical range: 5–50 ms. A related timer TWuTimeout defines the maximum time LNM waits for a wakeup acknowledgment before retrying or reporting failure.

Timer Implementation Pattern

if (timer_started == TRUE) {
    if (timer >= PERIOD_US) {
        timer -= PERIOD_US;        // Decrement by runnable period
    } else {
        // Timer expired — execute action
        timer_started = FALSE;
        // ... trigger action ...
    }
}
💡

Why microseconds? Timers are stored in microseconds (despite being configured in milliseconds) to avoid floating-point arithmetic on embedded platforms, provide sufficient resolution for short delays, and match AUTOSAR conventions.

Timer Reset: All per-network timers are reset to 0 when the network transitions from FULL_COMMUNICATION to NO_COMMUNICATION. This prevents stale timers from firing after a network goes to sleep.

How LNM ParamDef
How LNM ParamDef works with the module
LNM (LIN Network Manager) manages LIN bus networks with a layered configuration:

1. Inputs → Conditions → Rules: Schedule signals (from SWC, COM, or VPM) serve as inputs. Conditions compare inputs against values using operators (==, !=, <, >). Rules combine conditions with AND/OR logic.

2. Networks → Schedule States → Transitions: Each LIN network has its own schedule state machine. Transitions between states are triggered by Rules. States reference LinSM schedules.

3. Responders: Each network has LIN responder devices with MSCL (Master Schedule Control List) bit assignments, DTC configurations for loss-of-communication, and Internal Electronic Failure monitoring.

The wakeup delays (Commander/Responder) control timing when transitioning from sleep. The MSCL strategy (Calibration vs Evaluation) determines how responder presence is managed.

How SOH ParamDef
How SOH ParamDef works with the module
SOH's paramdef is built around a Reliability Monitor architecture with 5 monitor categories:
  • Reset Monitor: Tracks immediate, delayed, and diagnostic resets. Each detector counts occurrences within a time window (TW) and reports via DID F08F.
  • Memory Status Monitor: Tracks NvM errors (Status/Action/Privilege classes) and OS errors (6 OS error categories). Reports via DID F090.
  • Communication Monitor: Tracks diagnostic session activity, security access failures, MAC failures, replay attacks, and SecP errors. Reports via DID F092.
  • Watchdog Monitor: Tracks WdgM local supervision failures and DEM supervision errors, including ERRH-reported supervision status. Reports via DID F093.
  • Platform Monitor: Tracks shutdown delay patterns. Reports via DID F091.

How SSFM ParamDef
How SSFM ParamDef works with the module
SSFM's ParamDef mirrors its complex dual sub-module architecture:
  • SSM side: Sum_Ssfm_SerialData instances define every CAN/Ethernet signal the module monitors. Each links to an RteSerialData callback, a Channel, optional SecOC/PN/SD references, and FcI/FoI/FpI/FsI debouncers. GroupInfo organizes these by ECU, LIN responder, or target device with per-group DEM event mappings and debounce timers.
  • ERRH side: ErrorsHandlers categorizes errors by source (BSW, LNM, SUSD, SSC, SrvcMgr, Safety/Security) with individual DTC process flags. ErrorFilter provides reusable filtering methods (X_OF_Y windowing or BLOCK) that any error handler can reference.
  • DID/NvM: Errh_DID configures diagnostic DIDs (E0B8–E0BB, F094) and their NvM block storage for persistent error data across power cycles.
The two separate PermitExecutionMasks (SSM vs ERRH) allow SUSD to independently control startup of each sub-module based on wakeup source.

How SUSD ParamDef
How SUSD ParamDef works with the module
SUSD is the first SUM module to execute. It reads the wakeup source from EcuM, matches it against SUSDWakeUpRelation to determine which modules should start, then distributes PermitExecution bitmasks through SUSD_C_SUMsInfo (one instance per SUM module: SPM, LNM, SSFM, PNC, DIAG, TCS, etc.).

SUSDGeneral handles Vehicle Power Mode (VPM) determination from Primary/Backup Power Mode COM signals, with configurable security level and initial power mode values. Multiple periodicities control how often SUSD polls battery voltage, wakeup sources, RunCrank status, and VPM changes.

SUSDConfigSet configures RunCrank input diagnostics (stuck high/low with fault maturation counters), battery voltage ranges with hysteresis, and Activity Records (DID E0D7) for tracking wakeup history in NvM.
Key relationship: SUSD ↔ PermitExecutionMask
Every SUM module has a PermitExecutionMask parameter (INTEGER, 0..255, default 254). SUSD sets a PermitExecution value based on the wakeup source, and each module checks: if (PermitExecution & PermitExecutionMask) != 0 then execute. This allows fine-grained control over which modules run for each wakeup scenario.

Common Patterns Across Modules

PermitExecutionMask
Found in: TCS, DIAG, PNC, SrvcMgr, SPM, LNM, SOH, SSFM. Always INTEGER 0..255 with default 254. Used by SUSD to control module startup based on wakeup source.
GenerateInitRunnable + InitFuncPeriodicity
Found in: TCS, DIAG, SrvcMgr, and others. A BOOLEAN flag that enables generation of a one-shot init runnable, paired with a FLOAT periodicity (ms). When FALSE, init is called by BswM action list instead.
ServiceBased References
Found in: TCS, DIAG, SrvcMgr. Paired FOREIGN-REFs for DataTypeMappingSet + IMPLEMENTATION-DATA-TYPE-ELEMENT. These enable SOME/IP service-based communication as an alternative to signal-based COM. Presence activates service-based mode.
CHOICE-REFERENCE-DEF
Found in: TCS, DIAG, SrvcMgr, PNC, SSFM. Used when a reference can point to multiple target types (e.g., ComSignal OR ComGroupSignal, SdClientService OR SdServerService). The integrator selects which target type applies for their project.
Reliability Monitor / Detector Pattern (SOH)
SOH uses a highly consistent detector pattern repeated ~20 times: each detector has a Thresh_Init (INT, fault counter), TW_Thresh_Init (INT, time window in seconds), an NvM block reference for persistent storage, and a DcmDspData DID reference for diagnostic readout. Detectors are grouped under 5 Reliability Monitor categories (Reset, MemoryStatus, Communication, WatchdogManager, Platform).
Error Filter Pattern (SSFM)
SSFM uses reusable GeneralEventsFilter containers with FilterType (NONE/BLOCK/X_OF_Y), threshold X, and window Y parameters. Error handlers across all error categories reference these shared filters, allowing consistent error debouncing configuration.
NvM Block References
Found in: SOH (extensively), SSFM, SUSD, TCS. References to NvMBlockDescriptor containers for persistent data storage across power cycles. Used for DID data, counters, and configuration values that must survive reset.
