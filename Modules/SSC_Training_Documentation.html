SSC (Security Service Coordinator) — Training Documentation

Module: SUM_SSC  |  Product: RTA-SUM (ETAS)  |  Platform: GM SUM (AUTOSAR)
Version: 8.0.1_Pr38  |  SWC Name: SUM_SSC_IVNA

The Security Service Coordinator (SSC) is a core module within the ETAS RTA-SUM product for AUTOSAR-based automotive ECUs in the GM platform. SSC manages:

  • Message Authentication — MAC-based CAN/Ethernet message verification
  • Key Provisioning — SHE key slot lifecycle management
  • Freshness Value Management — Anti-replay counters for SecOC
  • SBAT Validation — Signature Bypass Authorization Ticket verification
  • Diagnostic Security — ECU unlock, encrypted DID/RID, security levels

Real-World Scenarios

The following scenarios illustrate how SSC operates in typical vehicle situations:

Scenario 1: MAC Verification on CAN Message
A safety-critical brake signal arrives on the CAN bus with a SecOC MAC appended. SSC verifies the MAC using the configured cryptographic key, checks the freshness counter to ensure the message is not a replay, and either accepts the signal (allowing it to reach the brake application) or rejects it (blocking the signal and alerting the fault manager).
Scenario 2: Key Provisioning During Manufacturing
A new ECU on the assembly line receives its cryptographic keys via a UDS diagnostic session. SSC processes the SHE M1–M5 key provisioning protocol, stores the validated keys in secure NvM blocks, confirms successful provisioning via M4/M5 response values, and transitions the ECU to operational security mode.
Scenario 3: Freshness Counter Synchronization
After an unexpected ECU reset, the freshness counter is out of sync with the sending ECU. SSC detects the counter mismatch when MAC verification fails, initiates counter re-synchronization via the freshness manager using the fallback counter reconstruction mechanism, and temporarily holds signal processing until sync is achieved.
Scenario 4: Security Attack Detection
Repeated MAC verification failures are detected on a specific PDU. SSC increments the per-message failure counter with each failed attempt. After the configured threshold is exceeded, SSC notifies SSFM which sets a security DTC (U19A3) and logs the event, alerting service technicians to a potential security intrusion on that communication channel.

Execution Model and Runnables

Feature 1: Execution State Machine (Init/Run/Shutdown)

What The execution state machine controls the SSC module's lifecycle — from power-on initialization through normal operation to orderly shutdown.

Why An automotive ECU must manage startup and shutdown carefully. At startup, NvM data must be read before authentication can begin. At shutdown, volatile counter values must be written back to NvM. If the ECU loses power unexpectedly, counters could be reused, enabling replay attacks.

How SSC uses a three-state machine stored in an AUTOSAR Inter-Runnable Variable (IRV). The periodic Ssc_Main() (5ms) reads the current state and dispatches to the appropriate handler. SUSD controls transitions by granting or revoking execution permission.

Init Mode Implementation 
static FUNC(void, SUM_SSC_CODE) Ssc_Main_HandleInitMode(void)
{
    SUSD_SWC_ExecutionStatusType pe_status;
    pe_status = Rte_DRead_RP_PermitExecution_SUSD_SWC_ExecutionStatus();

    if ((pe_status & ~SSC_PERMIT_EXECUTION_MASK) != 0u) {
        Rte_IrvWrite_Runnable_Ssc_Main_EIRV_ExecutionState(SSC_RUN_MODE);
    } else {
        (void)Rte_Write_PP_SSC_ShutdownPermission_SUSD_UserRequest(SSC_PERMITSHUTDOWN);
    }
}

Shutdown Status Flag

#define SSC_NVM_SHUTDOWN_STATUS_SHUTDOWN      (0x5AA5A55Au)
#define SSC_NVM_SHUTDOWN_STATUS_NOTSHUTDOWN   (~0x5AA5A55Au)

If the ECU starts and finds NOTSHUTDOWN, SSC adds a configurable offset (SscImproperShutdownIncrement, default 222) to all authoritative counters to prevent freshness value reuse.

Scenario Walkthrough — ECU Power-On Initialization Sequence
Scenario
The driver turns the ignition key. The body control module ECU powers up and SSC must initialize its security subsystem before any authenticated CAN messages can be processed. SUSD coordinates the startup sequence.
Implementation Example — Sum_Ssc_MainFunction (from Sum_Ssc_Main.c) 
/* Main cyclic function - drives the SSC state machine */
static FUNC(void, SUM_SSC_CODE) Sum_Ssc_MainFunction(void)
{
    uint8 permitExec;
    Std_ReturnType retVal;

    /* Read PermitExecution from SUSD via RTE */
    retVal = Rte_Read_RP_PermitExecution_DE_PermitExecution(&permitExec);

    switch (Ssc_GlobalState)
    {
        case SSC_UNINIT:
            /* Wait for NvM reads to complete */
            if (Sum_Ssc_AllNvmBlocksReady() == TRUE)
            {
                Sum_Ssc_ProcessShutdownStatus();
                Ssc_GlobalState = SSC_INIT;
            }
            break;

        case SSC_INIT:
            /* Wait for PermitExecution from SUSD */
            if ((permitExec & SSC_PERMIT_EXEC_MASK) == SSC_PERMIT_EXEC_MASK)
            {
                Ssc_GlobalState = SSC_RUNNING;
            }
            break;

        case SSC_RUNNING:
            Sum_Ssc_ProcessCounters();
            Sum_Ssc_ProcessDtcMonitors();
            Sum_Ssc_ManageShutdownPermission();
            break;

        case SSC_SHUTDOWN:
            Sum_Ssc_FlushNvmBlocks();
            Rte_Write_PP_ShutdownPermission(0xFFu);
            break;

        default:
            break;
    }
}

Feature 2: Message Authentication Configuration Table (MACT)

What The MACT is the central configuration database of SSC — a compile-time generated array defining every authenticated message on the ECU.

Why A modern GM ECU may have dozens of authenticated messages across CAN and Ethernet. The MACT provides a single, data-driven lookup table so SSC's generic algorithms work on any message by index.

How The Xpand code generator reads the AUTOSAR ECUC model and produces Sum_Ssc_PBCfg.c containing Ssc_RxMessage_Configuration[] and Ssc_TxMessage_Configuration[].

MACT Entry Structure 
typedef struct {
    AuthenticationID_Type               AuthenticationId;    // 5-byte unique message ID
    uint8                               FcntLen;             // Freshness counter bit length
    CounterIdType                       CounterId;           // 5-byte counter ID
    uint8                               SecurityFlags;       // Security configuration
    Ssc_MACTVariableFieldsCollectionType VariableFieldsCollection;
    boolean                             AcceptanceWindow_Support;
} Ssc_MACTEntryType;

MACT Lookup at Runtime

When SecOC calls SSC for a freshness value, SSC uses the AuthenticationId to find the matching MACT entry and retrieve the associated counter:

static const Ssc_MACTEntryType* Ssc_MACT_Lookup(
    const uint8* authId)
{
    for (uint16 i = 0; i < Ssc_NumberOfRxMessages; i++) {
        if (memcmp(Ssc_RxMessage_Configuration[i].AuthenticationId,
                   authId, 5) == 0) {
            return &Ssc_RxMessage_Configuration[i];
        }
    }
    return NULL_PTR; /* unknown message */
}
How MACT drives generic processing

Every SSC security algorithm (MAC generation, freshness lookup, counter sync) takes a MACT entry pointer rather than message-specific parameters. This means adding a new authenticated message requires only a configuration change — zero code modifications. The Xpand generator reads the ECUC model and populates the arrays automatically.

Feature 3: Counter Management (Active and Authoritative)

What Counter management maintains two families of 64-bit counters: Active Counters (Rx, anti-replay) and Authoritative Counters (Tx, monotonically increasing).

Why Without counters, an attacker could record a valid authenticated CAN message and replay it later. Monotonically increasing counters let the receiver reject any message with a counter value it has already seen.

How Counters are stored as uint64 arrays protected by Exclusive Areas. Tx: atomic increment and return. Rx: tentative verification mechanism with MAC confirmation. Counters are persisted to NvM hourly and at shutdown.

Get Active Counter (Rx) 
FUNC(uint64, SUM_SSC_CODE) Ssc_Counter_GetActiveCounter(Ssc_message_index rx_message_index)
{
    uint64 counter;
    SSC_ENTER_CS_RXCOUNTERS();
    counter = Ssc_Rxc_ActiveCounter[rx_message_index];
    SSC_EXIT_CS_RXCOUNTERS();
    return counter;
}
Increment Authoritative Counter (Tx) 
FUNC(uint64, SUM_SSC_CODE) Ssc_Counter_increment_authoritative_counter(
    Ssc_message_index tx_message_index)
{
    uint64 counter;
    SSC_ENTER_CS_TXCOUNTERS();
    counter = Ssc_Txc_AuthoritativeCounter[tx_message_index];
    if (counter < SSC_MAXIMUM_TX_COUNTER_VALUE) {
        counter++;
        Ssc_Txc_AuthoritativeCounter[tx_message_index] = counter;
    }
    SSC_EXIT_CS_TXCOUNTERS();
    return counter;
}
Scenario Walkthrough — Tx Counter Increment During Brake Signal Transmission
Scenario
The brake ECU transmits an authenticated CAN message every 10ms. Each transmission requires a unique freshness counter to prevent replay attacks. SSC manages the authoritative Tx counter that SecOC uses when generating the MAC for outgoing messages.
Implementation Example — Sum_Ssc_Counter_CheckRxValue (from Sum_Ssc_Counter.c) 
/* Validates an incoming Rx counter against the stored active counter */
static FUNC(Std_ReturnType, SUM_SSC_CODE) Sum_Ssc_Counter_CheckRxValue(
    uint32 msgIndex,
    uint64 receivedCounter)
{
    uint64 storedCounter;
    Std_ReturnType result = E_NOT_OK;

    SSC_ENTER_CS_RXCOUNTERS();
    storedCounter = Ssc_Rxc_ActiveCounter[msgIndex];

    /* Accept only if received counter is strictly greater than stored */
    if (receivedCounter > storedCounter)
    {
        /* Store as tentative - not yet confirmed by MAC */
        Ssc_Rxc_TentativeCounter[msgIndex] = receivedCounter;
        result = E_OK;
    }
    else
    {
        /* Replay or stale message detected */
        result = E_NOT_OK;
    }

    SSC_EXIT_CS_RXCOUNTERS();
    return result;
}

Feature 4: Freshness Value Management (SecOC Interface)

What The Freshness Value Manager is the primary callback interface between SSC and SecOC. It provides freshness values (counter-based) that SecOC uses for MAC generation (Tx) and MAC verification (Rx).

Why The AUTOSAR SecOC module is generic — it calls SSC via standardized callbacks to obtain the current freshness value for each message.

How SecOC calls Ssc_GetTxFreshness() before transmitting. For Rx, SecOC calls Ssc_GetRxFreshness() with truncated bits. SSC reconstructs the full 64-bit counter using the LSB bitmask algorithm. Two-attempt fallback is used if the first MAC check fails.

Scenario Walkthrough — Freshness Value Reconstruction on Rx with Fallback
Scenario
An authenticated steering angle message arrives on CAN. The PDU carries only the truncated freshness value (lower 8 bits). SSC must reconstruct the full 64-bit counter from the truncated bits and the stored active counter. If the first attempt fails MAC verification, SSC uses a fallback reconstruction (incrementing the upper bits).
Implementation Example — Sum_Ssc_GetRxFreshness (from Sum_Ssc_FreshnessValue.c) 
/* Reconstructs full 64-bit freshness from truncated value received on bus */
static FUNC(Std_ReturnType, SUM_SSC_CODE) Sum_Ssc_GetRxFreshness(
    uint16 freshnessValueId,
    const uint8* truncatedFreshnessValue,
    uint32 truncatedFreshnessLength,
    uint16 authVerifyAttempts,
    uint8* freshnessValue,
    uint32* freshnessValueLength)
{
    uint32 msgIndex;
    uint64 activeCounter;
    uint64 reconstructed;
    uint64 truncMask;

    msgIndex = Ssc_FreshnessIdToMsgIndex[freshnessValueId];
    activeCounter = Ssc_Rxc_ActiveCounter[msgIndex];
    truncMask = (1u << truncatedFreshnessLength) - 1u;

    /* Replace lower bits with truncated value from PDU */
    reconstructed = (activeCounter & ~truncMask)
                  | (Sum_Ssc_DecodeTruncatedFV(truncatedFreshnessValue, truncatedFreshnessLength));

    /* Ensure reconstructed > active (anti-replay) */
    if (reconstructed <= activeCounter)
    {
        reconstructed += (truncMask + 1u);
    }

    /* On fallback attempt, increment upper portion once more */
    if (authVerifyAttempts > 0u)
    {
        reconstructed += (truncMask + 1u);
    }

    Sum_Ssc_EncodeFreshness(reconstructed, freshnessValue, freshnessValueLength);
    return E_OK;
}

Feature 5: MAC Verification and Message Processing

What This feature processes the results of MAC verification from SecOC. On success, the active counter is updated. On failure, the system decides whether to alert the fault manager or attempt fallback.

Why The MAC verification result drives critical decisions: counter state updates, acceptance window maintenance, and SSFM alert generation.

How SecOC calls Ssc_update_verification_status() with the result. SSC dispatches to Ssc_Rxc_Verified(), Ssc_Rxc_VerifiedOnFallback(), Ssc_Rxc_Failed(), or Ssc_Rxc_FailedOnFallback().

Scenario Walkthrough — MAC Failure Escalation to SSFM
Scenario
A transmission control module PDU repeatedly fails MAC verification. This could indicate a compromised sender, a key mismatch after ECU replacement, or a man-in-the-middle attack on the CAN bus. SSC must track failures and escalate to SSFM after the configured threshold.
Implementation Example — Sum_Ssc_Rxc_VerificationHandler (from Sum_Ssc_MacVerify.c) 
/* Dispatches MAC verification result to appropriate handler */
static FUNC(void, SUM_SSC_CODE) Sum_Ssc_Rxc_VerificationHandler(
    uint16 freshnessValueId,
    uint8 verificationResult)
{
    uint32 msgIndex;

    msgIndex = Ssc_FreshnessIdToMsgIndex[freshnessValueId];

    switch (verificationResult)
    {
        case SECOC_VERIFICATIONSUCCESS:
            Sum_Ssc_Rxc_Verified(msgIndex);
            /* Update active counter with tentative value */
            Ssc_Rxc_ActiveCounter[msgIndex] = Ssc_Rxc_TentativeCounter[msgIndex];
            Ssc_Rxc_FailureCount[msgIndex] = 0u;
            break;

        case SECOC_VERIFICATIONSUCCESS_FALLBACK:
            Sum_Ssc_Rxc_VerifiedOnFallback(msgIndex);
            Ssc_Rxc_ActiveCounter[msgIndex] = Ssc_Rxc_TentativeCounter[msgIndex];
            Ssc_Rxc_FailureCount[msgIndex] = 0u;
            break;

        case SECOC_VERIFICATIONFAILURE:
            Ssc_Rxc_FailureCount[msgIndex]++;
            if (Ssc_Rxc_FailureCount[msgIndex] >= SSC_MAC_FAILURE_THRESHOLD)
            {
                Sum_Ssc_ReportMacFailure(msgIndex);
            }
            break;

        default:
            /* NO_VERIFICATION - no action */
            break;
    }
}

Feature 6: Counter Synchronization

What Counter synchronization keeps Rx counters aligned with Tx counters across ECUs. When a sender's counter jumps (e.g., after improper shutdown), the receiver must learn the new value.

Why After an ECU restarts, its Tx counter may jump by millions (improper shutdown offset). Without sync, all messages from the restarted ECU would be rejected as replay attempts.

How The sender transmits a counter sync message. On the Rx side, Ssc_Rxc_counter_sync() evaluates the sync value through a three-state logic that tracks tentative verification state.

Sync Implementation

void Ssc_Rxc_counter_sync(uint16 msgIdx, uint64 syncValue)
{
    Ssc_CounterSync_State* st = &Ssc_SyncState[msgIdx];
    uint64 halfRange = (uint64)1 << (mact[msgIdx].FcntLen - 1);

    switch (st->state) {
    case SYNC_BEFORE_TENTATIVE:
        /* Accept any out-of-range sync value */
        if (syncValue > st->activeCounter + halfRange ||
            syncValue < st->activeCounter - halfRange) {
            st->tentativeCounter = syncValue;
            st->state = SYNC_TENTATIVE_SET;
        }
        break;
    case SYNC_TENTATIVE_SET:
        /* Only accept higher tentative values */
        if (syncValue > st->tentativeCounter)
            st->tentativeCounter = syncValue;
        break;
    case SYNC_AFTER_VERIFIED:
        /* Only accept large jumps (re-enter tentative) */
        if (syncValue >= st->activeCounter + halfRange) {
            st->tentativeCounter = syncValue;
            st->state = SYNC_TENTATIVE_SET;
        }
        break;
    }
}
Why three states instead of a simple overwrite?

An attacker could inject a crafted sync message with an arbitrary counter value. The three-state logic ensures that a sync value is only committed to the active counter after a subsequent authenticated message passes MAC verification using the tentative counter. This prevents counter manipulation via unprotected sync messages.

What Key Provisioning manages cryptographic keys stored in SHE key slots — loading new keys, tracking which slots are provisioned, and reporting status via diagnostics.

Implementation Example — Sum_Ssc_KeyProvision_LoadSlot (from Sum_Ssc_KeyProvision.c) 
/* Loads a single SHE key slot via the M1-M5 protocol */
static FUNC(Std_ReturnType, SUM_SSC_CODE) Sum_Ssc_KeyProvision_LoadSlot(
    uint8 keySlotIndex,
    const uint8* m1m2m3Data,
    uint8* m4m5Response)
{
    Std_ReturnType result;
    uint8 m4Buffer[32u];
    uint8 m5Buffer[16u];

    /* Call CSM to load the key into the HSM SHE slot */
    result = Csm_RbSheLoadKeySlot(
        Ssc_KeySlotConfig[keySlotIndex].csmKeyId,
        &m1m2m3Data[0u],   /* M1: 16 bytes */
        &m1m2m3Data[16u],  /* M2: 32 bytes */
        &m1m2m3Data[48u],  /* M3: 16 bytes */
        m4Buffer,
        m5Buffer);

    if (result == E_OK)
    {
        /* Copy M4/M5 proof to response buffer */
        Sum_Ssc_MemCopy(m4m5Response, m4Buffer, 32u);
        Sum_Ssc_MemCopy(&m4m5Response[32u], m5Buffer, 16u);

        /* Mark slot as provisioned */
        Ssc_KeySlotProvisionStatus[keySlotIndex] = SSC_KEY_PROVISIONED;
        Ssc_NvmWriteRequired = TRUE;
    }

    return result;
}

Feature 8: HSM (Hardware Security Module) Support

What HSM Support provides the interface between SSC and the GM Hardware Security Module (GHSM) — managing initialization status polling, secure boot status checking, and bulk key load operations.

Why The HSM is a separate hardware component with its own startup sequence. SSC must wait for it before performing crypto operations.

How At startup, SSC polls Ssc_VerifyGHSMStatus() with a 50ms timeout until CMD_STATE_COMPLETE. For bulk SHE operations, a three-phase finalize state machine manages the sequence.

// GHSM command states
#define SSC_GHSM_SP_CMD_STATE_FREE              (0x00U)

#define SSC_GHSM_SP_CMD_STATE_TIMEOUT           (0x02U)
#define SSC_GHSM_SP_CMD_STATE_COMPLETE          (0x03U)
#define SSC_GHSM_SP_CMD_STATE_HOST_PROG_ACTIVE  (0x04U)
#define SSC_GHSM_SP_CMD_STATE_FAIL              (0x05U)
#define SSC_GHSM_SP_CMD_STATE_UNINITIALIZED     (0x06U)

Three-Phase Finalize State Machine

For bulk SHE key loading operations (RID 0x0272), SSC uses a three-phase finalize sequence to ensure all key slots are committed atomically:

1FINALIZE_PREPAREQueue all pending key slot writes to HSM command buffer
2FINALIZE_WAITPoll HSM status until all writes return CMD_STATE_COMPLETE or timeout
3FINALIZE_VERIFYRead back M4/M5 proof values from each slot and validate against expected
HSM initialization vs SSC initialization

The HSM has its own boot sequence independent of the AUTOSAR ECU startup. SSC must poll with a 50ms interval because the HSM may still be executing its secure boot when SSC's init runnable first executes. The UNINITIALIZED state means the HSM is still booting; HOST_PROG_ACTIVE means a flash programming operation is in progress. SSC can only proceed with crypto operations once the HSM reports COMPLETE.

Feature 9: APSRKP (APS Regional Key Provisioning)

What APSRKP manages region-based cryptographic key provisioning. Different geographic regions use different root public keys and key sets. APSRKP handles reading regional identity from flash CysInfoBlocks and provisioning region-specific keys.

Why Vehicle security regulations differ by region. A single ECU design must support deployment across multiple markets, each requiring its own root-of-trust keys.

How SSC reads two redundant CysInfoBlocks from flash (0x00002000, 0x00004000). Key updates use RID 0x0613 with multi-step verification. RID 0x0614 manages the back-office security counter.

CysInfoBlock Structure

Two redundant CysInfoBlocks are stored in flash at fixed addresses. SSC reads both at startup and validates consistency:

0x00002000Primary CysInfoBlockContains Root Public Key hash, Region ID, ECU ID, and MACs
0x00004000Backup CysInfoBlockRedundant copy for corruption detection

RID 0x0613 Verification Steps

2Host MAC verification0x0ARequest integrity compromised
3RPK hash comparison0x13Root public key mismatch for target region

RID 0x0614: Back-Office Security Counter

RID 0x0614 manages the back-office security counter used for region key update tracking. This monotonic counter prevents replay of old key provisioning sequences. The counter value is stored in NvM and incremented after each successful RID 0x0613 operation.

Why two CysInfoBlocks?

Flash memory corruption (e.g., during a power loss mid-write) could invalidate region identity data. By storing two copies at different addresses, SSC can detect single-block corruption and either use the valid copy or report DTC U198C_54 (region info invalid). If both blocks are valid but contain different Region IDs, DTC U198C_8A (region mismatch) is set.

What ECU Unlock implements the UDS SecurityAccess service (0x27) supporting 9 unlock levels, each gating access to specific diagnostic operations.

Feature 11: SBAT Validation (Signature Bypass Authorization Ticket)

What The SBAT (Signature Bypass Authorization Ticket) is a 930-byte digitally signed ticket that authorizes which signature-bypass operations are permitted on the ECU. It contains ECU identity, creation/expiration counters, security control flags, unlock level permissions, signer certificate chain, and a cryptographic signature. SSC validates the SBAT at every boot to determine which diagnostic unlock levels and reprogramming operations the ECU is authorized to perform without full signature verification.

Why During manufacturing, service, and OTA updates, certain operations (flash reprogramming, calibration writes, diagnostic routines) require bypassing the normal signature checks. Without a controlled bypass mechanism, either all signature checks would need to be disabled (insecure) or every operation would require full cryptographic signing (impractical). The SBAT provides a signed, time-limited, ECU-specific authorization ticket that gates exactly which bypass operations are permitted, ensuring that only authorized tools with valid tickets can perform privileged operations.

How Multi-stage validation state machine: (1) validate CysInfoBlocks region info, (2) load SBAT image from NvM, (3) verify Part B signature (RSA-2048 PKCS v1.5 or EdDSA Ed25519 via Csm), (4) extract and validate signer certificate, (5) final signature check, (6) mark validation done. The UnlockLevel field gates which of the 9 security access levels are permitted. SBAT V2 adds progressive BIS (Boot Integrity Stage) levels A–E for staged capability unlock. DIAG triggers validation via the RP_DIAG_SSC_StartSBATDIDValidation port after SBAT write/update operations.

SBAT in the Boot Sequence

During SSC initialization, SBAT validation is one of four sub-states executed before the module transitions to RUN mode:

  1. ReadNvM — Load all 19+ NvM blocks (counters, keys, SBAT image, flags)
  2. RestoreCounters — Reconstruct freshness counter state from persistent storage
  3. CheckSBAT — Execute the 6-stage SBAT validation state machine; extract UnlockLevel to determine which bypass operations are authorized
  4. WaitPermit — Wait for SUSD PermitExecution signal before transitioning to RUN

If SBAT validation fails at boot, SSC still transitions to RUN mode but with all bypass operations denied. A new valid SBAT can be provisioned via DID 0xE0B5 during a diagnostic session to restore bypass authorization.

Feature 13: NvM (Non-Volatile Memory) Management

What NvM Management provides persistent storage for all SSC security-critical data across power cycles — 19+ NvM blocks storing counters, flags, keys, SBAT images, and session state.

Why Security counters must survive power cycles — if counters reset to zero, replay attacks become trivial. Hourly writes balance wear-leveling against data loss risk.

How Each block uses a generic function-pointer-based abstraction (Ssc_GenericNvmAccessType) with a RAM mirror pointer and three RTE function pointers. Counters are written hourly during RUN and flushed at shutdown.

Scenario Walkthrough — Hourly Counter Persistence and Shutdown Flush
Scenario
The vehicle has been running for 59 minutes. SSC's hourly NvM write timer is about to expire. Meanwhile the driver turns off the ignition, triggering a shutdown sequence. SSC must ensure all counter values are safely persisted to NvM before granting shutdown permission to SUSD.
Implementation Example — Sum_Ssc_NvmFlushAllBlocks (from Sum_Ssc_Nvm.c) 
/* Flushes all NvM blocks during shutdown or provisioning events */
static FUNC(void, SUM_SSC_CODE) Sum_Ssc_NvmFlushAllBlocks(void)
{
    uint8 blockIdx;
    Std_ReturnType writeResult;

    for (blockIdx = 0u; blockIdx < SSC_NVM_BLOCK_COUNT; blockIdx++)
    {
        /* Use function pointer table for RTE NvM access */
        if (Ssc_NvmBlockConfig[blockIdx].writeFunc != NULL_PTR)
        {
            writeResult = Ssc_NvmBlockConfig[blockIdx].writeFunc(
                Ssc_NvmBlockConfig[blockIdx].ramMirrorPtr);

            if (writeResult == E_OK)
            {
                Ssc_NvmBlockPending[blockIdx] = TRUE;
            }
            else
            {
                /* NvM rejected write - block may be busy */
                Ssc_NvmWriteRetryCount[blockIdx]++;
            }
        }
    }

    /* Set shutdown status to SHUTDOWN (clean exit) */
    Ssc_ShutdownStatusRam = SSC_NVM_SHUTDOWN_STATUS_SHUTDOWN;
    Ssc_NvmBlockConfig[SSC_NVM_SHUTDOWN_BLOCK].writeFunc(
        &Ssc_ShutdownStatusRam);
}

Frequency-Based DTC Gating (U19A3_54)

The primary security DTC uses a timer-based evaluation to avoid false positives during initialization:

/* U19A3_54 is only evaluated after the frequency timer expires */
if (Ssc_DtcFrequencyTimer >= SSC_DTC_FREQUENCY_THRESHOLD) {
    boolean keysFailed  = Ssc_CheckAllKeySlotsEmpty();
    boolean ekpsFailed  = Ssc_CheckEKPS_MEC_Consistency();
    boolean cntrFailed  = Ssc_CheckAuthCounterValidity();

    if (keysFailed || ekpsFailed || cntrFailed) {
        Dem_SetEventStatus(DTC_U19A3_54, DEM_EVENT_STATUS_FAILED);
    } else {
        Dem_SetEventStatus(DTC_U19A3_54, DEM_EVENT_STATUS_PASSED);
    }
    Ssc_DtcFrequencyTimer = 0; /* reset for next cycle */
}
Why frequency-based gating?

During ECU startup, key slots may temporarily appear empty while NvM blocks are still being read. Immediate DTC evaluation would produce false failures. The frequency timer (typically configured to a few seconds) ensures SSC waits for the full initialization sequence before judging key slot status.

Feature 15: IVMAS (In-Vehicle Message Authentication Status)

What IVMAS tracks the ECU's overall message authentication capability as a 2-bit status with 4 states.

Why Other modules need to know whether this ECU can authenticate messages. In CAL-only mode, authentication is intentionally disabled. State 0x02 is flagged invalid because you cannot authenticate without provisioned keys.

How At init, Ssc_check_IVMAS_init() scans all protected message configurations and sets the IVMAS status accordingly. Used as both compile-time and runtime gate.

IVMAS Status Codes

ValueKPAuthMeaningDTC Impact
0x00NoNoCAL-only mode — no protected messages configured. Security features completely disabled.None (intentional)
0x01YesYesNormal operation — both key provisioning and message authentication supported and active.None (healthy)
0x02NoYesAuthentication enabled but keys not provisioned. INVALID state — authentication will always fail.Sets DTC (configuration error)
0x03YesNoKey provisioning enabled but authentication disabled. Keys can be provisioned but not used for MAC operations.None (valid configuration)
void Ssc_check_IVMAS_init(void)
{
    boolean hasProtectedMsg = FALSE;
    boolean hasKeyProv      = FALSE;

    for (uint16 i = 0; i < Ssc_NumberOfRxMessages; i++) {
        if (Ssc_RxMessage_Configuration[i].SecurityFlags & SSC_AUTH_ENABLED)
            hasProtectedMsg = TRUE;
    }
    for (uint16 i = 0; i < Ssc_NumberOfKeySlots; i++) {
        if (Ssc_KeySlotConfig[i].provisioningEnabled)
            hasKeyProv = TRUE;
    }

    if (hasProtectedMsg && hasKeyProv)       Ssc_IVMAS = 0x01;
    else if (hasProtectedMsg && !hasKeyProv) Ssc_IVMAS = 0x02; /* INVALID */
    else if (!hasProtectedMsg && hasKeyProv) Ssc_IVMAS = 0x03;
    else                                    Ssc_IVMAS = 0x00;
}

Feature 16: PCSM (Protected Counter Sync Message) Handling

What PCSM is a special CAN message carrying the full authoritative counter value so receiving ECUs can synchronize their Rx active counters.

Why If the receiver misses messages (bus-off, PN wakeup), its Rx counter falls behind. PCSM provides a recovery mechanism.

How Each PCSM-protected Tx message has a configured send timeout. An IPdu callout embeds the current authoritative counter. On the Rx side, counter sync logic uses the PCSM value after MAC verification succeeds.

PCSM Tx Configuration

/* IPdu Tx callout — embeds full authoritative counter in PCSM payload */
boolean Ssc_PCSMTxCallout(PduIdType pduId, PduInfoType* pduInfo)
{
    uint16 msgIdx = Ssc_GetMessageIndex(pduId);
    uint64 authCounter = Ssc_AuthoritativeCounters[msgIdx];

    /* Serialize 8-byte big-endian counter into PCSM payload */
    for (uint8 i = 0; i < 8; i++) {
        pduInfo->SduDataPtr[i] = (uint8)(authCounter >> (56 - i * 8));
    }
    return TRUE; /* allow transmission */
}

PCSM vs regular counter sync

Regular counter sync (Feature 6) handles counter jumps after ECU restart. PCSM handles counter lag when the receiver was offline. The key difference: counter sync is triggered by the sender detecting out-of-range values in incoming sync messages, while PCSM is a periodic broadcast from the sender carrying the full counter value so any offline receiver can resynchronize.

Feature 17: Acceptance Window for Service-Based Messages

What The Acceptance Window is an anti-replay mechanism for SOME/IP (Ethernet) messages that accepts freshness values within a configurable sliding window of up to 64 values.

Why Unlike CAN, SOME/IP messages over Ethernet can arrive out of order. A strict monotonic counter would reject legitimate out-of-order packets.

How Each Rx message maintains a 128-bit bitmask and the highest FV seen. New FV above highest: accept and shift. FV within window: check bitmask. Below window: reject. Equal to highest: reject as duplicate.

typedef struct {
    FreshnessValueID_Type SecOC_FreshnessValueId;
    uint8                 SecOC_RxAcceptanceWindow;   // max 64
    uint64                HighestFVSeen;
    uint64                SecOC_RxAcceptanceWindowMaskVal[2U]; // 128-bit mask
} Ssc_AWFreshnessValueInfo_Type;

Acceptance Window Algorithm

Std_ReturnType Ssc_AW_CheckFreshness(
    Ssc_AWFreshnessValueInfo_Type* aw, uint64 incomingFV)
{
    if (incomingFV == aw->HighestFVSeen) {
        return E_NOT_OK; /* duplicate — reject */
    }

    if (incomingFV > aw->HighestFVSeen) {
        /* New highest — shift window forward */
        uint64 shift = incomingFV - aw->HighestFVSeen;
        Ssc_AW_ShiftMask(aw, shift);
        Ssc_AW_MarkSeen(aw, 0); /* bit 0 = newest */
        aw->HighestFVSeen = incomingFV;
        return E_OK;
    }

    /* Within window? */
    uint64 age = aw->HighestFVSeen - incomingFV;
    if (age > aw->SecOC_RxAcceptanceWindow) {
        return E_NOT_OK; /* too old — reject */
    }

    /* Check bitmask for duplicate */
    if (Ssc_AW_IsSeen(aw, age)) {
        return E_NOT_OK; /* already seen — reject */
    }
    Ssc_AW_MarkSeen(aw, age);
    return E_OK;
}
Why 128-bit mask for a max-64 window?

The 128-bit bitmask (uint64[2]) provides 128 bit positions even though the maximum configurable window is 64. This extra capacity handles edge cases during window shifts — when the window slides forward, bits beyond the window size are naturally cleared, preventing stale "seen" flags from incorrectly rejecting fresh messages after a large counter jump.

Encryption Pipeline Detail

/* Step 1: Key derivation from session key */
Ssc_KeyDerivationFunction(sessionKey, derivedKey, SSC_AES_KEY_LEN);

/* Step 2: Generate AES-128 encryption key */
Ssc_EncryptedReadServices_GenerateKey(derivedKey, aesKey);

/* Step 3: Read plaintext data */
if (ridType == RID_04DB)
    Dcm_ReadDid(didId, plainBuffer, &dataLen);
else /* RID_04DC */
    Dcm_ReadMemory(address, size, plainBuffer, &dataLen);

/* Step 4: AES-128-CBC encrypt */
Ssc_SymEncrypt(aesKey, iv, plainBuffer, dataLen, cipherBuffer);

/* Step 5: AES-CMAC over ciphertext */
Ssc_MacGenerate(aesKey, cipherBuffer, dataLen, macBuffer);

/* Step 6: Return [ciphertext || MAC] to tester */
memcpy(responseBuffer, cipherBuffer, dataLen);
memcpy(responseBuffer + dataLen, macBuffer, SSC_MAC_LEN);
Why encrypt-then-MAC?

SSC uses the encrypt-then-MAC pattern (AES-CBC encryption followed by AES-CMAC). This ensures the tester can verify ciphertext integrity before attempting decryption, preventing padding oracle attacks. The MAC covers the ciphertext, so any tampering is detected without exposing the plaintext.

What Tx Variant Configuration allows a single ECU build to support multiple SOME/IP Tx message configurations (e.g., different radar sensor variants).

/* Called by application at startup to select SOME/IP Tx variant */

How SrvcMgr ParamDef works with the module
DID references (E0CC/E0CD/E0CE) for Learning Table diagnostics, RID references (0654/0612) for session control. COM signals (PropSysActv, VehSpdAvgDrvn) provide runtime inputs. Service-Based refs support SOME/IP architectures.

Troubleshooting

Common issues encountered during SSC integration, configuration, and runtime operation.

Key Provisioning Failures
SymptomRoot CauseResolution
DTC U19A3_54 set immediately after startupNvM blocks not yet read when DTC check runsIncrease SSC_DTC_FREQUENCY_THRESHOLD to allow NvM read to complete before first DTC evaluation
Key provisioning completes but EKPS remains FALSEMEC counter mismatch between SSC and HSMVerify MEC counter synchronization. Check that HSM MEC value matches SSC’s expected value. May require MEC reset via diagnostic session.
DTC U19A3_8A set during key provisioningIndividual SHE key slot MAC verification failureCheck key material integrity. Verify that the correct key hierarchy is being used. Re-provision affected key slot.
MAC Verification Failures
SymptomRoot CauseResolution
Intermittent MAC failures on specific PDUCounter desynchronization between sender and receiverCheck trip counter alignment. Verify counter sync mechanism. Use DID F084 to read current counter values.
All MAC verifications failing after reflashKey slots cleared during reflash, keys not re-provisionedRun key provisioning sequence after reflash. Verify InitialReflashFlag handling.
MAC failures only on certain messagesMACT configuration mismatch (wrong key slot or FV ID assigned)Review MACT table entries for affected messages. Verify key slot assignment matches sender configuration.
HSM Communication Issues
SymptomRoot CauseResolution
DTC U1961 set at startupHSM initialization timeoutCheck HSM hardware connection. Verify SPI/communication interface. Increase HSM init timeout if hardware is slow.
Crypto operations return CRYPTO_E_BUSYHSM queue full or previous operation not completedCheck scheduling. Ensure SSC execution period allows sufficient time for HSM responses. Review exclusive area configuration.
SBAT validation always failsSBAT signature keys not loaded or expiredVerify SBAT key provisioning. Check SBAT expiry date against current time. Confirm RSA/Ed25519 key is correctly provisioned.
NvM and Configuration Issues
SymptomRoot CauseResolution
SSC hangs during shutdownNvM write not completing within timeoutIncrease SSC_NVM_WRITE_TIMEOUT_IN_MS. Check NvM queue depth. Verify Fee/Fls driver is responsive.
DTC U198C_54 set at every startupCysInfoBlock corrupted in both NvM locationsRe-provision region info via APSRKP diagnostic session. Check for power loss during previous NvM writes.
