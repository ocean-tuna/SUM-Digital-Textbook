SUM_DIAG Module — Training Documentation

Module: SUM_DIAG Layer: AUTOSAR Application SWC Spec: GB8002 / GB6003 / SDV 2.0 Version: 8.0.1

1. Overview

What is SUM_DIAG?

SUM_DIAG is an AUTOSAR Application Layer Software Component responsible for managing diagnostic functionality on an automotive ECU. It acts as a gatekeeper and coordinator for UDS (Unified Diagnostic Services) operations, ensuring that diagnostic requests are only processed when the correct preconditions are met.

Why does it exist?

In modern vehicles, diagnostic tools (testers) connect to ECUs to perform operations like software updates, DTC clearing, memory reads, and ECU resets. These operations can be dangerous if performed under wrong conditions (e.g., resetting the ECU while the vehicle is moving). SUM_DIAG enforces safety preconditions and coordinates with other system modules to ensure safe diagnostic operations.

What does it do? (Feature Summary)

How does it fit in the system?

SUM_DIAG sits between the DCM (BSW) and other application-layer SUM modules. It receives diagnostic service requests from DCM, validates preconditions by consulting other SUMs, and returns allow/deny decisions.

Real-World Scenarios

The following scenarios illustrate how SUM_DIAG operates in practice. Each represents a situation you will encounter during development, integration, or diagnostics:

1. MEC Counter Lifecycle

A technician clears DTCs at the dealership. The MEC (Malfunction Elimination Confirmation) counter starts at 254. After each complete ignition cycle (OFF → RUN/PROPULSION → OFF), SUM_DIAG decrements the MEC counter and persists it to NvM. When MEC reaches 0, manufacturer-level diagnostic access is restricted. The counter value is broadcast to SUM_SSC, SUM_SOH, and SUM_SSFM every cycle so that security and fault management modules can adjust their behavior.

2. UDS Session Control

A diagnostic tester requests an Extended Diagnostic Session (0x03) via UDS Service 0x10. SUM_DIAG validates the request, stores the tester source address, and manages communication state. If the tester later requests a Programming Session (0x02), SUM_DIAG checks four preconditions: DTC setting disabled, normal messages disabled, vehicle power mode OFF, and either OTA authorization or valid security access. If any check fails, the session switch is denied with a negative response.

3. ECU Reset Safety Check

A UDS reset request (Service 0x11) arrives while the ECU is in an Extended Diagnostic Session. SUM_DIAG checks whether the vehicle is in a safe state — verifying power mode through SUSD and ensuring no active NvM writes are in progress. If preconditions pass, SUM_DIAG notifies SUM_SOH of the diagnostic reset event (incrementing the SOH reset counter) before permitting the reset to proceed through SUSD coordination.

4. Communication Control During Manufacturing

On the assembly line, a calibration tool sends ControlDTCSetting (Service 0x85) to disable DTC monitoring, followed by CommunicationControl (Service 0x28) to disable normal CAN/LIN/Ethernet message transmission. SUM_DIAG manages the enable/disable state for each of the three communication channels independently. When the diagnostic session ends (returns to Default Session), SUM_DIAG automatically re-enables all communication channels and restores DTC monitoring, ensuring the vehicle leaves the production line in a fully operational state.

3. Module Lifecycle

State Machine

How initialization works

Why two-phase init? The ECU boot sequence is complex. SUM_DIAG cannot start operating until other modules (NvM, DCM, Com, BswM) are fully initialized. The PermitExecution mechanism lets SUM_SUSD signal "all dependencies ready."
  1. Phase 1 — RE_DIAG_Init() (called periodically at 1s until done):
    • Runs exactly once (guarded by static flag)
    • Sets permit_execution = FALSE
    • Sets MEC cycle state to DIAG_START_OF_CYCLE
    • Reads stored OTA_PSF value from NvM
    • Sets DEM enable condition based on OTA_PSF
    • Writes initial MEC value to SSC, SOH, and SSFM output ports
  2. Phase 2 — Runnable_DIAG_Main() (called every 100ms):
    • Reads PermitExecution from SUSD
    • Checks if all required bits are set (mask = 254, i.e., bits 1-7)
    • When all bits set: calls initializeForRun() which initializes output ports, sets ECU address, and enables full operation
Scenario Walkthrough — SUM_DIAG Initialization and State Machine Transitions
Scenario
The ECU is powered on during a cold start. SUM_DIAG must complete its two-phase initialization, transition from INIT to RUN state, then later handle a shutdown request — all while coordinating with SUM_SUSD via the PermitExecution handshake.
Implementation Example — Sum_Diag_MainCyclicFunction (from SUM_Diag.c) 
/* Main cyclic function - FSM for INIT/RUN/SHUTDOWN states */
FUNC(void, SUM_DIAG_CODE) Runnable_DIAG_Main(void)
{
    uint8 permitExec;

    /* Read PermitExecution from SUSD */
    (void)Rte_Read_RP_SUSD_DIAG_PermitExecution(&permitExec);

    switch (DiagState)
    {
        case DIAG_STATE_INIT:
            if ((permitExec | DIAG_PERMIT_MASK) == 0xFFu)
            {
                Sum_Diag_InitializeForRun();
                DiagState = DIAG_STATE_RUN;
            }
            break;

        case DIAG_STATE_RUN:
            Sum_Diag_EvaluateMecCycle();
            Sum_Diag_EvaluateShutdownPermission();
            break;

        case DIAG_STATE_SHUTDOWN:
            /* Write shutdown permission to SUSD */
            (void)Rte_Write_PP_DIAG_SUSD_ShutdownPermission(
                DIAG_ENABLE_SHUTDOWN);
            break;

        default:
            break;
    }
}

4. Feature Deep-Dives

4.1 Manufacturer Enable Counter (MEC)

What is MEC?

The MEC is a countdown counter (initial value: 254) that tracks how many ignition cycles remain for manufacturer diagnostic access. Each complete power cycle (OFF → RUN/PROPULSION → OFF) decrements MEC by 1. When MEC reaches 0, certain manufacturer-level diagnostic capabilities are disabled.

Why does MEC exist?

Regulatory and OEM requirements mandate that manufacturer-level diagnostic access should be time-limited after vehicle delivery. The MEC ensures that after a certain number of ignition cycles, the ECU transitions from "factory mode" to "customer mode."

How does MEC work?

Key detail: Battery voltage is checked before NvM writes. If voltage is abnormal (DisableNVMWrite flag set), the write is skipped to prevent data corruption.

Where is MEC stored?

  • RAM Mirror: MEC variable in SUM_Diag_Cfg.c (initial = 254)
  • NvM Block: Referenced by DIAG_MEC_NvMRef configuration parameter
  • Pointer: MEC_RamBlockPtr provides NvM access to the RAM mirror

Who reads MEC?

MEC value is broadcast to three consumers via RTE ports:

  • PP_DIAG_SSC_GetMEC → SUM_SSC (Security Services)
  • PP_DIAG_SOH_GetMEC → SUM_SOH (State of Health)
  • PP_DIAG_SSFM_GetMEC → SUM_SSFM (Signal Status Fault Manager)
Scenario Walkthrough — MEC Counter Decrement Over Ignition Cycles
Scenario
A newly manufactured ECU is installed in a vehicle. The MEC counter starts at 254. The vehicle goes through its first complete ignition cycle on the production line, then subsequent cycles during dealer prep and customer use. SUM_DIAG must track and persist the countdown accurately.
Implementation Example — Sum_Diag_EvaluateMecCycle (from SUM_Diag.c) 
/* Evaluate MEC cycle state transitions based on vehicle power mode */
static FUNC(void, SUM_DIAG_CODE) Sum_Diag_EvaluateMecCycle(void)
{
    uint8 currentPowerMode;

    /* Read current vehicle power mode from SUSD */
    (void)Rte_Read_RP_SUSD_DIAG_VehiclePowerMode(&currentPowerMode);

    switch (MecCycleState)
    {
        case DIAG_START_OF_CYCLE:
            if (currentPowerMode == POWER_MODE_RUN)
            {
                MecCycleState = DIAG_PROPULSION_REACHED;
            }
            break;

        case DIAG_PROPULSION_REACHED:
            if (currentPowerMode == POWER_MODE_OFF)
            {
                MecCycleState = DIAG_END_OF_CYCLE;
                /* Decrement MEC if still above zero */
                if (MEC > 0u)
                {
                    MEC--;
                    Sum_Diag_ProcessMecWrite();
                }
            }
            break;

        default:
            /* DIAG_END_OF_CYCLE: wait for next init */
            break;
    }
}

MEC Counter Storage via HSM

What: The MEC (Message Encryption Counter) is stored securely in the HSM (Hardware Security Module) rather than in standard NvM. This provides tamper-resistant storage for the counter used in message authentication.

Why: Storing the MEC in NvM would allow an attacker to roll back the counter by restoring a previous NvM image, enabling replay attacks. HSM storage prevents counter rollback.

How: DIAG interfaces with the HSM via the CSM (Crypto Service Manager) to read and increment the MEC. The MEC is incremented on each successful key provisioning operation. During startup, DIAG reads the current MEC value from HSM and compares it against the expected value stored in SSC’s EKPS flags.

MEC Lifecycle States:
  • MEC_INIT — MEC value being read from HSM during startup
  • MEC_VALID — MEC value successfully read and validated against EKPS
  • MEC_INCREMENT_PENDING — Key provisioning complete, MEC increment requested to HSM
  • MEC_ERROR — HSM read/write failure or MEC/EKPS mismatch detected

4.2 Diagnostic Session Control

What is it?

UDS Service 0x10 (DiagnosticSessionControl) allows a tester to switch the ECU between diagnostic sessions: Default (0x01), Programming (0x02), and Extended (0x03).

Why does SUM_DIAG handle it?

Not all session switches should be allowed at any time. Switching to Programming Session (0x02) is particularly dangerous because it prepares the ECU for reflashing. SUM_DIAG enforces strict preconditions.

Indication Phase (precondition check)

Confirmation Phase (after DCM sends the response)

Why these preconditions for Programming Session?

  • DTC setting disabled: Prevents new DTCs from being logged during reflash
  • Normal msg disabled: Isolates the ECU from normal network traffic during programming
  • Power mode OFF: Vehicle must be stationary; engine not running
  • OTA_PSF or Security: Either OTA has been authorized, or the tester has proper security access
Scenario Walkthrough — Programming Session Request Sequence
Scenario
A diagnostic tester at a dealership needs to reflash the ECU with new calibration data. The tester must follow a strict multi-step sequence to enter Programming Session. If any step is skipped, SUM_DIAG blocks the transition.
Implementation Example — Sum_Diag_SessionControlIndication (from SUM_Diag.c) 
/* Validate preconditions for DiagnosticSessionControl (0x10) */
static FUNC(Std_ReturnType, SUM_DIAG_CODE) Sum_Diag_SessionControlIndication(
    uint8 SID,
    uint8 SubFunction,
    uint8 ConnectionId)
{
    Std_ReturnType retVal = E_OK;

    if (SubFunction == 0x02u)  /* Programming Session */
    {
        boolean dtcDisabled  = Rte_IrvIRead_IR_DIAG_ControlDTCsetting();
        boolean commDisabled = Sum_Diag_IsCommDisabled();
        uint8   powerMode    = Sum_Diag_GetPowerMode();
        boolean otaOrSec     = (OTA_PSF == TRUE) ||
                               (Sum_Diag_SecurityVerified() == TRUE);

        if ((dtcDisabled != TRUE) || (commDisabled != TRUE) ||
            (powerMode != POWER_MODE_OFF) || (otaOrSec != TRUE))
        {
            retVal = DCM_E_CONDITIONSNOTCORRECT;
        }
        else
        {
            /* Notify SOH of diagnostic session request */
            (void)Rte_Write_PP_DIAG_SOH_DiagSessionRequest(TRUE);
            TesterSourceAddress = ConnectionId;
        }
    }
    return retVal;
}
Diag_SetProgConditions Callout: Before entering programming session, the DCM calls Diag_SetProgConditions() to store the current diagnostic session state (tester address, security level, active DID locks) to a persistent location. This data is restored after ECU reset to maintain session continuity. The callout must complete within the P2*Server timing to avoid a negative response.

4.3 ECU Reset

What is it?

UDS Service 0x11 allows a tester to command the ECU to perform a reset (hard reset, key-off-on, soft reset).

Why does SUM_DIAG validate it?

Resetting an ECU while the vehicle is in motion could cause loss of critical functions. SUM_DIAG ensures the vehicle is in a safe state.

Scenario Walkthrough — ECU Reset During Active Diagnostic Session
Scenario
After completing a software reflash, the diagnostic tester sends a hard reset command (Service 0x11, SubFunction 0x01) to restart the ECU with the new software. SUM_DIAG must verify it is safe to reset before allowing the operation.
Implementation Example — Sum_Diag_EcuResetIndication (from SUM_Diag.c) 
/* Validate preconditions for ECU Reset (Service 0x11) */
static FUNC(Std_ReturnType, SUM_DIAG_CODE) Sum_Diag_EcuResetIndication(
    uint8 SID,
    uint8 SubFunction)
{
    Std_ReturnType retVal = E_OK;
    uint8 powerMode;

    /* Read current vehicle power mode */
    (void)Rte_Read_RP_SUSD_DIAG_VehiclePowerMode(&powerMode);

    if (powerMode != POWER_MODE_OFF)
    {
        /* Vehicle not in safe state for reset */
        retVal = DCM_E_CONDITIONSNOTCORRECT;
    }
    else
    {
        /* Notify SOH about diagnostic reset event */
        (void)Rte_Write_PP_DIAG_SOH_ResetRequest(TRUE);
    }

    return retVal;
}
ECU Reset — Shutdown Bypass: When an ECU hard reset is requested via UDS service 0x11 (subfunction 0x01), DIAG sets a flag that bypasses the normal SUSD shutdown coordination sequence. This is necessary because the tester expects a rapid reset (within P2*Server time). The normal shutdown handshake with SPM/SUSD would exceed this timing. The bypass flag is checked by SUSD to skip the orderly shutdown and proceed directly to reset.

Implementation Example — Sum_Diag_CommunicationControlIndication (from SUM_Diag.c) 
/* Process CommunicationControl (Service 0x28) indication */
static FUNC(Std_ReturnType, SUM_DIAG_CODE) Sum_Diag_CommunicationControlIndication(
    uint8 SubFunction,
    uint8 CommChannel,
    uint8 ConnectionId)
{
    Std_ReturnType retVal = E_OK;

    if (CommChannel < DIAG_NUM_COMM_CHANNELS)
    {
        switch (SubFunction)
        {
            case 0x00u:  /* Enable RxTx */
                CommChannelState[CommChannel].NormalMsgTx = COMM_ENABLE;
                break;

            case 0x03u:  /* Disable RxTx */
                CommChannelState[CommChannel].NormalMsgTx = COMM_DISABLE;
                CommChannelState[CommChannel].TesterAddr  = ConnectionId;
                break;

            default:
                /* No action for other sub-functions */
                break;
        }

        /* Write updated state to SSM via RTE */
        (void)Rte_Write_PP_DIAG_SSM_CommMode(
            CommChannel, CommChannelState[CommChannel].NormalMsgTx);
    }

    return retVal;
}

4.5 Read Memory by Address (RMBA)

What is it?

UDS Service 0x23 allows a tester to read raw memory from the ECU. SUM_DIAG delegates security verification to SUM_SSC.

Conditional compilation: Only compiled when RMBA_SERVICE_SUPPORT == STD_ON.

4.6 Dynamically Define Data Identifier (DDDI)

What is it?

UDS Service 0x2C (SubFunction 0x02) lets a tester create custom DIDs mapping to memory addresses. DDDI can contain multiple memory blocks in a single request. All blocks must pass security check.

4.7 OTA Programming Start Flag (OTA_PSF)

What is OTA_PSF?

The OTA_PSF indicates whether the vehicle has been authorized for remote (OTA) programming. When set to TRUE, certain DTC enable conditions are modified to prepare the ECU for OTA updates.

4.8 Shutdown Permission

What is it?

SUM_DIAG signals to SUM_SUSD whether the ECU is allowed to shut down. This prevents the ECU from powering off while a diagnostic operation is in progress.

Why the rolling count? It serves as an aliveness mechanism. SUM_SUSD detects if SUM_DIAG has crashed by checking whether the count value changes. A stuck value indicates a problem.
Scenario Walkthrough — Shutdown Permission During Active Diagnostics
Scenario
The vehicle initiates a shutdown sequence while a diagnostic tester is still connected and performing an extended diagnostic session. SUM_DIAG must delay the shutdown until the diagnostic operation is safely complete to prevent data corruption.
Implementation Example — Sum_Diag_EvaluateShutdownPermission (from SUM_Diag.c) 
/* Evaluate whether SUM_DIAG permits ECU shutdown */
static FUNC(void, SUM_DIAG_CODE) Sum_Diag_EvaluateShutdownPermission(void)
{
    uint8 shutdownValue;

    if ((ActiveRequestCount == 0u) &&
        (CurrentSession == DCM_DEFAULT_SESSION))
    {
        /* No active requests and default session → safe to shut down */
        shutdownValue = DIAG_ENABLE_SHUTDOWN;  /* 0xFF */
    }
    else
    {
        /* Still busy — send rolling count as aliveness signal */
        ShutdownRollingCount++;
        if (ShutdownRollingCount == DIAG_ENABLE_SHUTDOWN)
        {
            ShutdownRollingCount = 0u;  /* Skip 0xFF to avoid false "ready" */
        }
        shutdownValue = ShutdownRollingCount;
    }

    /* Write shutdown permission to SUSD */
    (void)Rte_Write_PP_DIAG_SUSD_ShutdownPermission(shutdownValue);
}

4.9 Protocol Pre-emption

What is it?

Controls which testers can access which diagnostic protocols based on vehicle state, via the DCM callout SUM_DIAG_DcmGetRxPermission().

DcmGetRxPermission Callout: The Dcm_GetRxPermission() callout is invoked for every incoming diagnostic request. It allows SUM_DIAG to filter or reject requests based on the current system state (e.g., reject requests during shutdown, restrict certain services during driving). Return E_OK to allow processing or E_NOT_OK to silently drop the request.
Scenario Walkthrough — OBD Tester Blocked When Vehicle is OFF
Scenario
A third-party OBD scan tool (connected via OBD-II port) tries to access the ECU while the vehicle power mode is OFF. SUM_DIAG blocks the request to prevent unauthorized diagnostic access when the vehicle is not in an active state.

4.10 DID Handling (F1A0 and F1B0)

DID F1A0 — Manufacturer's Enable Counter

  • ReadData(): Returns current MEC value from RAM mirror block
  • WriteData(): Writes new MEC value to NvM (with pending state machine)
  • ConditionCheckRead(): Simple pass-through (always returns E_OK)

DID F1B0 — Diagnostic Address Data

  • Runnable_DID_F1B0_ReadData(): Returns the configured ECU address (DIAG_ECUADDRESS = 16)
  • Single byte response

12. Common Debugging Scenarios

Scenario 1: ECU won't enter Programming Session

Symptom: Tester sends DiagnosticSessionControl (0x10, sub 0x02) and receives NRC 0x22.

Checklist (all must be true):

  1. Is IR_DIAG_ControlDTCsetting == TRUE? → Was ControlDTCSetting (0x85) sent?
  2. Is IR_Normal_msg_transmission == DISABLED? → Was CommunicationControl (0x28, sub 0x03) sent?
  3. Is vehicle power mode == OFF? → Is ignition off?
  4. Is OTA_PSF == TRUE OR security level != 0x03?

Correct tester sequence:

Scenario 2: MEC not decrementing

Symptom: MEC value stays the same across ignition cycles.

  1. Is the full cycle completing? (OFF → RUN/PROPULSION → OFF)
  2. Is SUM_DIAG_MEC_Cycle_States transitioning through all 3 states?
  3. Is ProcessMECWrite succeeding? Check NvM write status.
  4. Is battery voltage normal? (DisableNVMWrite flag = FALSE?)

Scenario 3: ECU not shutting down

Symptom: SUSD never receives shutdown permission (0xFF).

  1. Is IR_NumberActiveDiagnosticRequest == 0?
  2. Is current session == DEFAULT_SESSION?
  3. Is Runnable_Shutdown_Permission running?

Scenario 4: NvM write failures

Symptom: MEC or OTA_PSF changes lost after power cycle.

  1. Is DisableNVMWrite flag TRUE? (battery issue)
  2. Is NvM_GetErrorStatus returning NVM_REQ_OK?
  3. Is NvM block configured as shutdown block?
  4. Check write state — stuck in PENDING?

Scenario 5: Protocol pre-emption blocking legitimate requests

Symptom: OBD tester cannot communicate with ECU.

  1. Is tester address 0x0E00? (legislated tester)
  2. Is protocol OBD_ON_CAN or OBD_ON_IP?
  3. Is vehicle power mode OFF?
  4. All three must be true for blocking. If vehicle is running, 0x0E00 should be allowed.

How DIAG ParamDef works with the module
DiagConfigSet defines ComM channels for bus state monitoring. DiagGeneral controls ECU address, MEC (HSM/NvM), feature flags (RMBA, DDDI, E0CC), and 6 runnable periodicities. References connect to DCM data, NvM blocks, and COM signals for OTA/remote programming.
