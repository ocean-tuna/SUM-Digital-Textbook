TCS — Timing Client Service

Comprehensive Training Documentation
RTA-SUM TCS Version 8.0.1_Pr11 AUTOSAR Classic (RTA-CAR 12.0) GM SDV 2.0

1. Introduction: What is TCS?

TCS (Timing Client Service) is a software module in the AUTOSAR application layer of GM's SDV 2.0 automotive ECUs. It is part of the RTA-SUM (Startup Manager) product family developed by ETAS.

In simple terms, TCS is the ECU's "clock keeper." It:

  • Receives the vehicle's global time from a master clock over CAN/Ethernet
  • Keeps a local copy of that time ticking even when updates stop
  • Saves the time to non-volatile memory so it survives power cycles
  • Makes the time available to diagnostics (for fault timestamps and UDS reads)
Analogy Think of TCS like a wristwatch that syncs to an atomic clock signal: it gets the authoritative time when available, but keeps ticking on its own in between updates.

2. Why Does TCS Exist?

The Problem

Modern vehicles need accurate timestamps for:

NeedWhy
Fault diagnosisWhen a DTC (Diagnostic Trouble Code) is logged, the technician needs to know when it happened. The Dem needs a clock source.
Regulatory complianceOBD-II and GM-specific requirements demand timestamped fault records (Extended Data Records).
Service schedulingDID 0xF129 ("Total Vehicle Time") tells the service tool how long the vehicle has been running, enabling time-based maintenance.
Cross-ECU correlationMultiple ECUs must agree on "what time is it" so that fault events from different ECUs can be correlated.

The Solution

A single Time Leader ECU in the vehicle broadcasts a TimeSyncMessage on the communication bus. Every ECU that needs time runs a TCS instance that:

  1. Listens for the master signal
  2. Synchronizes its local clock
  3. Keeps the clock running between broadcasts
  4. Persists the last known time across power cycles
Key Benefit Without TCS, every ECU would need its own RTC (Real-Time Clock) hardware, which is expensive and still wouldn't solve the cross-ECU synchronization problem.

Real-World Scenarios

The following scenarios illustrate how TCS operates in typical vehicle situations. Each one demonstrates a different aspect of the module's behavior.

Scenario 1 — Time Synchronization from Global Master
Scenario
The gateway ECU receives a GPS-based time sync message from the global time master. TCS unpacks the 48-bit nanosecond timestamp, applies rate/offset corrections, and distributes the corrected time to local time domains. 
/*
 * TIMELINE: Time Synchronization from Global Master
 *
 * T=0.0s  : Gateway ECU powers on; TCS_Init loads last-known time from NvM (stale value)
 * T=0.5s  : SUSD grants PermitExecution → TCS transitions to TCS_RUN_MODE
 * T=0.6s  : First TimeSyncMessage arrives on CAN bus from Time Leader ECU
 * T=0.6s  : MasterClockPolling detects new value, overwrites local clock, resets SubCounter=0
 * T=0.7s  : TimeManagement outputs corrected time via TCS_SWC_Clock port to all consumers
 * T=0.7s  : NvM write triggered → updated time persisted to flash
 * T=1.6s  : Next TimeSyncMessage arrives → cycle repeats with fresh master value
 *
 * KEY POINT: TCS always trusts the master clock when available; local timekeeping
 *            only bridges the gap between master updates.
 */
Scenario 2 — Time Domain Handoff (Master Failover)
Scenario
The primary time master fails (e.g., Time Leader ECU enters a fault state). TCS detects the timeout when no new TimeSyncMessage arrives. The secondary master takes over broadcasting. TCS recalibrates offset/rate corrections to maintain monotonic time across the vehicle. 
/*
 * TIMELINE: Time Domain Handoff
 *
 * T=0.0s  : Primary Time Leader broadcasting TimeSyncMessage every 100ms; TCS in sync
 * T=5.0s  : Primary Time Leader stops broadcasting (fault condition)
 * T=5.1s  : MasterClockPolling reads same value as last cycle → no update, SubCounter keeps incrementing
 * T=5.2s  : TimeManagement increments local clock autonomously via precision counter
 * T=6.0s  : Secondary Time Leader begins broadcasting; MasterClockPolling detects new value
 * T=6.0s  : TCS overwrites local clock with secondary master's value, SubCounter resets to 0
 * T=6.1s  : Corrected time distributed; NvM updated with new authoritative value
 *
 * KEY POINT: TCS's local timekeeping ensures no time gap during the handoff period.
 *            The vehicle never loses its sense of "what time is it."
 */
Scenario 3 — Cross-Domain Time Correlation
Scenario
An ADAS ECU needs to correlate camera timestamps (Ethernet time domain) with radar timestamps (CAN time domain). TCS provides synchronized time bases so both sensor inputs can be temporally aligned for sensor fusion algorithms. 
/*
 * TIMELINE: Cross-Domain Time Correlation
 *
 * T=0.0s  : TCS on ADAS ECU running in TCS_RUN_MODE, synced to global master
 * T=0.1s  : Camera SW-C reads TCS_SWC_Clock = 50000 (5000.0s since epoch)
 * T=0.1s  : Camera captures frame, tags it with timestamp 50000
 * T=0.1s  : Radar SW-C reads TCS_SWC_Clock = 50000 (same synchronized value)
 * T=0.1s  : Radar returns detection, tagged with timestamp 50000
 * T=0.2s  : Fusion algorithm correlates camera + radar data using matching timestamps
 * T=0.2s  : Objects detected by both sensors are merged into a single world model
 *
 * KEY POINT: Without TCS providing a common clock, camera and radar timestamps
 *            would drift apart, making sensor fusion unreliable.
 */
Scenario 4 — Time Jump Detection After ECU Reset
Scenario
After an ECU reset, the local oscillator has drifted significantly. TCS detects a large time offset versus the master when the first TimeSyncMessage arrives, applies the jump correction by overwriting the local clock, and notifies consumers via the TCS_SWC_Clock port update. 
/*
 * TIMELINE: Time Jump Detection After ECU Reset
 *
 * T=0.0s  : ECU resets; TCS_Init loads NvM value = 40000 (stale, from before reset)
 * T=0.3s  : SUSD grants PermitExecution → TCS enters TCS_RUN_MODE
 * T=0.4s  : TimeManagement outputs stale time (40000) via TCS_SWC_Clock
 * T=0.5s  : First TimeSyncMessage arrives: master value = 45000 (actual current time)
 * T=0.5s  : MasterClockPolling detects large jump (45000 vs 40000 = +5000 ticks = ~500s)
 * T=0.5s  : Local clock overwritten to 45000; SubCounter reset to 0; NvM write triggered
 * T=0.6s  : Consumers now receive corrected time (45000) → Dem timestamps are accurate
 *
 * KEY POINT: TCS unconditionally trusts the master clock value. Any jump—large or
 *            small—is applied immediately, ensuring rapid re-synchronization.
 */

5. Core Concepts

5.1 TimeSyncMessage

The TimeSyncMessage is the master time value broadcast by the Time Leader ECU across the vehicle network.

  • A counter value representing elapsed time since an epoch
  • Each increment = 100 milliseconds of real time
  • Uses 36 bits of a 5-byte (40-bit) field, giving a range of ~217 years

Scenario
A TimeSyncMessage arrives on the SOME/IP Ethernet bus carrying a 5-byte big-endian timestamp. TCS must unpack this byte array into the internal uint64 format for arithmetic operations, then split it into the high/low structure for efficient storage and overflow handling.
Implementation Example — Sum_Tcs_Prv_byteArray_to_uint64 (from SUM_TCS.c) 
/* Converts a 5-byte big-endian TimeSyncMessage array into a uint64 value.
 * Byte 0 is the most significant byte (masked to lower 4 bits).
 * Used during SOME/IP reception and NvM restore on startup. */
static FUNC(uint64, SUM_TCS_CODE) Sum_Tcs_Prv_byteArray_to_uint64(
    const uint8 byteArray[])
{
    uint64 result = 0U;
    uint8  idx;

    /* Assemble 5 bytes into uint64, big-endian order */
    for (idx = 0U; idx < 5U; idx++)
    {
        result = (result << 8U) | (uint64)byteArray[idx];
    }

    /* Mask high byte to 4 bits (36-bit value range) */
    result &= 0x0FFFFFFFFFULL;

    return result;
}

5.2 Master Clock vs Local Clock

TCS maintains two distinct time concepts:

Why two? The master clock signal arrives periodically (e.g., every 100ms), but:

  • The signal could be delayed or temporarily unavailable
  • The ECU needs time between reception events
  • TCS provides sub-master-cycle precision via the local clock

How they interact:

  1. MasterClockPolling reads the latest TimeSyncMessage from Com
  2. If the value has changed since last read, it overwrites the local clock and resets SubCounter to 0
  3. Between master updates, TimeManagement increments the local clock based on the precision counter
  4. SubCounter tracks how many cycles have elapsed since the last master sync

5.3 Precision Counter

The precision counter controls how granularly the local clock increments between master clock updates.

Formula

precisionCounter = SumTCSGlobalTimePrecision / TimeManagementPeriodicity

Default Configuration

SumTCSGlobalTimePrecision  = 200 ms
TimeManagementPeriodicity  = 100 ms
=> precisionCounter = 200 / 100 = 2

Worked Example

Why the precision counter? It ensures the local clock doesn't increment faster than the TimeSyncMessage resolution (100ms per tick). With default config, TCS increments the local clock by 2 (= 200ms worth of ticks) every 200ms, matching real-time passage.
Scenario Walkthrough — Compensating for Oscillator Drift Between ECUs
Scenario
Two ECUs on the same CAN bus have slightly different oscillator frequencies. The Time Leader ECU increments its clock at exactly 100ms intervals, but the local ECU's oscillator runs 0.1% fast. The precision counter mechanism ensures TCS increments the local clock at the correct rate, matching the master's tick rate rather than the local oscillator rate.
Implementation Example — Sum_Tcs_Prv_CalculatePrecisionCounter (from SUM_TCS.c) 
/* Calculates the precision counter value that determines how often
 * the local clock increments. This effectively controls the rate at which
 * TCS ticks, ensuring it matches the master clock's resolution.
 * Called once during TCS_Init. */
static FUNC(uint16, SUM_TCS_CODE) Sum_Tcs_Prv_CalculatePrecisionCounter(void)
{
    uint16 precision;
    uint16 globalTimePrecision_ms;
    uint16 timeMgmtPeriodicity_ms;

    /* Read configured values (e.g., 200ms and 100ms) */
    globalTimePrecision_ms = SumTCS_Cfg_GlobalTimePrecision;
    timeMgmtPeriodicity_ms = SumTCS_Cfg_TimeManagementPeriodicity;

    /* Guard against divide-by-zero */
    if (timeMgmtPeriodicity_ms == 0U)
    {
        precision = 1U;
    }
    else
    {
        /* precision = 200 / 100 = 2 (default) */
        precision = globalTimePrecision_ms / timeMgmtPeriodicity_ms;
    }

    return precision;
}

5.5 Execution FSM (Finite State Machine)

The Execution FSM controls when TCS is allowed to operate. It coordinates with SUM_SUSD (Startup/Shutdown Coordinator).

Key signals:

  • PermitExecution (uint8 from SUSD): Bitmask. TCS checks (execStatus | PermitExecutionMask) == 0xFF
    • Bit 0 = Wakeup Active
    • Bit 6 = ECU Reset Request (checked via TCS_RESETREQUEST_MASK = 0xBF)
  • ShutdownPermission (uint8 to SUSD):
    • 0..3 = alive counter (NvM write in progress, not ready)
    • 255 = TCS_ENABLE_SHUTDOWN (ready to power off)
Why the FSM? Without it, TCS might try to write NvM during shutdown when the flash controller is already powering down, causing data corruption. The FSM ensures TCS only operates after SUSD grants permission, holds the ECU alive until NvM writes complete, and only then votes "safe to shutdown."
Important: 4-State Architecture
The TCS module operates with a 4-state FSM, not 3 states. The complete state set is:
  • INIT_MODE — Initial state after power-on. TCS reads NvM data and initializes internal structures.
  • RUN_MODE — Normal operational state. TCS processes telematics requests and manages communication channels.
  • MEMORY_MODE — Pre-shutdown state where TCS writes all volatile data to NvM. TCS stops accepting new requests and flushes pending operations. Transition to SHUTDOWN_MODE occurs only after NvM writes complete or timeout.
  • SHUTDOWN_MODE — Final state. TCS releases all resources and signals shutdown readiness to SUSD.
The MEMORY_MODE is critical for data integrity — skipping it (e.g., due to power loss) may result in counter desynchronization on next startup.

6.1 TCS_Init — Initialization

What: One-time initialization of the TCS module.

When: Called once at startup, either by BswM action list (default) or by periodic Runnable_TCS_Init (if TcsGenerateInitRunnable=TRUE).

How it works

Key detail: TCS_Init does NOT start the clock ticking — it just loads the saved time. The clock starts running only after Runnable_TCS_PermitExecutionShutdown transitions to TCS_RUN_MODE.

Source: SUM_TCS.c (generated from SUM_TCS_c.xpt)

6.2 Runnable_TCS_MasterClockPolling

What: Polls the master clock signal and synchronizes the local clock.

When: Periodic, every MasterClockPollingPeriodicity ms (default: 100ms).

Precondition: permit_execution != FALSE (set by PermitExecutionShutdown FSM).

Step-by-step logic

Why compare with lastReadTime? The Com layer may return the same value on consecutive reads if no new message arrived. TCS only acts on actual changes to avoid unnecessary NvM writes and SubCounter resets.
Scenario Walkthrough — Correcting a Large Time Offset After ECU Startup
Scenario
An ECU was powered off for 3 days. On startup, TCS loads the stale NvM time (3 days old). When the first TimeSyncMessage arrives from the Time Leader, MasterClockPolling detects that the master value is significantly ahead of the local clock. It overwrites the local clock with the master value, effectively applying a large offset correction in a single step.
Implementation Example — Sum_Tcs_Prv_ApplyOffsetCorrection (from SUM_TCS.c) 
/* Applies offset correction by comparing the received master clock value
 * against the last known value. If different, the local clock is overwritten
 * with the authoritative master value, and SubCounter is reset.
 * Called from Runnable_TCS_MasterClockPolling when a new signal is available. */
static FUNC(void, SUM_TCS_CODE) Sum_Tcs_Prv_ApplyOffsetCorrection(
    uint64 masterClockValue)
{
    uint64 lastReadTime;
    uint64 localClock;

    /* Read the previously stored master value */
    lastReadTime = Rte_IrvRead_Runnable_TCS_MasterClockPolling_EA_lastReadTime();

    /* Only act if the master has actually changed */
    if (masterClockValue != lastReadTime)
    {
        /* Overwrite local clock with authoritative master value */
        Rte_IrvWrite_Runnable_TCS_MasterClockPolling_EA_Localtime_Clock(masterClockValue);

        /* Reset SubCounter so TimeManagement starts fresh */
        Rte_IrvWrite_Runnable_TCS_MasterClockPolling_EA_SubCounter(0U);

        /* Remember this value for next comparison */
        Rte_IrvWrite_Runnable_TCS_MasterClockPolling_EA_lastReadTime(masterClockValue);

        /* Convert to byte array and persist to NvM */
        Sum_Tcs_Prv_uint64_to_byteArray(masterClockValue, SumTCSInitValue);
        Sum_Tcs_Prv_WriteNvM();
    }
}

6.3 Runnable_TCS_TimeManagement

What: Keeps the local clock ticking between master clock updates.

When: Periodic, every TimeManagementPeriodicity ms (default: 100ms).

Precondition: permit_execution != FALSE.

Step-by-step logic

The Increment Algorithm

Scenario Walkthrough — Distributing Corrected Time to Consumers
Scenario
TCS has been running for several seconds without a new master clock update. The TimeManagement runnable must increment the local clock at the correct rate (governed by the precision counter) and distribute the updated time to all consumers via the TCS_SWC_Clock port. Dem and other SW-Cs rely on this output for accurate timestamps.
Implementation Example — Sum_Tcs_Prv_increment_current_time (from SUM_TCS.c) 
/* Increments the local clock by the precision counter value.
 * Handles 32-bit overflow of the low word by carrying into the high byte.
 * The high byte is masked to 4 bits (0x0F) to maintain the 36-bit range.
 * Called from Runnable_TCS_TimeManagement when SubCounter % precisionCounter == 0. */
static FUNC(uint64, SUM_TCS_CODE) Sum_Tcs_Prv_increment_current_time(
    uint64 currentTime,
    uint16 precisionCounter)
{
    uint32 low;
    uint32 low_before;
    uint8  high;

    /* Split uint64 into high byte and low dword */
    low  = (uint32)(currentTime & 0xFFFFFFFFUL);
    high = (uint8)(currentTime >> 32U);

    /* Save low before increment for overflow detection */
    low_before = low;
    low += (uint32)precisionCounter;

    /* Check for 32-bit overflow (wrap-around) */
    if (low < low_before)
    {
        high++;
        high &= 0x0FU;  /* Keep within 36-bit range */
    }

    /* Reassemble uint64 */
    return ((uint64)high << 32U) | (uint64)low;
}

6.4 Runnable_TCS_PermitExecutionShutdown

What: Manages the execution state machine and NvM shutdown coordination.

When: Periodic (same period as TimeManagement, default 100ms).

This is the most complex runnable. It has three states:

State: TCS_INIT_MODE (Startup)

Why the bitmask? PermitExecutionMask (default 0xFE) masks out bit 0 (Wakeup). The check (execStatus | 0xFE) == 0xFF effectively tests whether bit 0 of execStatus is set (Wakeup Active).

State: TCS_RUN_MODE (Normal Operation)

State: TCS_SHUTDOWN (Waiting for NvM)

Alive Counter During shutdown, SUSD monitors all modules. If a module stops responding (counter frozen), SUSD can detect it's hung. The modulo-4 alive counter proves TCS is still actively processing.
Scenario Walkthrough — Complete Time Sync Cycle from Reception to Distribution
Scenario
A full time synchronization cycle: the ECU starts up, PermitExecutionShutdown manages the FSM transitions, MasterClockPolling receives a new master value, TimeManagement distributes it, and eventually the ECU shuts down with NvM persistence. This shows how PermitExecutionShutdown orchestrates the entire TCS lifecycle.
Implementation Example — Runnable_TCS_PermitExecutionShutdown (from SUM_TCS.c) 
/* Main cyclic function that orchestrates the TCS execution state machine.
 * Manages transitions between INIT, RUN, and SHUTDOWN modes.
 * Gates all other TCS runnables via the permit_execution flag.
 * Called periodically (default 100ms) by the RTE. */
static FUNC(void, SUM_TCS_CODE) Runnable_TCS_PermitExecutionShutdown(void)
{
    uint8 execStatus;
    boolean wakeupActive;

    /* Read PermitExecution bitmask from SUSD */
    (void)Rte_Read_RP_PermitExecution_DE_PermitExecution(&execStatus);
    wakeupActive = ((execStatus | SumTCS_Cfg_PermitExecutionMask) == 0xFFU);

    switch (Sum_TCS_executionState)
    {
        case TCS_INIT_MODE:
            if (wakeupActive != FALSE)
            {
                Sum_TCS_executionState = TCS_RUN_MODE;
                Sum_TCS_permit_execution = TRUE;
            }
            break;

        case TCS_RUN_MODE:
            if (wakeupActive == FALSE)
            {
                /* Shutdown requested — initiate NvM write */
                Sum_Tcs_Prv_WriteNvM();
                Sum_TCS_executionState = TCS_SHUTDOWN;
            }
            break;

        case TCS_SHUTDOWN:
            /* Wait for NvM write to complete, then allow shutdown */
            if (Sum_TCS_LastRequestResult != NVM_REQ_PENDING)
            {
                Sum_TCS_permit_execution = FALSE;
                Rte_Write_PP_ShutdownPermission_DE_ShutdownPermission(TCS_ENABLE_SHUTDOWN);
            }
            else
            {
                /* Alive counter: proves TCS is still processing */
                Sum_TCS_aliveCounter = (Sum_TCS_aliveCounter + 1U) % 4U;
                Rte_Write_PP_ShutdownPermission_DE_ShutdownPermission(Sum_TCS_aliveCounter);
            }
            break;

        default:
            /* Defensive: reset to INIT */
            Sum_TCS_executionState = TCS_INIT_MODE;
            break;
    }
}

6.5 Runnable_TCS_Dem_Clock

What: Provides the current time to Dem for DTC timestamping.

When: On-demand (operation-invoked), called by Dem when logging a fault event.

Why 5 bytes? Dem stores timestamps as extended data records in DTC snapshots. The 5-byte format matches the TimeSyncMessage wire format, so the timestamp can be directly compared with master clock values during offline analysis.
Scenario Walkthrough — Evaluating Time Sync Quality for DTC Timestamps
Scenario
The Dem module needs to log a DTC with an accurate timestamp. It calls Runnable_TCS_Dem_Clock to get the current time. TCS must evaluate whether it has a valid, synchronized clock before providing the timestamp. If permit_execution is FALSE (module not yet running), TCS returns E_NOT_OK to signal that the timestamp would be unreliable.
Implementation Example — Sum_Tcs_EvaluateClockStatus (from SUM_TCS.c) 
/* Evaluates the current time sync status and provides the timestamp
 * to Dem for DTC logging. Checks permit_execution to ensure the clock
 * is valid before returning data.
 * Called as a client-server operation by the Dem module. */
static FUNC(Std_ReturnType, SUM_TCS_CODE) Sum_Tcs_EvaluateClockStatus(
    P2VAR(uint8, AUTOMATIC, RTE_APPL_DATA) Data)
{
    Std_ReturnType retVal = E_NOT_OK;
    uint64 localClock;

    /* Only provide timestamp if TCS is fully operational */
    if (Sum_TCS_permit_execution != FALSE)
    {
        /* Read current local clock from IRV */
        localClock = Rte_IrvRead_Runnable_TCS_Dem_Clock_EA_Localtime_Clock();

        /* Convert uint64 to 5-byte big-endian for Dem */
        Sum_Tcs_Prv_uint64_to_byteArray(localClock, Data);

        retVal = E_OK;
    }

    return retVal;
}

  • Service-based mode requires UINT8_N signal type; signal-based requires UINT64

10. Code Generation System

Why Code Generation?

TCS code is generated from Xpand templates, not hand-written. This approach:

  • Adapts the C code to the ECUC configuration (e.g., different RTE port names depending on signal references)
  • Supports multiple TimeSyncMessage reception modes from the same template
  • Generates the AUTOSAR SW Component Description (SWCD) matching the code
  • Ensures consistency between code and configuration

14. Parameter Definition (ECUC ParamDef)

Interactive ECUC parameter definition tree for TCS. Click on containers (▶) to expand and view parameters, types, ranges, defaults, and references.

TCS (Timing Client Service) provides global time synchronization for the ECU. It polls a master clock signal, converts it to local time, and manages NvM-backed timestamps for the DEM subsystem. The ParamDef is simple: a single TcsGeneral container with timing and initialization parameters.
▶ M Tcs 0..1 — Timing Client Service module
▶ C TcsGeneral 1..1 6 params 6 refs — timing, execution mask, init config

How TCS ParamDef works with the module
The timing parameters control how often TCS polls the master clock and processes time management. References link TCS to DCM DIDs (vehicle time), DEM (timestamping), NvM (persistent storage), and COM (time sync messages). The PermitExecutionMask defines which SUSD wakeup bits must be set before this module starts.
