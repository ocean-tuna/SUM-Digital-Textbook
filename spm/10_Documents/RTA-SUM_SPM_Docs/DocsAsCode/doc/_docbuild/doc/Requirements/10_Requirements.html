The Payload associated with REQ_STATUS_PROF_STATE responses SHALL use the following fields ( Figure 10 provides an illustration of this message):

  1. Msg Type = 01 (1 byte)

  2. Entry Length (2 byte value counting the number of remaining bytes in this Msg Type)

  3. Activation Profile IDs (4 bytes each) Repeating with Request Status and Profile State

  4. Request Status Value (1 byte) Repeating with Profile IDs and Profile State

    • The request status field SHALL be populated with the enumerations provided Table

    • Note that request status can be of two varieties:

      • An immediate response to a request

      • Unsolicited response to an earlier accepted request because operating conditions have changed

Value

Literal

Description

0x00

NOT_APPLICABLE

Set to this value when the request status field is not used. For example, when the message is used purely for communicating the profile states

0x01

OK_ACTIVATION

Set to this value when an activation request is accepted. The requester is added to the requester list.

0x02

OK_DEACTIVATION

Set to this value when a deactivation request is accepted. The requester is removed from the requester list.

0x03…0xFF

Reserved for more OK’s

These enum values are reserved to protect for future acknowledgements to additional request actions

0x10

REJECTED_REQUEST_INVALID

Set to this value when a request is invalid. A request is invalid if the request is missing required information or that the request contains conflicting information (such as both activation and deactivation for the same profile).

0x11

REJECTED_RESET_DETECTED

Set to this value when a reset of the requester is detected, and the requester is removed from the requester list. This response is given in an unsolicited manner to the requester.

0x12

REJECTED_PROFILE_UNKNOWN

Set to this value when the requested profile is not unknown.

0x13

REJECTED_LACK_OF_PERMISSION

Set to this value when the requester is determined to not have permission to activate the profile being requested. This response may be unsolicited if the permissions can dynamically change.

0x14

REJECTED_LACK_OF_COMPUTATION_RESOURCES

Set to this value when the requested profile cannot be activated or needs to be deactivated due to a lack of computational resources. If the profile was already activated and needs to be deactivated, then all requesters are removed from the requester list. This response may be unsolicited in situations where the availability of the computation resources changes.

0x15

REJECTED_LACK_OF_POWER

Set to this value when the requested profile cannot be activated or needs to be deactivated due to lack of power capability within the vehicle. If the profile was already activated and needs to be deactivated, then all requesters are removed from the requester list. This response would be provided as an unsolicited response in that situation.

0x16…0xFF

Reserved for more reject reasons

These enum values are reserved for future reject reasons.

The following devices SHALL support the stated wakeup mechanisms:

  1. MCB: CAN Wakeup Line

  2. CCU SOCs: Specific MCB-controlled mechanism addressed in MIS001: MCU Farm Startup and Shutdown Requirements

  3. CHM MCU: CAN Wakeup Line

  4. CHM SOC: Specific CHM MCU-controlled mechanism addressed in CHM Power Mode Architecture | SDV-2403

  5. CCU MCU1A/B: CAN Wakeup Line

  6. CCU MCU3s: Specific MCU1A/B-controlled mechanism addressed in MIS001: MCU Farm Startup and Shutdown Requirements

  7. 10-Based T1S Devices: TC10

  8. Devices connected directly to 100M/1GB Ethernet ports (e.g. SADM): TC10

  9. Aggregrator MCUs: TC10, CAN Wakeup Line

  10. CAN Gateway: CAN Wakeup Line

  11. Ethernet Switches and their Host Micros:

    1. Switches capable of waking with TC10 WUP (Wakeup Pulse) on any external facing port and relaying that WUP to other ports based on configuration

    2. Host micros capable of waking up on any incoming TC10 WUP from an external port of the switch it hosts (via INH Line or other circuitry)

PM SHALL power on Target Devices based on the incoming PowerOnDevice request received. Note that this means the following:

  1. send the commands identified by the proper PGTT Waking and Target Device fields in the order of the Wakeup Sequence field, beginning withthe value of 1.

  2. wait for the Wakeup Step Delay period of time before processing the next Wakeup Command in the Sequence.

  3. process all of the Sequence Steps for the given Target Device.

  4. combine consecutive Wakeup Frame steps into the same transmission when the Wakeup Step Delay Field has a value of zero. e.g. Step 1 is Wakeup Frame with bit 8 set and Step 2 is Wakeup Frame with bit 6 set, result is one transmission with both bits 6 and 8 set

  1. process the commands identified by the proper Waking and Target Device fields in descending Wakeup Sequence order, each separated by a calibratable period of time.     2. entries requiring a TC10 command: do nothing.

    3. entries for local activations: refer to Domain-specific Specifications.

When a SM activates a profile due to an ActivateProfile request from a remote host, there is the possibility that the remote host can either die or reset without requesting deactivation. In these conditions, the remote host will not be able to request deactivation even after it restarts because all of the previous requests would be lost. This is a highly undesirable condition since the SM may never be able to deactivate the profile and thus keeping part of the vehicle awake indefinitely. To manage this condition, the SM MUST use MonitorDevice method to request its local PM to monitor the status of the remote host that made the activation request and then subscribe to the DevicePowerState from its local PM get the state of that remote host. As described previously, the PM analyzes the heartbeat from the remote host to determine if the host has gone offline or that a restart has occurred within that host for either the PM or SM functions. When either of these conditions occur, the SM SHALL remove this host as an activation requester from every profile that it has requested previously. This allows the SM the ability to deactivate the profile without receiving an explicit deactivation request from that host. The requesting SM is responsible for re-requesting the activations of profiles upon its restart as it needs. The SM SHALL communicate this action to the requester via the REQ_STATUS_PROFILE_STATE message by setting the Request Status field to REJECT_RESET_DETECTED.
