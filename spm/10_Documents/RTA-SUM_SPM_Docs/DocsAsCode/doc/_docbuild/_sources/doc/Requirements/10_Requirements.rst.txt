    The frame design is given as follows:

    +-------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------+
    | Frame Type  |             Field Name                                                                                                                                      |
    |             +----------------+-----------------+--------------------------------+------------------------+------------------------------+---------------------------------+     
    |             |  Cusotm Header |      Length     | 2nd part SOME/IP Header        | SrcPM_ID               | DstPM_ID                     |              Payload            |
    +=============+================+=================+================================+========================+==============================+=================================+
    |    PM       |  4 Bytes       |      4 Bytes    |          8 Bytes               |  4 Bytes of IP Address | 4 Bytes of Heartbeat Counter |               N/A               |         
    +-------------+                |                 |                                |                        +------------------------------+---------------------------------+
    |    SM       |                |                 |                                |                        | 4 Bytes of IP Address        |       Specific frame Design     |
    +-------------+----------------+-----------------+--------------------------------+------------------------+------------------------------+---------------------------------+


    2nd Part of the SOME/IP header: is added to allow the SOME/IP bridge to consume the PM traffic without a need for special handling for the PM traffic,
    therefore the values below are dummy and not used by the PM logic. The values SHALL be set as follow:

    * Request ID = 0x00000000 (4 Byte)
    * Protocol Version = 0x01 (1 Byte)
    * Interface Version=0x01  (1 Byte)
    * Message Type=0x02       (1 Byte)
    * Return Code=0x00        (1 Byte)

    The Payload associated with SMFrame.PROFILE_REQUEST SHALL use the following fields (See Figure 7 for an illustration):
    
    #. Msg Type = 00 (1 byte)
    #. EntryLength (2 byte value counting the number of remaining bytes in this Msg Type)
    #. Activation Profile IDs (4 bytes each) repeating with Request
    #. Request enumeration (1 byte each) repeating with Activation Profile IDs
        * Request enumeration SHALL be given by the table in:

    ============= ===================== ============================================================================
        Value         Literal                    Description
    ============= ===================== ============================================================================
        0x00            Empty            Not used - avoiding putting a real action request as the default value
        0x01           ACTIVATE          Request to activate a profile
        0x02           DEACTIVATE        Request to deactivate a profile
     0x03...0xFF   Reserved for future   Potential future literals can include ENABLE, DISABLE
    ============= ===================== ============================================================================

    The Payload associated with REQ_STATUS_PROF_STATE responses SHALL use the following fields ( Figure 10 provides an illustration of this message):

    #. Msg Type = 01 (1 byte)
    #. Entry Length (2 byte value counting the number of remaining bytes in this Msg Type)
    #. Activation Profile IDs (4 bytes each) Repeating with Request Status and Profile State
    #. Request Status Value (1 byte) Repeating with Profile IDs and Profile State
        * The request status field SHALL be populated with the enumerations provided Table
        * Note that request status can be of two varieties:
            * An immediate response to a request
            * Unsolicited response to an earlier accepted request because operating conditions have changed

    ============= =========================================== ========================================================================================================================================================
        Value           Literal                                                Description
    ============= =========================================== ========================================================================================================================================================
        0x00       NOT_APPLICABLE                               Set to this value when the request status field is not used. For example, when the message is used purely for communicating the profile states
        0x01       OK_ACTIVATION                                Set to this value when an activation request is accepted. The requester is added to the requester list.
        0x02       OK_DEACTIVATION                              Set to this value when a deactivation request is accepted. The requester is removed from the requester list.
     0x03...0xFF   Reserved for more OK's                       These enum values are reserved to protect for future acknowledgements to additional request actions
        0x10       REJECTED_REQUEST_INVALID                     Set to this value when a request is invalid. A request is invalid if the request is missing required information or that the    
                                                                request contains conflicting information (such as both activation and deactivation for the same profile).
        0x11       REJECTED_RESET_DETECTED                      Set to this value when a reset of the requester is detected, and the requester is removed from the requester list. This
                                                                response is given in an unsolicited manner to the requester.
        0x12       REJECTED_PROFILE_UNKNOWN                     Set to this value when the requested profile is not unknown.
        0x13       REJECTED_LACK_OF_PERMISSION                  Set to this value when the requester is determined to not have permission to activate the profile being requested. This
                                                                response may be unsolicited if the permissions can dynamically change.
        0x14       REJECTED_LACK_OF_COMPUTATION_RESOURCES       Set to this value when the requested profile cannot be activated or needs to be deactivated due to a lack of
                                                                computational resources. If the profile was already activated and needs to be deactivated, then all requesters are
                                                                removed from the requester list. This response may be unsolicited in situations where the availability of the computation
                                                                resources changes.
        0x15       REJECTED_LACK_OF_POWER                       Set to this value when the requested profile cannot be activated or needs to be deactivated due to lack of power
                                                                capability within the vehicle. If the profile was already activated and needs to be deactivated, then all requesters are
                                                                removed from the requester list. This response would be provided as an unsolicited response in that situation.
     0x16...0xFF   Reserved for more reject reasons             These enum values are reserved for future reject reasons.
    ============= =========================================== ========================================================================================================================================================

    The Profile State field shall use the enumeration provided:

    ============= ====================== ========================================================================================================================================================
        Value           Literal                                                Description
    ============= ====================== ========================================================================================================================================================
        0x00            INACTIVE            Set to this value when the profile is valid and is currently in an inactive state.
        0x01            ACTIVATING          Set to this value when the profile is valid and is currently in an activating state.
        0x02            ACTIVATED           Set to this value when the profile is valid and is currently in an activated state.
        0x03            DEACTIVATED         Set to this value when the profile is valid and is currently in a deactivating state.
     0x04...0xFE        Reserved            Reserved for future state expansion.
        0xFF            UNKNOWN             Set to this value when the profile requested is unknown to the SM or when profile requester does not have permission to request the profile.
    ============= ====================== ========================================================================================================================================================

.. req:: Power Graph Mechanisms 
    :id: [$SRS_SPM 0024]
    :status: Accepted 
    :category: Non-Functional
    :sub_category: TO-DO                 
    :source_id: SDVA-5394           
    :test_technique: Integration Testing

    :source_doc: SDV-2017 174 0p0

    The following devices SHALL support the stated wakeup mechanisms:

    #. MCB: CAN Wakeup Line
    #. CCU SOCs: Specific MCB-controlled mechanism addressed in MIS001: MCU Farm Startup and Shutdown Requirements
    #. CHM MCU: CAN Wakeup Line
    #. CHM SOC: Specific CHM MCU-controlled mechanism addressed in CHM Power Mode Architecture | SDV-2403
    #. CCU MCU1A/B: CAN Wakeup Line
    #. CCU MCU3s: Specific MCU1A/B-controlled mechanism addressed in MIS001: MCU Farm Startup and Shutdown Requirements
    #. 10-Based T1S Devices: TC10
    #. Devices connected directly to 100M/1GB Ethernet ports (e.g. SADM): TC10
    #. Aggregrator MCUs: TC10, CAN Wakeup Line
    #. CAN Gateway: CAN Wakeup Line
    #. Ethernet Switches and their Host Micros:
        #. Switches capable of waking with TC10 WUP (Wakeup Pulse) on any external facing port and relaying that WUP to other ports based on configuration
        #. Host micros capable of waking up on any incoming TC10 WUP from an external port of the switch it hosts (via INH Line or other circuitry)

    PM SHALL power on Target Devices based on the incoming PowerOnDevice request received. Note that this means the following:

    #. send the commands identified by the proper PGTT Waking and Target Device fields in the order of the Wakeup Sequence field, beginning withthe value of 1.
    #. wait for the Wakeup Step Delay period of time before processing the next Wakeup Command in the Sequence.
    #. process all of the Sequence Steps for the given Target Device.
    #. combine consecutive Wakeup Frame steps into the same transmission when the Wakeup Step Delay Field has a value of zero.
       e.g. Step 1 is Wakeup Frame with bit 8 set and Step 2 is Wakeup Frame with bit 6 set, result is one transmission with both bits 6 and 8 set

.. req:: Powering down a device requirement 
    :id: [$SRS_SPM 0033]
    :status: Implemented 
    :category: Functional
    :sub_category: TO-DO                 
    :source_id: SDVA-5380           
    :test_technique: Integration Testing
    :comments: 
    :source_doc: SDV-2017 174 0p0
    :doc_version: TODO_DOC_VERSION
    :last_update: Dec 13, 2023

    When powering down a device, the PM SHALL:

    #. process the commands identified by the proper Waking and Target Device fields in descending Wakeup Sequence order, each separated by a 
       calibratable period of time. This is to account for situations where a switch or other mechanisms need to relay the power off signals to the devices
       further away in the Power Graph.
    #. perform the following for each of the entry types:
        #. entries requiring a bit set: send message with zero values where 1's are required for wakeup.
        #. entries requiring a TC10 command: do nothing.
        #. entries for local activations: refer to Domain-specific Specifications.

    PM SHALL broadcast the Heartbeat message at a calibratable periodic rate for the first 3 counts (default 5ms) and a separate calibratable periodic rate for
    all subsequent counts (default 1 second). The periodic rate for the first three transmissions is calibrated to be faster to make sure that recipients can
    receive the heartbeat as quickly as possible even if the initial heartbeat is dropped. The periodic rate for the subsequent counts and the value of the
    counter should also provide a rough idea of the time a device has been awake.

      method to its local PM to request monitoring of a remote requester. The profile state SHALL be updated appropriately based on the request. The
      SM SHALL provide feedback to the requester using the RequestStatusProfileState interface.
    * If the request is determined to be invalid or not permitted, then the SM SHALL provide feedback to the requester using the
      RequestStatusProfileState interface, specifying the appropriate reject reason in the Request Status field and the appropriate profile state in the
      Profile State field.

        * The reject reasons SHALL be those defined in the table Figure 8.
        * If the reject reason is REJECTED_PROFILE_UNKNOWN or REJECTED_LACK_OF_PERMISSION, then the Profile State provided
        * SHALL be UNKNOWN.
        * If the reject reason is otherwise, then the Profile State provided SHALL be the actual state of the profile.

.. req:: Loss of node or reset with requesting SM 
    :id: [$SRS_SPM 0092]
    :status: Accepted 
    :category: Functional
    :sub_category: TO-DO                 
    :source_id: SDVA-5442           
    :test_technique: Integration Testing
    :comments: 
    :source_doc: SDV-2017 174 0p0
    :doc_version: TODO_DOC_VERSION
    :last_update: Dec 13, 2023

    When a SM activates a profile due to an ActivateProfile request from a remote host, there is the possibility that the remote host can either die or reset
    without requesting deactivation. In these conditions, the remote host will not be able to request deactivation even after it restarts because all of the
    previous requests would be lost. This is a highly undesirable condition since the SM may never be able to deactivate the profile and thus keeping part of
    the vehicle awake indefinitely.
    To manage this condition, the SM MUST use MonitorDevice method to request its local PM to monitor the status of the remote host that made the
    activation request and then subscribe to the DevicePowerState from its local PM get the state of that remote host. As described previously, the PM
    analyzes the heartbeat from the remote host to determine if the host has gone offline or that a restart has occurred within that host for either the PM or SM
    functions. When either of these conditions occur, the SM SHALL remove this host as an activation requester from every profile that it has requested
    previously. This allows the SM the ability to deactivate the profile without receiving an explicit deactivation request from that host. The requesting SM is
    responsible for re-requesting the activations of profiles upon its restart as it needs. The SM SHALL communicate this action to the requester via the
    REQ_STATUS_PROFILE_STATE message by setting the Request Status field to REJECT_RESET_DETECTED.


.. req:: Requested SM reset or loss of node 
    :id: [$SRS_SPM 0093]
    :status: Accepted 
    :category: Functional
    :sub_category: TO-DO                 
    :source_id: SDVA-5444           
    :test_technique: Integration Testing
    :comments: 
    :source_doc: SDV-2017 174 0p0
    :doc_version: TODO_DOC_VERSION
    :last_update: Dec 13, 2023

    There is also the converse situation where a SM makes a request to a remote SM and the remote SM goes offline or experiences a reset in its power
    management components. In these conditions, the requesting SM may incorrectly assume that the swEntities it has requested are active when they are
    not.
    To manage this condition, the SM MUST also subscribe to the status of the host of the requested SM via the DevicePowerState topic via its local PM. Note
    that in this case, because the SM made a PowerOnDevice request to its local PM for the remote SM host, there's no need to do a MonitorDevice request.

    * If the state of the remote host becomes Off, then this SM MUST request deactivation of all profiles that it has requested previously from that host.
    * If a restart condition has been detected, then the SM SHALL re-request all profiles that it previously requested to that host.

    When transmitting the Wakeup Frame, SPM SHALL set the bits by applying **OR** logic to the following:

    #. the bits required based on internal requests from the Power Graph Traversal Table
    #. the bits received from any incoming Wakeup Frame (either CAN or Ethernet) that has been received since the last time SPM transmitted the Wakeup Frame.

    Example if the Wakeup Frame was 4 bits in length:

    * internal requests (0100) OR 
    * Rx Wakeup Frame 1 (0001) OR
    * RX Wakeup Frame 2 (1000) = Tx Wakeup Frame (1101)
  
    since the last time SPM transmitted the Wakeup Frame.

    SUM SPM SHALL do the following when attempting to activate an activation profile:

    #. Find if the profile dependencies are remotely provided services by using the Sd_GetNodeAddress API defined in SDV-8201. If the IP Address is found for these dependencies, the SPM sends a remote 
       ACTIVATE command as defined in SDV-2017. 
    #. For the profile dependencies that are local AND the profile dependencies that are remote with the activation status received as ?ACTIVATED?, SPM uses the SUM SrvcMgr client server operation 
       SrvcMgr_ActivateServices defined in SDV-8201 to activate the profile dependencies.
    #. For every profile dependency in Step 2:

        a. If the return value of the service activation operation SrvcMgr_ActivateServices is 
           E_OK_LOCAL_ENABLED or E_OK_REMOTE_ENABLED, SPM enables the corresponding PDU-Group for that service.
        b. If the service is unknown or calibrated off (return value is E_DISABLED or E_NOT_OK) the SPM 
           skips activating PDUs for this dependency.

    SUM SPM SHALL do the following when attempting to de-activate an activation profile:

    #. Find if the profile dependencies are remotely provided services by using the Sd_GetNodeAddress API
       defined in SDV-8201. If the IP Address is found for these dependencies, the SPM sends a remote DE-ACTIVATE command as defined in SDV-2017. 
    #. For the profile dependencies that are local AND the profile dependencies that are remote with the 
       de-activation status received as ?DEACTIVATED?, SPM uses the SUM SrvcMgr client server operation  SrvcMgr_ActivateServices defined in SDV_8201 to de-activate the profile dependencies.
    #. For every profile dependency in Step 2: 
        a. If the profile service is used by other profiles, SPM shall not deactivte the service for this dependency.
        b. If the profile PDU groups are used by other profiles, SPM shall not disable the PDUs for this dependency.
        c. If no other profile uses the service, SPM shall deactivate the service for this dependency using SrvcMgr_ActivateServices.
        d. If no other profile uses the PDU Groups, SPM shall disable PDUs for thie dependency.
        e. If the service is unknown or calibrated off (return value is E_DISABLED or E_NOT_OK) the SPM 
           skips deactivating PDUs for this dependency.

    SUM SPM SHALL provide a sender receiver interface SPM_ServiceActivationStatusNotification_Ifc
    as described below to provide Indication to other SUMs (SSFM, SSC ..etc.) about the activated service list and 
    if setting a DTC is allowed based on DTC suppression Timer as defined in SDV-8002. SUM SSFM uses that to 
    determine services to start monitoring and when to inhibit setting of DTCs (Loss of Function, invalid data?etc).
    SPM_ServiceActivationStatusNotification_Ifc interface dataElement definition:

    .. code:: 

        SPM_ServiceActivationStatusNotification_Ifc.DataElement {
            Uint16* serviceIdList, // List of Services Activated
            bool* dtcAllowedList, // List of DTC Allowed Boolean 
            uint16 listLength // Length of the 2 output lists
        }

    **NOTE**: The dtcAllowed flag will be set to true by default and will never change. There is no plan to use this flag  in the initial usage of the SPM because the SPM waits for the status of the activated 
              activation profile to be ?ACTIVATED? before activating the services and the PDU groups as specified in SPM_0031 and SPM_0032
    **NOTE**: The list will maintain the up to date active services list at any point in time and should not change in the case of losing the Heartbeat of a remote device with a profile that the local SPM has 
              activated (i.e. Loss of Node DTC should not affect this interface so that the Loss of Function can occur)
