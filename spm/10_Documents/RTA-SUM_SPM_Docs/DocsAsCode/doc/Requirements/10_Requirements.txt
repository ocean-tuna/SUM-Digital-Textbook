.. req:: No Title
    :id: [$SRS_SPM 0003]
    :status: Not Implemented

    The frame design is given as follows:

    +-------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------+
    | Frame Type  |             Field Name                                                                                                                                      |
    |             +----------------+-----------------+--------------------------------+------------------------+------------------------------+---------------------------------+     
    |             |  Custom Header |      Length     | 2nd part SOME/IP Header        | SrcPM_ID               | DstPM_ID                     |              Payload            |
    +=============+================+=================+================================+========================+==============================+=================================+
    |    PM       |  4 Bytes       |      4 Bytes    |          8 Bytes               |  4 Bytes of IP Address | 4 Bytes of Heartbeat Counter |               N/A               |         
    +-------------+                |                 |                                |                        +------------------------------+---------------------------------+
    |    SM       |                |                 |                                |                        | 4 Bytes of IP Address        |       Specific frame Design     |
    +-------------+----------------+-----------------+--------------------------------+------------------------+------------------------------+---------------------------------+


    2nd Part of the SOME/IP header: is added to allow the SOME/IP bridge to consume the PM traffic without a need for special handling for the PM traffic,
    therefore the values below are dummy and not used by the PM logic. The values SHALL be set as follow:

    * Request ID = 0x00000000 (4 Byte)
    * Protocol Version = 0x01 (1 Byte)
    * Interface Version=0x01  (1 Byte)
    * Message Type=0x02       (1 Byte)
    * Return Code=0x00        (1 Byte)
    
    **NOTE**: the SM/PM communication is designed to look like event notifications over SOME/IP, hence the message type being 0x02. This
    includes use cases where one SM is making a request to another SM and the requested SM subsequently providing response back to the
    requesting SM.

    The Payload of the SMFrame is used to convey activation commands, deactivation commands, and/or Status information. All SMFrame messages SHALL
    be sent with the ID *0xFFFD 8FFF*. (service ID / method ID).
    
    **NOTE**: service ID 0xFFFD is used to avoid conflict with other actual SOME/IP services in the vehicle. Also the value 0xFFFF is avoided to
    prevent conflict with uProtocol, where 0xFFFF is a reserved wild-card.

    | The Payload associated with SMFrame.PROFILE_REQUEST SHALL use the following fields (See Figure 7 for an illustration):
    
    #. Msg Type = 00 (1 byte)
    #. EntryLength (2 byte value counting the number of remaining bytes in this Msg Type)
    #. Activation Profile IDs (5 bytes each) repeating with Request

    ============= ===================== ============================================================================
        Value         Literal                    Description
    ============= ===================== ============================================================================

        0x02           DEACTIVATE        Request to deactivate a profile
     0x03...0xFF   Reserved for future   Potential future literals can include ENABLE, DISABLE
    ============= ===================== ============================================================================

    | The Payload associated with REQ_STATUS_PROF_STATE responses SHALL use the following fields ( Figure 10 provides an illustration of this message):

    #. Msg Type = 01 (1 byte)
    #. Entry Length (2 byte value counting the number of remaining bytes in this Msg Type)
    #. Activation Profile IDs (5 bytes each) Repeating with Request Status and Profile State
    #. Request Status Value (1 byte) Repeating with Profile IDs and Profile State
        * The request status field SHALL be populated with the enumerations provided in Table
        * Note that request status can be of two varieties:
            * An immediate response to a request
            * Unsolicited response to an earlier accepted request because operating conditions have changed

    ============= =========================================== ========================================================================================================================================================
        Value           Literal                                                Description
    ============= =========================================== ========================================================================================================================================================
        0x00       NOT_APPLICABLE                               Set to this value when the request status field is not used. For example, when the message is used purely for communicating the profile states
        0x01       OK_ACTIVATION                                Set to this value when an activation request is accepted. The requester is added to the requester list.
        0x02       OK_DEACTIVATION                              Set to this value when a deactivation request is accepted. The requester is removed from the requester list.
     0x03...0xFF   Reserved for more OK's                       These enum values are reserved to protect for future acknowledgements to additional request actions
        0x10       REJECTED_REQUEST_INVALID                     Set to this value when a request is invalid. A request is invalid if the request is missing required information or that the    
                                                                request contains conflicting information (such as both activation and deactivation for the same profile).
        0x11       REJECTED_RESET_DETECTED                      Set to this value when a reset of the requester is detected, and the requester is removed from the requester list. This
                                                                response is given in an unsolicited manner to the requester.
        0x12       REJECTED_PROFILE_UNKNOWN                     Set to this value when the requested profile is not unknown.
        0x13       REJECTED_LACK_OF_PERMISSION                  Set to this value when the requester is determined to not have permission to activate the profile being requested. This
                                                                response may be unsolicited if the permissions can dynamically change.
        0x14       REJECTED_LACK_OF_COMPUTATION_RESOURCES       Set to this value when the requested profile cannot be activated or needs to be deactivated due to a lack of
                                                                computational resources. If the profile was already activated and needs to be deactivated, then all requesters are
                                                                removed from the requester list. This response may be unsolicited in situations where the availability of the computation
                                                                resources changes.
        0x15       REJECTED_LACK_OF_POWER                       Set to this value when the requested profile cannot be activated or needs to be deactivated due to lack of power
                                                                capability within the vehicle. If the profile was already activated and needs to be deactivated, then all requesters are
                                                                removed from the requester list. This response would be provided as an unsolicited response in that situation.
        0x16       REJECTED_LACK_OF_THERMAL_CAPABILITY          Set to this value when the requested profile cannot be activated or needs to be deactivated due to a lack of thermal management capability for the 
                                                                CCU. If the profile was already activated and needs to be deactivated, then all requesters are removed from the requester list. This response 
                                                                would be provided as an unsolicited response in that situation.
        0X17       REJECTED_PROFILE_BLOCKED                     Set to this value when profile activation is blocked due to pending update/shutdown/suspend-to-RAM
        0X18       REJECTED_LOSS_OF_HEARTBEAT                   Set to this value when the heartbeat from the requester is determined to be lost and the request is rejected, and
                                                                requester is subsequently removed from the requester list
     0x19...0xFF   Reserved for more reject reasons             These enum values are reserved for future reject reasons.
    ============= =========================================== ========================================================================================================================================================

.. req:: PGTT Target Device

    :last_update: Nov 11, 2024

    | The PGTT SHALL then specify all the remote device wakeup that can be executed from this device. To do so, it will populate the following fields for
      each target device

    #. Target Device Name - this is the official network name for the target device (e.g. FARM_VMC)
    #. Nickname
    #. IP Addresses (can have multiple)
    #. Diagnostic Address
    #. DTC Base ID
    #. DTC Timeout
    #. Intermediate Node Wakeup Frame Handling Information
        a. Directly Managed by the Waking Device?
        b. Wakeup frame 
        c. Wakeup bit
    #. 1 or more wakeup sequences
        a. Command type 
        b. Command value
        c. Step Delay     

    When an intermediate node receives a wakeup frame (CAN or Ethernet) where bits are set to 1 for devices 
    that are managed by the intermediate node, the intermediate node uses the Intermediate Node Wakeup Frame Handling Information 
    for the various target devices to understand the wakeup action it should perform. This information is 
    written for each target device. The boolean field Directly Managed by the Waking Device identifies if 
    the target device is a device that the intermediate node is directly managing so that a wakeup action 
    must be taken when the intermediate node receives a wakeup frame with this device's bit set to true. 
    The Wakeup frame field identifies the wakeup frame (A or B) that this target device bit resides. 
    Then the Wakeup bit field identifies the actual wakeup bit within that frame corresponding to this 
    target device.

.. req:: Transmit Wake-up frame Periodicity
    :id: [$SRS_SPM 0045]
    :status: Implemented 
    :category: Functional
    :sub_category:                  
    :source_id: SDVA-5013           
    :test_technique: Integration Testing
    :comments: 
    :source_doc: SDV-2017 27.179.0p0
    :doc_version: 
    :last_update: Dec 20, 2024


    | PM SHALL transmit the wakeup frame in the following way
    
    * On start of transmission or a change in transmitted frame content, the PM SHALL transmit the changed frame within 5ms of the change and transmit in a burst periodic fashion for a calibrated amount of time at a calibratable time interval.
    * After the burst period is over, the frame SHALL be transmitted at a steady state calibratable periodic rate.
    
    When there is no longer any device to be activated, the PM SHALL transmit an all-zero wakeup frame for 3 steady state periodic intervals and then stop transmitting the frame.

.. req:: SM determine validity of the profile (de)activation requests 
    :id: [$SRS_SPM 0077]
    :status: Implemented 
    :category: Functional
    :sub_category:                  
    :source_id: SDVA-5430           
    :test_technique: Integration Testing
    :comments: How to provide this? Port? Callout? we just have service information by port from SPM
    :source_doc: SDV-2017 27.179.0p0
    :doc_version: 
    :last_update: Nov 11, 2024

    Upon receiving an activation request, the SM SHALL first determine if the request is valid and permitted.

    * This determination SHALL be performed separately for each profile requested.
    * If the request is determined to be valid and permitted, then the SM SHALL add the requester to the list of requesters for the requested profiles. If
      the requester was already on the requester list for that profile, then it does not need to be added again. The SM SHALL also use MonitorDevice
      method to its local PM to request monitoring of a remote requester. The profile state SHALL be updated appropriately based on the request. The
      SM SHALL provide feedback to the requester using the RequestStatusProfileState interface.
    * If the request is determined to be invalid or not permitted, then the SM SHALL provide feedback to the requester using the
      RequestStatusProfileState interface, specifying the appropriate reject reason in the Request Status field and the appropriate profile state in the
      Profile State field.

        * The reject reasons SHALL be those defined in the table Figure 8.
        * If the reject reason is REJECTED_PROFILE_UNKNOWN or REJECTED_LACK_OF_PERMISSION, then the Profile State provided
        * SHALL be UNKNOWN.
        * If the reject reason is otherwise, then the Profile State provided SHALL be the actual state of the profile.

    Please, take into account that *If the request is determined to be invalid or not permitted* point is not implemented.

      remote SM. But the response was not received by the requesting SM.
    * SM makes an activate request to a remote SM. It subsequently receives a response indicating that the request was accepted, and the profile is in
      an activating state. When the profile state changes to Activated, this profile state was sent by the requested SM but not received by the
      requesting SM.

    In each of these cases, the requesting SM SHALL resend the request periodically for as long as the profile is still required to be activated until a response
    is received

.. req:: Loss of node or reset with requesting SM 
    :id: [$SRS_SPM 0092]
    :status: Implemented 
    :category: Functional
    :sub_category:                  
    :source_id: SDVA-5442           
    :test_technique: Integration Testing
    :comments:  
    :source_doc: SDV-2017 27.179.0p0
    :doc_version: 
    :last_update: March 03, 2025

    When a SM activates a profile due to an ActivateProfile request from a remote host, there is the possibility that the remote host can either die or reset
    without requesting deactivation. In these conditions, the remote host will not be able to request deactivation even after it restarts because all of the
    previous requests would be lost. This is a highly undesirable condition since the SM may never be able to deactivate the profile and thus keeping part of
    the vehicle awake indefinitely.
    To manage this condition, the SM MUST use MonitorDevice method to request its local PM to monitor the status of the remote host that made the
    activation request and then subscribe to the DevicePowerState from its local PM get the state of that remote host. As described previously, the PM
    analyzes the heartbeat from the remote host to determine if the host has gone offline or that a restart has occurred within that host for either the PM or SM
    functions. When either of these conditions occur, the SM SHALL remove this host as an activation requester from every profile that it has requested
    previously. This allows the SM the ability to deactivate the profile without receiving an explicit deactivation request from that host. The requesting SM is
    responsible for re-requesting the activations of profiles upon its restart as it needs. The SM SHALL communicate this action to the requester via the
    REQ_STATUS_PROFILE_STATE message by setting the Request Status field to REJECT_RESET_DETECTED.


.. req:: Requested SM reset or loss of node 
    :id: [$SRS_SPM 0093]

    There is also the converse situation where a SM makes a request to a remote SM and the remote SM goes offline or experiences a reset in its power
    management components. In these conditions, the requesting SM may incorrectly assume that the swEntities it has requested are active when they are
    not.
    To manage this condition, the SM MUST also subscribe to the status of the host of the requested SM via the DevicePowerState topic via its local PM. Note
    that in this case, because the SM made a PowerOnDevice request to its local PM for the remote SM host, there's no need to do a MonitorDevice request.

    * If the state of the remote host becomes Off, then this SM MUST request deactivation of all profiles that it has requested previously from that host.
    * If a restart condition has been detected, then the SM SHALL re-request all profiles that it previously requested to that host.

.. req:: PGTT information required
    :id: [$SRS_SPM 0164]
    :status: Implemented
    :category: Functional
    :sub_category: 
    :source_id: SDVA-7328
    :test_technique: Integration Testing
    :comments:
    :source_doc: SDV-2017 27.179.0p0
    :doc_version: 
    :last_update: Sep 15, 2025

    The PGTT SHALL first identify the following characteristics for each device in the power graph:

    #. Is device an intermediate node?

        a. This identifies whether or not the device is an intermediate device that has the responsibility of performing tasks required for intermediate devices, such as receiving ethernet wakeup frames and then sending CAN wakeup frames. Devices which are not
           intermediate nodes will disable functions that are exclusively performed by intermediate nodes.
    #. IP address of the MCU where ethernet wakeup frame SHALL be unicasted to from this device.

        a. This field is only applicable for an edge device that will send ethernet wakeup frames to a controlling MCU. e.g. MCU3 sending
           ethernet wakeup frame to MCU1a/1b or CCU SoC sending the wakeup frame to MCB.
        b. The field SHALL be left empty for intermediate nodes in the power graph.
    #. Heartbeat related IP address information:

        a. Each VLAN on which the heartbeat will be broadcasted
        b. The source IP address used for heartbeat on each VLAN
        c. The destination IP address (multicast IP address) used for heartbeat on each VLAN
    #. The wakeup mechanisms that can be used to wake up this device
        a. This field is specified as an integer in hex form

            i. 0x00 = TC10
            ii. 0x01 = CAN Wakeup Frame
            iii. 0x02 = CAN Network Management Frame
            iv. 0x03 = Board level wakeup (GPIO)
        b. This field is used to support testing, where based on the information here, the testing procedure can be appropriately to apply the correct wakeup mechanism to wake up the device under test. This attribute is not used to configure the SM/PM software

    #. The calibratable wakeup frame information for this device
        a. Wakeup Frame
            i. WUF A
            i. WUF B
        b. Wakeup Bit: from 0 to 63, where 0 is LSB of first byte

    The PGTT SHALL then specify all the remote device wakeup that can be executed from this device. To do so, it will populate the following
    fields for each target device:

        #. Serial Data Name
        #. Nickname
        #. IP Addresses (can have multiple)
        #. Diagnostic Address
        #. DTC Base ID
        #. DTC Timeout
        #. 1 or more wakeup sequences
        #. Command type
        #. Command value
        #. Step Delay

.. req:: Profile activation data to record
    :id: [$SRS_SPM 0175]
    :status: Accepted
    :category: Functional
    :sub_category: 
    :source_id: SDVA-6813
    :test_technique: Integration Testing
    :comments:

    :doc_version: 
    :last_update: Nov 11, 2024

    | To support these use cases, the following diagnostic data SHALL be supported

    | *Activation Profiles Binary Activation Status:*

    * This data is used to allow a user to query various controllers which profiles managed by the controller are currently active.
    * Because the number of profiles managed by a device can be in the hundreds, this data SHALL be constructed as a bit field where each bit is mapped to a profile on that device. A bit is set to 0 if the profile mapped to that bit is inactive. It is set to 1 if the profile mapped to that bit is NOT inactive.
    * The mapping between the bit field and the profile is established by the profile YAML file.
    * This DID is not intended on providing more detailed information about each profile such as how long the profile is active etc.
    * This DID is intended to be used by engineers not service technicians to support use cases 1 and 4.

    | *Off Power Mode Locally Activated Activation Profile Records:*

    * This data captures the following information regarding the last 5 profiles that were directly locally activated in previous off-power mode session
    
        * Profile ID
        * Cumulative amount of time the profile was active
        * Number of times the profile was activated
    * When more than 5 profiles were activated in the last off-power mode session, the data recording follows a first-in first-out storage approach to limit the record to the last 5 profiles
    * Upon entering a new off-power mode session (i.e. transition from a non-Off state to Off), the data in the DID will be erased and recording shall start again.
    * This data SHALL be stored in NVM so that the data can be kept across key-cycles AND battery disconnect.
    * This diagnostic data directly supports use case 2.
    * This data also supports use case 3 if data collection mechanisms are put in place to collect the stored data into a longer-term storage location (e.g. CCU SoC or back-office) before entering a new Off-power session.

    | * Off Power Mode Remotely Activated Activation Profile Records:*

    * This data captures the following information regarding the last 5 profiles that were remotely activated in previous off-power mode session
        * Profile ID
        * IP address of the last remote requester
        * Cumulative amount of time the profile was active
        * Number of times the profile was activated
    * When more than 5 profiles were activated in the last off-power mode session, the data recording follows a first-in first-out storage approach to limit the record to the last 5 profiles
    * Upon entering a new off-power mode session (i.e. transition from a non-Off state to Off), the data in the DID will be erased and recording shall start again.
    * This data SHALL be stored in NVM so that the data can be kept across key-cycles AND battery disconnect.
    * This diagnostic data directly supports use case 2.
    * This data also supports use case 3 if data collection mechanisms are put in place to collect the stored data into a longer-term storage location (e.g. CCU SoC or back-office) before entering a new Off-power session.

.. req:: Auto Transmission of TC10 on wake-up
    :id: [$SRS_SPM 0206]
    :status: Not Implemented.
    :category: Functional
    :sub_category: 
    :source_id: SDVA-6825
    :test_technique: Integration Testing

    | There are use cases where a SE-D waking up due to a hardware input needs to very quickly wakeup the MCU farm (MCU1/MCU3).
    | To support this need, the ethernet switch SHALL support the following two types of automatic TC10 transmission from aggregators to MCU1A/B, MCB, and CHM MCU. This allows the MCU1A/B, MCB, CHM MCU to start its wake up while the aggregator is still in the
      process of waking up since the TC10 will be transmitted as soon as the ethernet switch on the aggregator is awake enough to transmit the TC10 pulse

    * Type 1: an ethernet switch on a device is configured to send a TC10 out on a port whenever it is awakened (regardless of the mechanism that woke it up).
    * Type 2: an ethernet switch on a device is configured to send a TC10 out on a port whenever it receives TC10 on a port. This is commonly referred to as TC10 forwarding.
    * Both types of configurations are configured statically.

.. req:: E0D7 Support
    :id: [$SRS_SPM 0221]
    :status: Implemented
    :category: Functional
    :sub_category: 
    :source_id: IDOC-1437
    :test_technique: 
    :comments: 
    :source_doc: SDV-6001 
    :doc_version: 27.27.184.1p0
    :last_update: March 03, 2026

    The SDV-6001's req describes the overall behavior of the DID 0xE0D7 as SUM's level. 

    Three RxID are in scope of SPM:
    
    - 0x02 = Remote PN/AP Active, No Local PN/AP Active. 
    - 0x20 = Locally Active AP
    - 0x26 = WUF Received, No PN/AP Active

    The requirements specifies that:

    RxID:

    0x02 At least one remote PN or AP is active (a partial network or activation profile is active that the ECU participates in), 
    no local PNs or APs are active (the ECU is not activating any partial networks or activation profiles), and no private networks are active.

    0x20 An activation profile has been locally activated.

    0x26 Any WUF is received with valid wake up bits.

    RxWR/RxLAR:

    For Record {X} ID = 0x02 .. If the ECU supports activation profiles, this field does not need to be supported.
    For Record {X} ID = 0x20, this field does not need to be supported. 
    For Record {X} ID = 0x26, this field shall be set to the last byte of the WUF’s CAN ID or IP Address.

    * **Access**: R
    * **Session**: D, E
    * **Availability**: A, U

    * Profile ID 5 – Service ID [2 bytes, IDN]
    * Profile ID 5 – Profile Number [1 bytes, IDN]
    * Profile ID 5 Activity Timer [3 bytes, UNM 0-16,777,215, seconds]
        * Cumulative amount of time that the profile was active.
    * Profile ID 5 Activation Count [1 byte, UNM 0-255]
        * Number of times the profile was directly locally activated

    This record shall be managed in the same manner as DID E0D7 as defined in the Activity Records section of SDV-6001.

    =====================   ========================= ===================== ========== ==========

.. req:: Usage of interfaces PowerOnDevice/PowerOffDevice and DevicePowerState
    :id: [$SRS_SPM 0246]
    :status: Accepted
    :category: Interface
    :sub_category:
    :source_id: GM-SDV-2017-402
    :test_technique: Integration Testing
    :comments:
    :source_doc: SDV-2017
    :doc_version: 27.27.182.3p1
    :last_update: Oct 1st, 2025

    SPM **SHALL** execute the Power operation on a remote Target_Device as follows:

    #. *SM* requests a power operation to *PM* setting PowerOnDevice/PowerOffDevice
    #. *PM* executes the Power-up/Power-down sequence from Power Graph Traversal Table
    #. *PM* sets the MonitorDevice interface to enable health check operation on the Target Device based on the heartbeat reception from the Target_Device
    #. *PM* updates the DevicePowerState interface to notify to SM the status of the Target_Device

    .. uml::

        @startuml
        !pragma teoz true

        box local_ECU
            box SPM
                entity SM 
                entity PM
            end box
            participant ComStack as lcs
        end box

        box Target_Device
        participant Com_Stack as rcs
        participant rem_SPM
        end box

        SM -> PM: PowerOnDevice(TrgIp)/PowerOffDeviceIp(TrgIp)
        PM -> PM: ParsePGTT(//In//: TrgIp, //Out//: wkup_seq)
        PM -> PM: MonitorDevice(//In//: TrgIp, //In//: True)
        PM -> lcs: //Rte//
        lcs -> rcs: //Send frames and commands (Wakeup and Heartbeat)//
        rcs -> rem_SPM: //Rte//
        rem_SPM -> rcs: //Rte//
        rcs -> lcs: //Send frames and commands (Heartbeat)//
        lcs -> PM: //Rte//
        PM -> PM: UpdateTargetPowerState(//In//: Heartbeat.SrcIp)
        SM -> PM: DevicePowerState(//In//: Heartbeat.SrcIp)

        @enduml

.. req:: Heartbeat Value for Shutdown Pending
    :id: [$SRS_SPM 0266]
    :status: Implemented 
    :category: Functional
    :sub_category:                  
    :source_id: SDVA-4221           
    :test_technique: Integration Testing
    :comments:
    :source_doc: SDV-2017 27.27.184.0p0
    :doc_version: 
    :last_update: Mar 18, 2026

    Shutdown Pending is defined as any HeartbeatCounter value >= 2^32-256 (0xFFFFFF00). SPM SHALL interpret any HeartbeatCounter received from a remote device in the range [0xFFFFFF00 .. 0xFFFFFFFF] as a shutdown pending indication.


.. req:: Heartbeat Value for Secondary and Tertiary Power Off
    :id: [$SRS_SPM 0267]
    :status: Implemented
    :category: Functional
    :sub_category:
    :source_id: SDVA-7474
    :test_technique: Integration Testing
    :comments:
    :source_doc: SDV-2017 27.27.184.0p0
    :doc_version:
    :last_update: Mar 18, 2026

    A host with multiple power-off states SHALL transmit the Heartbeat message with a HeartbeatCounter value of 2^32-2 (0xFFFFFFFE) for its secondary power off state and 2^32-3 (0xFFFFFFFD) for its tertiary power off state. The same pattern applies for additional power off states as required. SPM (non-Linux, non-MCB) SHALL recognise these values on reception as shutdown pending indications (see $SRS_SPM 0266) but SHALL NOT transmit them.
